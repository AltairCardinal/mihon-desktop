# 主干安卓版与原版：下载章节打开差异及优化方案

日期：2026-11-03。分析基线为本地主干 `b3efe1469e4a0dbda798c121891ba1fe6c36f48e`；被测产品逻辑来自 `0db8c3ddf37e28e2ca1a895cf21accbeee05a0e0`，随后只增加诊断探针。原版为官方 Mihon 0.19.9，以及对应的隔离上游探针构建。本轮只做既有数据复算、代码与文件清单读取，没有修改产品、操作设备或取得新的性能样本。

后续用户要求先取得优化结果、完整验证后置。新会话执行以[优化方案与roadmap](../../roadmap/2026-11-03-downloaded-reader-startup-optimization-roadmap.md)为准：首轮只做A0–A3的最小红绿、优化构建与三次原场景采样；本文第6节的较完整验证不再全部作为首轮前置条件。历史数值和性能目标不变。

## 1. 结论

主干当前最应优先处理的是 **Android 页表发布前的全章原图元数据读取屏障**，不是先优化窗口启动、解码器或双页评分算法。

同一平板、史莱姆第04卷、单页 RTL、同一旧表采集方法下，上游探针版初始化到漫画首次绘制为 **243.3 / 196.9 / 222.3ms**，主干为 **646.8 / 632.7 / 651.7ms**。三样本平均差为 **422.9ms**；主干页表就绪前的全187页 header facts 遍历平均 **404.2ms**，在量级上相当于这个差额的 **95.6%**。当前测量没有将遍历移除，不能把95.6%解释为已经通过干预证明的因果贡献率。

代码确认：主干必须等全页遍历结束才发布页表；上游没有这项前置工作。现行非阻塞呈现协议已允许未知事实与临时分组，当前页自身可用即可继续显示。因此，**拆除整章前置依赖、保留当前页可信元数据与原有事实链**，是证据最充分、范围最小的首选方案。

这项元数据并非只供双页匹配使用，还关联尺寸、EXIF方向与内容身份。应改变获取时机和工作范围，不能删除可信元数据、把未知方向猜成普通竖图，或回退原图认证保护。

## 2. 比较口径与数据

### 2.1 身份与可比范围

- 同一 PCE-W30 / Android12(API31)，同一41,380,343B CBZ、187张WebP、目标第1页；文件SHA256为 `b3d7c4e56e58dfee6d9da7d5afafe12b267ccc6d50dd48cd3660456b8d2b4677`。
- 三样本顺序都是新进程首次①、同进程再次、新进程首次②。均正常进入主界面和详情后点击章节；不是应用启动全过程，也不是冷磁盘测试。文件复制/哈希已预热缓存。
- 两个探针包均使用单页RTL，横图自动放大和阅读模式提示关闭；相同原MKV+Perfetto协议。上游RTL另由原件 `prefs-app.mihon.benchmark-reader-0.xml` 确认。没有混用主干先前LTR试跑。
- 官方安装版 `app.mihon` 保持不变；上游探针包 `app.mihon.benchmark` 与主干探针包 `app.mihon.desktop.fork.benchmark` 的APK、签名、私有库、source元数据和运行状态并不完全相同。实际ART compiler filter均不能凭历史 `speed Success` 判为相同。
- 数据允许按相同语义端点描述产品差异；不是同次随机A/B，不用于计算探针净开销。主干保留原 `ReaderDiagnostics`，两版新增探针的实现也不完全相同。三样本不能提供可靠P95。

均值仅用来概括这三份观察，性能验收仍分别检查首次和再次样本。上游 `PAGE_LIST_READY` 在 `getPages()`、绑定章节和发布Loaded之后；主干在共享物化及全章header之后。虽然工作量不同，边界同为“目标章节页表可交给后续显示链”，所以可以描述性比较。不能假装两个事件之前执行了相同操作。

`OPEN_READER_INTENT` 实际位于ViewModel初始化，不是触摸或真正发Intent。`OPEN_PAGE` 不是读取完成；`DECODE_SUBMIT` 不是底层解码CPU开始；`FIRST_DRAW` 是应用图像绘制回调，不是物理屏幕呈现。两版首绘接线实现有差别，但都针对目标漫画内容，仍应继续用外部画面交叉验证。

当前数据不支持“主干解码慢了400ms”：第四段并未出现这样的增加。也不支持“所有差异都来自探针”：原版探针包的外部黑屏仍短，而主干存在明确的额外前置I/O链。

## 3. 为什么全章检查昂贵

### 3.1 首图必须排在全章检查之后

真实调用链：

1. `ReaderViewModel.loadChapter` 等待 `ChapterLoader.loadChapter` 返回，之后才继续当前章节的owner与正常显示链。
2. `AndroidReaderChapterContentPort.loadChapterContent` 调用 `loader.getPages()`，取得归档条目对应的ReaderPage。
3. 对每个Ready且有stream的页绑定章节、encoded引用，并调用 `publishHeaderFact()`；全部完成后才返回descriptors。
4. 共享materialize返回后，`ChapterLoader.completePageListLoad` 才发布页表和 `PAGE_LIST_READY`。
5. 已Loaded复用路径也有全页header循环；只有PREFETCH免除，不按单页/双页模式区分。

这在IO上下文执行，**不是主线程同步卡死**；但它仍是首图必须等待的前置依赖。再次打开也未免除：有效元数据缓存保存在页对象中，并不等于跨阅读器会话保留所有页事实。本轮再次打开仍实测412.4ms全章遍历。

源码入口：[ChapterLoader](../../../app/src/main/java/eu/kanade/tachiyomi/ui/reader/loader/ChapterLoader.kt)、[AndroidReaderMaterializePorts](../../../app/src/main/java/eu/kanade/tachiyomi/ui/reader/loader/AndroidReaderMaterializePorts.kt)、[ReaderPage](../../../app/src/main/java/eu/kanade/tachiyomi/ui/reader/model/ReaderPage.kt)。

### 3.2 “header”实际会读多少

`publishHeaderFact()` 先执行 `source.peek().readByteArray()`，然后才检查元数据完整性、解析EXIF和尺寸。默认读取上限为512KiB，达到EOF前并不会因为已经拿到尺寸就停止。

本轮只读CBZ目录，得到188个归档条目、187张WebP；图片最小9,216B、最大467,784B，全部小于512KiB；编码数据合计 **41,348,502B，即39.433MiB**，均为ZIP_STORED。因此在本轮新建页、事实未缓存且成功读取的路径中，代码会把这187张图的编码内容读完以检查元数据。这是**代码与文件清单推导**，不是新增的逐字节运行时计量，也不等于39.4MiB都来自物理磁盘，更不等于完整解码187张位图。

`ArchiveReader.getInputStream(name)` 每次还会新建归档读取器，从头逐条定位目标；全章逐图打开会重复定位。当前400ms区间没有细分归档定位、读取、解析、分配和调度各自占比，不能据此指定JNI或EXIF为唯一慢点。来源：[ArchiveReader](../../../core/archive/src/androidMain/kotlin/mihon/core/archive/ArchiveReader.kt)、[读取上限](../../../domain/src/commonMain/kotlin/mihon/domain/reader/ReaderDualPageFactLimits.kt)。

### 3.3 Windows为何没有这一整章屏障

Desktop的 `ReaderScreenModel.bindDualFactPublisher` 围绕当前目标、认证所需事实和既有有界邻页窗口，挑选Ready且仍需原图几何的页，再通过 `pageContentOwner.acquireHeader` 取得资料；它不会在章节页表发布之前依次打开187张图。筛选页对象不等于打开每一张图片。Android已有的单页 `PagerPageHolder` 与双页 `DualPagerPageHolder` 也能在正常图片链中为本页发布header，并核对有效身份。

这说明应让两端遵循相同的“显示所需优先、增强事实按需补齐”语义，而不是要求Windows也增加整章遍历。本轮没有新增Windows同章节、同视觉端点测量，不能从Android数字计算Windows的当前差距或宣称Windows已达标。

## 4. 原版作为目标：怎么要求而不混淆指标

沿用[双端基准](../../evidence/reader-startup-performance-baseline-2026-11-02.md)，不放宽既定要求：

| 目标 | 判定办法 |
| --- | --- |
| 官方原版的短黑屏体验 | 对登记参考场景，继续采用无内容间隔≤60ms的工程预算；原表官方上界33–54ms。三份主干样本下界均超过60ms，当前明确未满足 |
| 快速响应 | 保留≤100ms工程预算，但必须核实实际画面/图层；约90ms的首TX只能说明窗口帧代理值，不能单独判漫画或真实内容响应通过 |
| 首漫画实际可见 | 同设备、内容、设置、外部协议下不慢于官方参考；不能靠延长转场、冻结详情、显示无关图或降低画质掩盖等待。源PTS约284/289ms为已取得的历史参考，需同协议补主干端点 |
| 内部定位目标 | 探针条件下向上游首次222–243ms、再次约197ms靠拢。它是工程诊断参照，不能写成“未修改官方的内部耗时已测得” |
| 正确性 | 当前页/方向/恢复位置正确；迟到配对不搬动已绘画面，不漏页、不伪造已读，不破坏失败重试及手动记录 |

单页与双页都适用体验目标；本轮数值只证明单页问题。双页还须分别记录首目标页可读和当前阅读单元完整可读，不能借单页成绩替双页验收。Windows沿用体验目标，按本机真实端点单独计时，不能借用平板内部毫秒数证明性能。

## 5. 优化顺序与边界

### P0：解除整章header与页表发布的依赖

**建议首先实施的唯一主方案。** 保留页表自然排序、`page.chapter`、`encodedPageRef`、descriptors、generation及Loaded发布检查；解除ContentPort和Loaded复用分支的全章同步header循环。页表与身份准备完成即可激活章节。

当前可见页继续沿单页/双页holder的原有header→方向核验→解码→before-draw链；配对资料继续沿现有有界事实请求、permit及取消机制补齐。UNKNOWN owner可由已有原子快照建立；后续真实方向由 `acceptOrientedFact` 接收。临时分组不回灌为Certified，目标自身几何与像素锁仍必须成立。

不增加模式开关，不发起187个后台任务，也不在首帧之后无条件继续整章扫描。否则只是把I/O争抢和耗电挪到翻页期间，并未实现按需获取。

这与现行[非阻塞设计4.1/5节](../../2026-11-01-reader-nonblocking-pairing-design.md)一致，不需要放宽原图身份或配对正确性规则。共享 `ReaderPageDescriptor` 本身不要求几何，因此无须为此重写共享页表模型或增加平行状态系统。

**收益预算，非预测：** 若只做算术假设“全章遍历消失，其他区间完全不变”，主干总计变成249.811 / 220.327 / 248.503ms，均值239.547ms；比上游仍多6.498 / 23.444 / 26.208ms，均值18.717ms。真实改动仍会支付当前页及既有挂载窗口的元数据成本，也可能改变调度、配对与帧机会，不能承诺实际净省404ms或直接达标。

### P1：P0实测后，仅处理仍存在的差距

移除全章遍历后的算术场景中，第一段剩余均值约118.8ms，上游约109.7ms；页表→当前页调用均值38.3ms，上游21.7ms。优先用原有事件确认剩余成本是否仍在这些位置；不凭区间名称认定其中16.6ms全是可删工作。

若本页元数据仍昂贵，可单独研究复用正常图片链已经取得的同一编码内容，或按格式读取最小充分元数据。当前完整性规则对PNG要求IEND、WebP要求RIFF全长；“读前几KB”“没看到EXIF就按NORMAL”会破坏方向可信度。归档skip也可能实际读取/解压。该方向必须单独验证完整性、EXIF1–8、预算、失败与重试，不能捆绑P0直接缩短读取上限。

若P0后已达到原版目标，即停止扩大优化。当前没有证据要求先重写归档后端、添加持久header缓存、换解码器、扩大并发或加入新调度器。

### 必须保留的行为

- 当前页可以是恢复的第126页，不能只优化page0；单/双/AUTO切换继续使用真实源页锚点。未知前缀和迟到伙伴不能挡住正常目标，也不能移动已绘像素。
- 宽图、EXIF、内容版本变化必须正确。UNKNOWN不等于PORTRAIT，临时默认不等于Certified。普通显示位图不能自动充当原图分析证据。
- 损坏header保留FAILED及重试序号，正常图片沿既有错误/重试链。取消继续传播，旧pages/owner/generation/attempt回调不能授权新呈现或制造已读；物理操作真正退出后才释放资源。
- 不新增仅按URI、长度或mtime认定可信的缓存。当前storage reset token只处理online→downloaded转换，不保证识别SAF同URI原地替换；若将来做跨会话缓存或热替换，须另有可靠内容身份与失效设计。
- Android条漫当前未沿相同方式消费 `page.contentFact` 方向。P0保持其现有显示语义，并验证条漫切单/双页时事实补齐；不能据此声称条漫方向适配已全部等价。
- 手动配对读取失败保留原记录、未知revision及禁写限制；配对失败不能重新变成基本阅读门禁。

### 不重启既有负结果

已读[档案索引](README.md)、[R6–R9裁定](history/engineering/DECISIONS-R6-R9.md)、[R10处置](history/engineering/R10.md)。本轮新增条件是真机单页首图前实测约400ms全章header I/O，而非认证评分内核变慢。

不因此重启A2/A3/A4、Strong、摘要树/全章索引、弱图片复用、预测调度或扩大缓存。相关方案的负结果与适用限制仍成立；既有A1评分、方图空采样、同绑定请求提升继续保留。P0只修正资料取得时序，不更改配对算法或预算。

## 6. 后续实施的最小验收方案

本节是实施建议，不表示已经执行或通过。

1. **先写真实阻塞红测。** 用生产ChapterLoader与真实形状下载归档，保持远处非显示所需页的元数据读取挂起，当前页可读；应能发布页表并由实际holder产生目标像素。现实现会在全章遍历被扣住。分别覆盖首次加载和已有Loaded路径，核对页序、引用与generation保留。
2. **按需工作回归。** 在合法挂载/预取窗口外的页没有被提前打开；单页RTL、双页代表路径、恢复中间页、迟到宽图/伙伴及切模式都保持源页锚点和已绘内容。不能只断言Ready或空容器。
3. **复用受影响focused保护。** 选择真实header/EXIF、流替换、旧回调拒收、取消关闭、图片重试、未知revision禁写的对应测试。将旧“必须在整章物化时完成header”的时序断言改为真实按需生产者行为，保留其取消/失败保护。已有metadata retry基线红项见主干采集报告；不冒称整类全绿，不用跳过掩盖触及路径的问题。只在相应风险不能被focused覆盖时申请扩大验证。

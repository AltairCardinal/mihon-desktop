# 同步 DEMO 交互审查与调整清单

- 日期：2026-09-13
- 前提：用户已审核通过[技术方案](../2026-09-13-multi-device-sync-technical-proposal.md)。
- 审查对象：当前[并列双端 HTML DEMO](multi-device-sync/README.md)，交互基线 a2d870e32。
- 本轮仅检查和记录，不修改 DEMO 界面、模型或生产代码。
- 后续决定（2026-09-13）：用户明确要求 DEMO 只用于调整交互，不投入资源修复逻辑错误。因此第 5 节的“先修模型再补交互”顺序已被覆盖；已按此要求补充模拟交互，入口和边界见 [DEMO 说明](multi-device-sync/README.md#新增交互的审阅路径)。以下 A1–A6 保留为历史观察，不代表本次已修复。
- 方法：技术方案与源码静态对照；Chrome 独立会话打开 http://127.0.0.1:50943/，核验 Windows/Android 配置、真实双端阅读同步、待处理、失败重开、计数与批量。浏览器中的模拟数据只存在于隔离会话，没有操作用户已打开的页面。
- 结论：既定界面结构可保留；存在需要优先修正的交互偏差，也缺少已批准方案要求的配置、导入和恢复场景。真实 Git、加密和数据库尚未实现，本身不作为 HTML 交互缺陷。

## 1. 建议保留的设计

书架顶栏同步入口、旋转/数量/无状态的表达、同步高位底部子面板、同面板设置返回，以及直接位于列表上方的多选操作条均可继续使用。

保留更新底栏只提示漫画更新、取消类批量边界、待上传三行的简洁呈现、收起后不回放临时通知，以及手机/PC并列深色预览。不恢复已经删去的独立待处理摘要栏和状态三行说明小字，不引入感叹号或第四种顶栏错误角标。

建议围绕现有结构补充内容和状态，不重做导航。

## 2. 需要优先修正的现有偏差

### A1：正在阅读时仍会被后台同步跳页

**已在浏览器复现。** PC正在看《星海骑士》第1页；手机到第19页后上传，使用外部演示栏触发PC后台同步，PC画面直接变成第19页。手机继续至第20页并重复交换，PC又跳到第20页。

界面同时声称“当前正在阅读时不会自动跳页”。这是 DEMO 行为与已批准设计不一致，不是技术方案要求自动跳页。

原因证据：[app.js](multi-device-sync/app.js) 的 renderReader 使用 readPositions；[sync-model.js](multi-device-sync/sync-model.js) 的 applyIncoming 即使 readingActive 也更新 readPositions。已有 currentReadingPositions 并未作为该画面的显示权威。

**调整：** 当前阅读会话固定使用本机已采用的位置。收到新位置仅建立待处理候选；用户选择采用后才换页。继续翻页/记录当前位置也必须基于当前会话，而不是尚未采用的远端位置。后台到达不得切换页面或阅读模式。

**验收：** PC停在第1页，手机上传第19页 → PC后台同步 → PC仍在第1页，出现可处理的候选；采用之后才到第19页。

### A2：阅读候选显示和实际采用的内容不一致

**已在浏览器复现。** 同一本漫画先收到第19页、后收到第20页；条目显示“远端阅读位置：第19页”，点击“采用此位置”，实际采用第20页，并清掉该书所有候选。

证据：renderRemoteSuggestion 只取 remoteSuggestions[0]；adoptRemotePosition 优先取 pendingRemotePositions[objectId] 中的最新值。

**调整：**

- 用户看到哪个候选，就按该候选的稳定ID和版本执行，不能从另一个“最新值”缓存替换。
- 能证明第20页是第19页的后续时，合并成一个显示第20页的当前候选；不能排序的并发位置保留在同一决定内比较。
- 条目至少显示漫画、章节、来源设备和位置；详情显示本机与各端位置。
- 明确区分“采用此位置”“保留本机位置并同步”。返回表示暂不处理，不暗中批准。
- 候选已失效时刷新条目，不执行过期按钮；无法验证页码时提供“从本章开头继续”。

**验收：** 列表显示第19页时不允许实际采用第20页；若第19页已失效，先更新可见内容。一本书一个待决定事项内可查看全部有效候选。

### A3：顶栏数量与“待手动处理的同步”列表不是同一口径

**已在浏览器复现。** 清理默认取消后，PC收到两条阅读候选：顶栏角标为2，面板没有待处理标题，显示“当前设备没有待确认项目”，下方只有一条阅读候选。

原因：顶栏计 confirmations + conflicts + remoteSuggestions，面板标题只计前两类；阅读候选又只渲染第一条。同书线性后继还被按原始事件数重复计入。

**调整：** 保留现有一个待处理列表，把取消、冲突、阅读选择和后续待匹配/导入恢复纳入统一的有效事项集合。角标、列表标题和空状态使用同一集合；同一对象同一字段需要一次决定，就计一项。

类型较多时可在列表附近提供轻量筛选；默认显示全部。多选只作用于取消收藏/关注，不把阅读选择或匹配加入“全部确认取消”。空状态改为“当前没有待手动处理的同步”，且只在整个事项集合为空时出现。

**验收：** 只有阅读候选时，列表可见且不显示空状态；同书第19→20页的因果后继合并为一项；任何角标数量都能在列表中找到对应决定。

### A4：同步过程与结果的几个数字容易误导

**已在浏览器复现：**

1. PC未执行同步，手机独立同步后，PC的“最近交换”仍从模拟03:00变为04:00；当前设备状态借用了共享时间。
2. PC开始同步时有1条待上传，运行期间新增1条；结束显示上传2条、接收2条、待上传0。模型到定时回调时才读取全队列，也把本机刚上传的事件计入接收。

这说明 DEMO 尚未表达方案中的“冻结本轮集合”和“来自其他设备的接收”语义，不能据此声称真实系统已经丢数据。

**调整：**

- 时间显示为“本设备上次同步成功”，记录每台设备自己的结果。
- 本轮开始冻结待上传集合，运行期间新增操作继续显示在待上传三行；本轮成功只清已确认发布集合。
- “接收”不把本机自己上传的事件算作其他端新数据；“已接收”“已应用”“待手动处理”在结果详情中区分。
- 结果未知时显示“正在核对上传结果”，数量继续保留；部分完成显示“本次同步部分完成”，提供详情与重试。
- 阅读类三行中的第三行建议改名“阅读记录”，涵盖续读、已读/未读和历史，仍不增加小字。

**验收：** 初始1条，运行中新增1条 → 第一轮确认上传1条，待上传剩1条；来源端上传不虚增接收；另一台设备运行不刷新本端成功时间。

### A5：关闭临时通知后，没有地方查看上次未完成的问题

**已在浏览器复现。** PC离线手动同步失败，收起面板，恢复网络再重开：旧通知正确消失，但模型仍保存失败结果，面板没有错误详情入口，只剩当前收藏待处理/队列状态。

**调整：** 继续让临时通知收起后消失。在现有状态摘要区为尚未恢复的问题提供“上次同步未完成 · 查看详情”，详情按原因给“重试”“更新访问令牌”“核对恢复密钥”等动作。不要把旧 snackbar 常驻回来。

顶部运行状态与取消待处理、传输错误可同时存在。遇到失败不能因为另有一条取消而让失败原因完全不可见；成功重试后解除问题状态。

**验收：** 收起后没有旧临时通知，但未解决的问题仍可查看和修复；成功恢复后不继续显示失败。

### A6：冲突选择没有准确说明业务和传播范围

**通过真实模型构造场景并在浏览器核验。** 作者白河的关注/取消关注冲突被写成“相反的收藏决定”，来源显示内部ID phone-a。按钮是“保留本地 / 采用远端”，用户选择前看不到它会生成新的上传决定；点击后待上传关注确实增加1条。

**调整：**

| 场景 | 建议表达 |
| --- | --- |
| 收藏冲突 | “电脑B：保留收藏；手机A：取消收藏” |
| 作者冲突 | 使用“关注/取消关注”，显示“手机A”等设备名 |
| 冲突中的选择 | “保留收藏并同步 / 取消收藏并同步”，作者同理 |
| 普通取消的处理 | 继续“确认 / 忽略”；详情说明只处理本设备，忽略不产生反向上传 |
| 阅读位置分歧 | 显示双方章节/页码，明确选择是否形成新的同步决定 |

选择取消时说明仍需其他接收端各自确认，不能让“并同步”被理解为一次批准全端删除。用详情承载解释，不把长说明塞回三行状态或所有普通列表行。

**验收：** 选择前能判断改什么、影响哪台设备、是否上传；作者不再使用收藏文案；内部设备ID不出现在面向用户的决定文案。

## 3. 已批准方案要求补齐的流程

这些属于原型覆盖不足，不等同于现有功能失效。优先用模拟状态表达，不在本轮审查中接入真实凭据或Git。

### B1：配置与恢复密钥

当前双端设置只有“启动时自动同步”“后台定期同步”，没有仓库、连接测试或密钥入口。

保留书架 → 同步 → 齿轮 → 设置子页面，补“同步服务”和“设备”分组：

~~~text
未配置 → 设置同步
  ├─ 创建同步空间 → GitHub专库 / 本设备访问令牌 → 连接测试
  │                → 保存恢复密钥 → 确认初始导入
  └─ 加入已有空间 → GitHub专库 / 本设备访问令牌 → 导入恢复密钥
                   → 验证 → 协调本机已有数据
~~~

设置显示服务、仓库、设备名和连接状态；支持更新凭据、查看恢复资料、断开连接。令牌遮罩，密钥只在显式查看/导入步骤显示；演示时使用明确的模拟数据。创建空间的设备不成为永久主设备。

补空库待初始化、权限不足、令牌失效、密钥不匹配的代表状态。更换空间需明确新的导入范围，不能一个“连接”按钮无提示混合旧空间。

当前设置标题下“仅此设备”将变得不够准确：保留用于自动执行偏好，服务/空间区明确区分共享空间与本设备凭据，不暗示更换空间或恢复密钥都只有本地影响。

### B2：首次导入与旧备份恢复

配置成功不能直接把当前书架当作刚发生的重新收藏。补一次导入摘要：本机已有多少收藏、关注、阅读，解释与其他设备合并，提供“开始合并”。

这是首次导入步骤的摘要，不是恢复已删掉的同步面板待处理摘要栏。

代表场景：

- 空设备加入：显示正在接收已有数据，不上传空书架清除其他端。
- 双方已有不同收藏：显示合并结果。
- 本机旧收藏遇到远端仍有效的取消：进入待处理恢复候选，提供“保留取消”“重新收藏并同步”。
- 旧取消已被新的重新收藏覆盖：按当前有效结果合并，不因为历史出现过取消就额外弹确认。
- 恢复中断/继续：保留已完成部分及待处理，不伪造新操作。

### B3：周期和自动执行边界

当前固定写“每60分钟同步一次”，没有周期选择。

补“同步频率”行，默认1小时，可选15分钟/1小时/6小时/24小时。Android说明“系统允许时自动同步”，Desktop说明“应用运行期间执行”。说明放在设置页，主面板不加常驻解释。

关闭自动同步仍记录用户操作，手动按钮保持可用。已关闭的自动触发不应先给出“更新中”的工作动画再告诉用户跳过；模拟栏可反馈未执行，产品运行状态保持空闲。

### B4：阅读与无法匹配对象的代表场景

当前原型只有续读位置；补充：

- 章节已读/明确未读在两端传播，以及相反决定的比较。
- 无痕阅读不进入上传队列；退出无痕不补上传之前记录。
- 来源不可用：条目说明相关漫画与来源，可“查看来源 / 重试匹配”。
- 作者同名无法对应：显示候选来源和作品依据，用户明确关联。
- 章节已定位但页码无法验证：提供从该章开头继续。
- 本机清除历史不抹除远端；重复旧事件不立刻恢复被屏蔽条目。

这些事项沿用统一待处理列表及同面板详情，不新增底部导航或平级页签。

### B5：长批量的处理中、部分完成与恢复

当前120项演示已有多选、全选、反选、冻结集合和确认范围，浏览器核验“多选条直接在列表上方”及“80本漫画/40位作者，仅本机取消”的说明正确，可以保留。

补长任务的“已处理 N/M”、已完成/跳过/失败结果及剩余项恢复。推荐有“停止后续处理”动作：保留已完成结果，剩余项仍待处理，不假装回滚全部。

仅收起同步面板不应被暗中当作撤销已确认批量；如果允许后台继续，应在本次处理区域说明。应用中断后重新打开能看到未完成事项。全部处理只处理当时有效取消集合，新到达项不纳入。

## 5. 调整顺序与边界

建议后续按两批进行：

1. **先修正已有链路：** A1–A6，确保阅读不会被跳页、选择与实际结果一致、数量和同步状态可信。补对应失败测试后再修改，不重做现有布局。
2. **再补齐审核所需流程：** B1–B5，用模拟场景覆盖配置/密钥、首次导入、周期、匹配和部分完成。复用现有面板及预览栏，演示条件继续留在产品外。

后续不需要让HTML实现完整Git、真实加密、SQLDelight或系统后台调度，也不需要把协议版本、操作ID、因果图和Git提交细节暴露给用户。这些由生产实施验收；DEMO负责让用户看清入口、选择和结果。

本次清单是审查交付，尚未应用到DEMO。

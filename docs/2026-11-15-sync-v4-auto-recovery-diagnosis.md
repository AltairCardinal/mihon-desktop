## 结论与范围

指定构建不能自动接续一个已有的 `BLOCKED/UNKNOWN` 同步任务。原始异常发生于旧构建的本地投影阶段；v4 启动后沿用该任务，却没有重新处理它。不能将其描述为“v4 再次发生了相同 SQLite 异常”。

本轮确认了造成持续停滞的恢复策略和调度缺口；没有找回原始 SQLite 异常的具体错误码，因此不能认定最初原因是数据库锁、损坏或磁盘故障。修改目标是由应用负责诊断、保全、恢复和验证，不再要求用户点击检查、重试、清理数据库或重新配置来处理程序内部故障。

## 已证实的原因与其他缺口

| 层次 | 观察及代码位置 | 判断 |
| --- | --- | --- |
| 最初故障 | 旧构建 `setHeads` 抛出 SQLiteException | 类别与位置已证实；具体 SQLite 原因未知，锁冲突仅是假设 |
| 错误分类 | `SyncDatabaseExchange.syncProblem()` 没有 SQLite 分类，落入 UNKNOWN | 丢失可恢复性语义；未知错误最终进入 BLOCKED |

| 延迟恢复接线 | `DesktopSyncScheduler.kt:38-55`、`SyncRuntime.kt:686` | 启动只检查一次；持久化重试未到期时返回但未安排到期唤醒。周期关闭时可无限等待；源码推导，本轮未单独执行此场景 |
| 远端变化接线 | 原仓库 `SyncRuntime.kt:1319`、`:1362`，scheduler `:43` | runtime 增加 REMOTE_CHANGED 退避，而 scheduler 仍只消费 NETWORK 完成事件；不是完整自动恢复链。源码推导，不能归因于本次 SQLite 异常 |
| 恢复入口 | 原仓库 `SyncPanelController.kt:959`、`:2018` | 用户打开恢复页后才开始自动检查，不满足无人操作的恢复目标 |

因此，仅把错误页改成“稍后重试”、只放宽网络重试次数，或让用户重新点击同步，都不能解决本次问题。

## 修改设计（待实施）

复用现有 Runtime、RunStore、InboxProjector、RecoveryWorkflow 和平台 scheduler，不新增第二套同步引擎。承接既有[异常流程审计](2026-10-07-sync-exception-flow-audit.md)与[恢复闭环审查](2026-10-07-desktop-sync-recovery-closure-review.md)，本次将程序内部故障的恢复触发从用户操作移到后台。

### 1. 故障事实与恢复策略分开

- 在同步边界识别平台数据库异常。共享层消费统一分类，Desktop adapter 提供 SQLite 主/扩展错误码；Android 使用对应 adapter，不能在共享逻辑依赖 JDBC 类型。
- BUSY/LOCKED 等明确瞬时故障：先确认事务已回滚，再对整个幂等投影事务做有限短退避；仍失败则保存检查点和后续自动探测 deadline，避免占用 UI 或持续抢锁。不能只重试事务中某条 SQL。
- 网络/限流/服务暂不可用：保存到期时间，尊重 Retry-After 和账户级 gate。远端 head 改变：重新读取并校验同一空间的最新 head，重新协调原计划，不丢失未发布操作，不无限重用过期候选。
- CORRUPT、NOTADB、约束异常及未知异常不能一律转为网络失败。保存固定故障类别、SQLite code、阶段、尝试和恢复步骤；不记录 SQL 参数、作品名、token、仓库地址或任意 exception message。

### 2. 升级后自动接管旧 BLOCKED

不能直接将所有 BLOCKED 变成 RUNNING，也不能用“取消旧轮次并新建”绕过检查点。

1. 启动后台恢复先核对活动空间、代数、授权 epoch、owner 和显式暂停/停止状态；只接管本机无 owner 的已接受任务，事务 claim 防止启动、周期、网络回调重复执行。
2. 对旧 UNKNOWN 做一次有界的本地恢复探测：保留已接收事件和回执，按现有 dirty 字段与幂等投影继续；本次现场应在该步骤即可推进，不必请求用户检查数据库。
3. 本地投影成功后沿用 `confirmReceived` 和原计划收尾。网络可用、身份复核通过时继续原任务剩余工作。只有所有计划、回执和必要业务选择实际完成才成功。
4. 探测再次失败时使用新记录的具体错误分类决定下一步。短时错误退避；同一不可恢复故障进入持久化冷却和自动健康复核，保存失败指纹及最近进展，避免每次打开面板或重启都重复昂贵操作。
5. 若需重建派生投影，必须先证明可从完整持久事件、heads、决定及本地未上传操作确定性重建；先在独立 staging 验证，再在身份/owner 栅栏下原子应用。条件不足则保全和等待，不能清空数据库、丢弃坏批次或悄悄换空间。

旧 UNKNOWN 记录缺少错误码，只允许受栅栏保护的本地探测，不能据 UNKNOWN 推定数据库安全、授权有效或给予远端写许可。

### 3. 调度以持久状态为准

- 启动、每次状态改变及休眠唤醒后，统一查询当前可恢复任务的 deadline 并注册唯一 wake job；不再仅依赖某次 NETWORK completion 的瞬时事件。
- 定期同步开关控制新轮次，不能使已接受轮次的到期恢复丢失。用户明确暂停、取消或关闭连接则撤销相应恢复；“定时同步关闭”与“用户停止这轮任务”分开判断。
- deadline 同时考虑任务退避和账户 gate；到期重新核对身份、owner 和截止时间。任务完成、切空间、注销、停止应用时取消旧 job。休眠/时钟跳变后重新计算，避免重复运行和忙循环。
- 共享恢复准入/策略由 Runtime 提供；Desktop 管理进程内唤醒，Android 复用其现有后台调度 adapter，分别覆盖平台接线。

### 4. 用户反馈与不可自动解决的边界

这里是 PROJECT_POLICY，尚未实现。复用现有共享同步面板与通知状态，不新增诊断向导或模态错误弹窗。

- 普通系统异常由后台恢复；面板给出正在恢复、下次检查时间和实际新增确认数。打开/关闭面板不启动或停止恢复，不抢焦点、不重复 Toast。
- 图源暂不可用：保留待应用内容，在源恢复/安装状态变化或计划的后台复核后再应用；一个对象失败不阻断已经可以安全推进的对象。不得将等待或隔离项计为成功。
- 用户业务决定保持既有语义；本次留下的取消收藏确认不应由故障恢复擅自决定。其他同步工作继续，面板明确“同步技术恢复”与“业务待确认”。
- 网络断开、GitHub 撤权、密钥永久丢失、真实磁盘损坏等不能承诺凭空恢复。应用负责保全、自动复核及条件恢复后的续接；只有用户身份同意或业务选择本身不可替代时才需要用户动作，不能要求其诊断错误、操作数据库、重新建仓库来绕过程序故障。
- 本次不实现自动更新、重建账号或静默更换空间。持续程序缺陷保留未完成状态与本地诊断，不能通过隐藏失败项实现“没有异常”。

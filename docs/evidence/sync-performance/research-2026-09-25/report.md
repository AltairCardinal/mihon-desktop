# 同步进一步提速预研（追加2%额度）

研究基线：`ebc652bed6`（生产代码同 `a0142effab`）。本轮只做隔离本地诊断与可撤销原型，不落地生产、不构建发布、不访问真实同步仓库。复用一名实施代理，主代理独立分析与复核；约1.5%停止新增实验，余量用于交付，2%为总上限。额度统计是工作假设估算，不是官方账户扣减。

## 研究问题与判定

1. 上轮H100暖增量从23请求变30请求，是否因为冷读只验证递归结果而没有复用直接子树？先记录真实路径与OID对应，再做原型；只看总请求减少不足以解释因果。
2. 若有安全的内存复用路径，用相同H100 profile各3样本比较；成功标准为消除已归因的冗余请求、完整同步中位至少改善10%，并保持首次冷读与相关安全契约。10%是本轮探索性阈值，不替代既有发布门禁。
3. 其他候选只做源码成本模型与优先级评估，不同时实现GraphQL、批量发布和解密缓存。任何模型数字均不冒充测得耗时。

## 源码确认的剩余工作

### 单批发布重复付出的成本

`SyncDatabaseExchange`每轮`uploadNext`只发布一个协议批次；`GitHubSyncTransport.publish`的正常无冲突路径按批执行仓库私有性读取、tree创建、commit创建、ref更新、ref读取和commit读取，另有按制品/目录决定的blob/tree请求。每次发布确认都会解析新快照。现有256事件/512KiB是单协议批次边界，不是Git提交只能携带一批的限制。

仅对上述六个固定往返计数，B批、每组K批的模型可减少 `6 × (B-ceil(B/K))` 次请求。以每次50ms纯串行延迟计算，B=40、K=8是192次/9.6秒；B=391、K=8是2052次/102.6秒。这里40/391仅是假设事件装满256边界时10k/100k事件对应的批数，不是现有Scale实际上传批数；不含字节传输、限流、冲突和组容量约束。**这不是已实现或已测提速**，组装制品仍须先持久化，未知结果整体对账，组内index链及最终actor head必须一致。

### 历史验证可能随批次数累积

每个变化快照都遍历全部index并调用decryptShard，之后完整验证actor链、batch路径和guard证据。若初始H个历史批次、随后B批逐个发布，每次确认解密的index数量（含bootstrap）合计为 `BH + B(B+1)/2 + B`，不含初始读取、预制品校验、重试等额外工作；这是正常路径的源码推导，不是CPU耗时。

有界解析结果缓存能减少重复AEAD/JSON，但不能因此跳过旧路径消失/修改、链连续性或guard。键必须包含空间/代次、路径、OID、密钥验证上下文与解析版本，失败不入缓存；容量、断连/换账号与重启均单独验收。若主要成本在后面的排序/guard/SQL，解密缓存的整体收益会有限。

### 无变化快照仍有全历史本地工作

`SyncSnapshotManifestStore.findWarmSnapshot`读取全部normalized entries/batches并计算checksum；`validateWarmAdmission`又计算传入对象checksum、再次读取全部normalized记录并计算checksum。随后`SyncOutboxExchange.uploadNext`再次observe当前快照时，guard仍排序并重建完整证据。减少网络请求不等于这个路径为常数成本。

这些复核保护caller-owned可变List、数据库内容变化和owner/fence。优化方向应先建立真正不可变且绑定验证上下文的快照/证据所有权，再讨论复用；不能只凭head相同删除校验。当前结论为源码证据，未测SQL行数/分段CPU，不能据此预报倍率。

## 实验结果

### 同轮H100实测

沿用真实Runtime/文件SQLite/MockWebServer链路，100个历史批次，再新增一次收藏并完成确认；准备历史和冷下载不计入warm阶段。每个样本重新建库、缓存目录、fixture；响应首部延迟50ms、正文10Mbit/s，并模拟上传字节延迟。基线和原型各3个独立样本，按组先后运行，未随机交替、未独占机器，不报告p95或统计显著性。

| 样本 | 当前生产基线 ms | 最终门控原型 ms |
| --- | ---: | ---: |
| 1 | 2504 | 2082 |
| 2 | 2432 | 2070 |
| 3 | 2412 | 2109 |
| 中位 | **2432** | **2082** |
| 范围 | 2412–2504 | 2070–2109 |
| 每次HTTP总数 | 30 | 23 |
| 每次tree GET | 17 | 10 |
| 每次blob GET | 3 | 3 |

中位减少350ms（**14.4%**），请求减少23.3%，通过本轮探索阈值≤2188ms。减少的7个串行请求在50ms注入延迟下恰对应350ms；这是与请求消除机制一致的观测，不能外推为任意网络都快14.4%，也不能证明CPU变快。最终原型保留当前实例目录上限和快照准入门控，不用更宽松的早期原型结果充当最终数值。

### 7个额外请求的具体来源

日志将请求OID与前次递归响应中的目录映射对照，确认是前次已验证、下一轮却重新GET的旧目录：

- `.mihon-sync/index/bootstrap`
- `.mihon-sync/index/bootstrap/0`
- `.mihon-sync/index/device-0`
- `.mihon-sync/index/device-0/1`
- `.mihon-sync/batches/device-0`
- `.mihon-sync/batches/device-0/1`
- `.mihon-sync/heads/device-0`

原冷读逐树验证完后只返回平铺blob结果，既未写raw tree L2，也未保存可跨transport复用的direct entries；`SyncOnboarding.transport`每次构建新实例，因此只填原实例L1不能解决。本原型把**全树和根OID全部校验成功**后的各目录direct entries放入另一个有界共享内存缓存，键包含API origin、repository、branch、tree OID、validationScope、connectionRevision；没有把递归JSON写入raw L2，没有缓存凭据或HTTP客户端。下一轮改变head后的分层读取继续按原逻辑验证，命中只替代不可变对象请求。

### 独立审查与真实失败

主代理检查了准入顺序、缓存key、锁和容量算法，并指出两个跨实例边界：

1. 高目录上限实例的条目不能绕过低上限实例限制；最终共享读取保留当前`maxTreeEntries`检查。
2. 第一轮安全集合59项中58项通过、1项失败：manifest checksum损坏后共享缓存挡住了原契约要求的远端树重读。没有改测试放宽语义。最终只允许当前transport已经成功准入/验证快照（`hasValidatedSnapshot`）后使用shared；新实例准入失败时走原远端读取。该失败项定向复验通过，同次H100三样本仍保持23请求与上述收益。

原型前一版本在集中集合中完成首次300单样本：连接419ms、7请求、tree GET1，保留首次冷读请求收益。但最终门控修正后没有再次跑首次300或整个59项集合，所以这不是最终版本完整安全/首次性能认证。容量淘汰、跨账号/密钥/连接隔离、并发/取消、新进程、Android及真实网络均未专项测量；原型不跨OS进程持久化，不保证进程重启后的首次增量获得该收益。未实际埋点解密次数或SQL行数，相关成本仍只作源码推导。

本轮完成的是**请求来源归因、可撤销原型和有界收益验证**，不是生产优化发布。生产代码最终恢复研究基线，仅提交报告、补丁与日志。


## 落地候选与安全前提（按收益证据排序）

1. **已验证direct tree的跨轮有界内存复用**：本轮唯一实作原型。须覆盖manifest损坏后的强制重读、scope/key/账号隔离、不同目录上限、容量淘汰、并发和取消。单实例L1不够，因Runtime每轮新建transport；共享层只能保存经过真实OID验证的目录直接子项，不保存token/client，不写伪造raw tree L2。4MiB为估算权重上限，且与原L1各自独立，不是整个应用额外内存峰值已证≤4MiB。
2. **多批次原子发布**：面向大量首次上传的潜力比只消除7个请求更大，但本轮只有成本模型。为保护首次确认体验，可先单独发布首批，再对余下批次有界分组；必须另测B=40/391等多批场景，现有300收藏/两批样本不足以验收此方案。组容量还受正文和本地冻结制品资源边界约束。
3. **解析结果与不可变证据复用**：优先补计数/分段测量，再选择解密缓存或manifest/guard重复工作。不要同时改完整安全验证和发布协议，避免无法归因收益与恢复失败。

GraphQL、下载流水线、压缩与原生Git继续后置：它们尚无新增实测依据，而且不能自动消除本地历史验证成本。本轮不是优化穷举，也不能证明已找到全局最优。

## 首次上传与原生Git的比较口径

本节记录预研结束时的口径；后续已完成 [1,600 条真实形状书架的配对对照](../git-comparison-1600-2026-09-25.md)：同制品 REST 88.516s、原生 Git 14.592s，受控模型下速率为 Git 的 16.5%，并非真实 GitHub 或架构速度上限。

当时尚无Git同条件对照。首次300收藏的现有REST端到端中位5.333秒不能除以一个猜测的Git耗时；暖增量原型14.4%也不能外推至首次上传。

Git push通过receive-pack接收一组对象的pack并验证/更新ref，具备批量传输能力，见[Git官方pack协议](https://git-scm.com/docs/gitprotocol-pack)。因此应优先研究减少REST逐批发布与确认次数；不能据此断言原生Git必然在任意输入下最快，也不能把明文数据库或普通文本的Git压缩效果套到同一加密制品上。

固定相同有效数据量时，速率比例为`T_git/T_sync`。只有在两路线共同成本为G、同步路线额外成本为E的简化假设下，才可写成`G/(G+E)`：E=G时50%，E=G/4时80%，E=G/9时90%。这是达到目标所需的成本条件，不是对本项目当前或最终速度的估计。传输占绝对主导且有效字节/吞吐接近时可能接近100%；小制品、高延迟、多批次时固定请求主导，比例可能低很多。

可信实验须固定冻结制品、目标分支初始状态、网络延迟/带宽、代理与认证状态，分别记录本地commit/pack成本、实际传输字节、远端确认，以及端到端事件构造/加密/持久化。至少区分“已生成制品的发布比较”和“同书库起点的完整首次同步比较”，不能以已经备好文件的一次Git push去代表具备额外业务处理的整条首次同步。

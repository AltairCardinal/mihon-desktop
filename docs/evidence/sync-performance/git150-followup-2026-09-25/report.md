# Git 150% 首次同步目标：3% 定向预研

## 本轮结论

**未达到完整首次同步≤Git耗时150%的目标，也没有证据保证下一项改动一定达标。** 本轮验证了一个安全但收益有限的分页优化，并把后续优先级从“小查询次数”收敛到“批次描述反复处理、字段归并的重复工作、可靠的分组上传”。

- 真实文件库契约的前驱记录SELECT从304次降至3次，逐条精确因果链、关闭重开和已有导入恢复契约通过。
- 同1600条完整Runtime为138.984秒；上一轮进度原型为137.661秒。没有观察到明确端到端收益，不能以查询减少宣布明显提速。
- 导入与投影累计仍32.833秒；保留这两段本地串行成本时，即使网络完全隐藏也超21.887秒目标，至少还需减少约33.3%，其他本地开销尚未计入。
- 本轮未实现真正的生成/上传重叠，未测到组合后的Runtime耗时。研究源码已撤回，归档补丁不是正式产品功能。

## 范围与测量口径

本轮接续[第一轮预研](../git150-research-2026-09-25/report.md)，研究本地处理成本和生成/上传重叠的可行性，不进行正式产品落地。基线提交为 `720a29afa1`；沿用同一1600本样本（424本真实收藏与1176本保形扩充），10300事件、41个协议批次。样本 SHA-256 为 `e2cbcb9dad186f22a15615b374588f8b694e37b2f660e515c160b10ceea17458`。私人输入、数据库、密文和完整采样文件只保留在忽略目录。

原生 Git 冻结制品对照为14.591507秒，完整首次同步目标为21.8872605秒；受控模型为每响应首部50ms、上下行各10Mbit/s。Git对照从已生成文件开始，完整应用指标从接受导入开始，后者包含额外本地业务成本。未访问或写入真实GitHub仓库，不能外推公网与Android结果。

## 分页原型与实测

每页只为当前对象集合读取一次 import heads，页内在每个事件持久更新头引用后同步更新临时map，下一页重新读取数据库。仍按50条/事务推进，事件顺序、批次边界、序号、冻结描述和取消/恢复语义不变；没有全历史预加载或跨事务缓存。SQL新增查询，不涉及schema迁移。

新增文件库测试在第一页后关闭重开，再完成剩余页，逐一验证后一个summary的parents等于前一个summary的完整引用。旧实现RED记录304次SELECT，新实现GREEN为3次；仅检查parent数量不足以证明缓存正确，因此审查中改为精确引用匹配。对1600条样本按effect数量推导旧查询14757次，新非空分页206次；这是源码与样本推导，大样本未另行拦截每条SQL。

| 指标 | 上一轮进度原型，无JFR | 本轮分页原型，带JFR |
| --- | ---: | ---: |
| 接受 → 导入生成完成 | 19.244s | 18.486s |
| 接受 → 首批确认 | 37.219s | 37.042s |
| 接受 → 全部确认 | 137.661s | 138.984s |
| baseline.process | 17.731s / 206页 | 16.858s / 206页 |
| projector.project | 15.448s / 231次 | 15.975s / 231次 |
| 发布及确认 | 89.298s / 41批 | 89.366s / 41批 |
| 上传事件 / HTTP / ref更新 | 10300 / 794 / 41 | 10300 / 794 / 41 |

两次都是单样本，没有随机配对，本轮还有JFR采样扰动。导入段减少不足1秒不能全部归给批读；总耗时反而增加约1.3秒，也不足以证明该改动导致退化。严谨结论是：**可证明减少重复查询，尚不能证明明显提速。** 加密重新生成，密文tree ID与上一轮不同；不能把新运行当作原冻结制品的逐字节配对重播。

JFR在接受计时开始前启动，完整耗时在synchronize返回时立即捕获，stop/dump/close在计时之外。最初口径错误的启动由协调器定向取消，不是有效性能样本；有效key为 `sync-import-head-1600-jfr-v2`。实际保留206个分页结束时间点。

## 运行时采样指向的热点

录制含354个Java ExecutionSample和4740个NativeMethodSample。Java样本按64层导出，按栈中实际调用路径归组：导入99、投影38、outbox81、其他136。默认CLI只展示5层会漏掉大部分业务调用者，因此不能用默认导出的浅栈宣称业务耗时很低。Native概览仍只用于叶方法观察。

| 路径 | Java执行栈样本 | 解释 |
| --- | ---: | --- |
| 导入：对象描述decode | 34 / 99 | 每事件重新解码整个open batch对象描述 |
| 导入：描述batchBytes | 28 / 99 | 反复将描述字符串转换为UTF-8计算体积 |
| 导入：描述encode | 11 / 99 | 每事件重新合并并编码对象描述 |
| 投影：reduction | 35 / 38 | 字段事件与父闭包加载、校验与归并 |
| 投影：SyncReducer.reduce | 23 / 38 | 包含于reduction，不能与上一行相加 |

这些是包含该方法的采样栈次数，**不是墙钟占比或可直接兑现的提速百分比**。样本有限，原生SQLite耗时可能落在native step/prepare中，不在上述Java比例内。全录制的native叶方法可见SQLite step359个样本、prepare_utf8 152个样本，也包含大量Gradle/MockWebServer socket等待；不能把它们混成产品CPU百分比，更不能据此断言磁盘fsync就是根因。

源码与采样共同支持的下一实施重点是：在事务范围内减少批次对象描述的重复decode/encode和UTF-8统计，保留准确字节上限、去重顺序、冻结描述及回滚一致性。应以真实append路径的批次字节一致性/边界测试和分段耗时验收，不能仅给缓存加命中计数。

投影另有明确重复读取：`getFieldEvents`已经取得event_json，调用方丢弃正文后再经`getEventsByKey`读取第一层。可评估复用首次结果与有界、不可变事件解码结果，但必须保留invalid事件过滤、完整父闭包、缺父/冲突和依赖失效语义。本轮没有实现或测量其收益，也没有绕过自身导入事件的投影。

## 有界重叠的源码约束

1. `SyncDatabaseExchange.exchange` 先清空初导队列，再读取远端、投影字段和上传。仅将网络改为异步，不能消除已有的这道顺序屏障。
2. `SyncOutboxStore.nextBatch` 总是领取最早未发布批次。不能为取得后续批次而提前标记 PUBLISHED；已持久保存的制品与本地确认仍须一一对应。
3. `GitHubSyncTransport.prepare` 要求当前快照的同 actor 前驱序号、索引路径与新批次连续。生成后续批次需显式区分“已验证远端前驱”和“本组冻结但未发布的前驱”，不能伪造已确认快照。
4. 上轮分组原型把最终文件按路径排序，UUID路径顺序不是事件生成顺序，而且预加载全部文件；原型自身没有生成/上传重叠能力。
5. 可以考虑在有界持久队列内将已冻结批次及其索引上传到未引用的 staging tree，最后统一创建commit、非强制更新ref、读回验证，再确认组成员。需要显式组归属、连接/世代隔离、失败重启对账及内存上限；远端对象创建成功不等于同步成功。

## 调度估算边界

任何调度估算都不是组合后的Runtime实测。上轮11次tree POST共19,299,863B：在既定模型中，仅上传等待加11次首部延迟就约15.996秒。77次请求的串行首部等待合计3.850秒，分组发布实测20.755秒；相对21.887秒目标的余量只有约1.132秒。不得把每个阶段的累计时间直接相加，或将不同运行相减后冒充完整首次同步成绩。

上一轮优化后导入 `process` 和投影累计约33.18秒。如果继续使用同一本地串行处理链，即使网络完全隐藏也仍超过目标。因此下一决策必须同时考虑本地工作量减少、依赖顺序和安全恢复，不能仅以“上流水线”作为达标结论。

## 本轮时间线对重叠方案的约束

本次第6页结束在1.519秒，届时首个256事件批次已有后续事件触发封口；这只是事件生成就绪，不代表加密制品已持久化。第206页在18.483秒结束，导入完成通知在18.486秒，首次投影开始于18.820秒。当前首批确认到37.042秒，确实存在网络尚未启动的本地前置等待。

- **先完成导入，再重叠投影与上传**：只能隐藏后续阶段的一部分；18.5秒导入前置成本已经用掉绝大部分21.9秒总预算。
- **导入过程中开始staging，最后统一发布**：有早期产物释放的机会，但当前本地导入+投影32.833秒仍是瓶颈。在保留测得工作量与串行本地链的条件下，理想隐藏网络也不够。
- **先削减本地重复工作，再做持久分组与有界重叠**：是仍有证据值得继续的路线。尚无真实组合成绩，不能报一个估算秒数作为承诺。

这里的条件下界只针对保留当前本地成本的方案，不是说重构后的所有方案都至少需要32.833秒；也没有把相互嵌套的outbox/observe累计重复求和。制品持久化、领取/确认、状态写入和并发资源争用尚未计入这条必要条件。

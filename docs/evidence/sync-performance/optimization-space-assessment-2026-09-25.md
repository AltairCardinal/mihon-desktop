# 同步性能：剩余优化空间评估

本报告与 [优化前后测试报告](baseline-2026-09-25.md) 配套。评估对象是 Android/Desktop 共用生产同步链路，既定协议、加密、冲突规则与恢复安全均为约束。报告区分本地已验证改动与尚无收益证据的候选，不将待测方案记作成果。

## 判断方法

按完整流程中的占比决定下一项优化，不按候选技术的数量决定完成程度。分别统计首次导入生成、首次确认、全部上传、首次下载归并、暖增量与恢复；不能把其中一个场景的改善外推到其他场景或真实设备。

证据强度分为三类：实测热点、源码中仍存在的重复工作、尚未验证的架构候选。缓存命中和 HTTP 请求减少不是 CPU、数据库或完整同步耗时下降的充分证据。不同层的嵌套计时不能相加，包含测试服务器和数据夹具的 JVM 堆不能冒充应用内存。

## 当前主要差距

理想的小增量同步主要付出新增数据的传输与本地处理成本。当前设计已经复用不可变对象、确认快照和持久发现记录，但新快照仍可能遍历、解密历史索引及构建完整安全证据；变更 actor 的平铺目录也仍随其历史增长。阶段 A 不保证所有工作均为 O(新增数据)。

首次加入没有暖缓存，不能依赖命中历史对象获得同样收益。真实设备的闪存、SQLite driver、后台调度与网络延迟也不同于本机 JVM，最终真机/真实私有仓库验收由用户执行。发布成功或 JVM 测试通过不能代替这部分证据。

## 候选项与启动条件

| 优化方向 | 证据与适用瓶颈 | 下一次最小实验 | 主要边界 |
| --- | --- | --- | --- |
| 已验证索引解析结果复用 | 变化快照仍有全历史解密/解析；主要是源码证据，不能预报整体倍率 | 固定新增量、递增历史，分开统计命中、解密、链验证和墙钟；先试有界内存缓存 | 键绑定空间、路径、密钥上下文及验证版本；清缓存不能丢 guard，重启成本单列 |
| 已验证树/历史前缀复用 | 分层取对象不自动消除路径展开与完整链检查 | 对同一组正常和篡改快照与原完整 guard 做差分；测目录变化量与历史量 | 必须发现旧对象消失、head 未变但历史被改、分叉与远端回退；缺少可信前缀时退回完整验证 |
| 多批次原子发布 | 固定发布/确认请求可能仍随协议批次数增长；尚无本轮组发布实测 | 同一批确定制品，比较单批发布与有界组的预计请求/等待占比，再决定是否实现 | 保留单批上限；组制品先持久化，结果未知时整体对账；验证旧客户端可读 |
| 下载与本地处理重叠 | 只有网络等待和本地处理都显著时才有收益 | 从串行基线估计可重叠时间，上界约为两者中较小者；达到预冻结收益再做有界原型 | 取消、先后顺序、字节额度和失败批次不能被后续预取越过 |
| 导入与上传交错 | 面向首个有效确认的等待体验，未必同幅改善总时长 | 先测全部导入生成占首批确认时间的比例 | 不能改变导入冻结范围、parents 或同时操作的因果语义 |
| 加密前压缩 | 仅在正文传输占比高且样本可压缩时适用 | 离线测代表性合成明文的压缩率、CPU、内存；不直接改变远端格式 | 格式版本、旧设备、已冻结旧制品、认证与受限解压均需独立设计 |
| GraphQL 聚合上传 | 现有候选 adapter 未接入默认生产；尚无启用收益证据 | REST 优化后再核对固定请求是否仍主导，先估算可节省比例 | 权限、冲突与未知结果恢复不能借切换 API 绕过；不计作已实现性能成果 |
| 历史检查点与目录分片 | 面向长期规模和首次加入成本，属于更大架构变化 | 固定活跃状态、增加历史，找到现有成本和容量边界 | 长期离线设备、删除记录、因果历史、检查点认证及格式迁移 |
| 原生 Git 传输 | 仅是传输层候选，不会消除数据库归并 | 使用相同冻结制品比较整体耗时、内存、磁盘及恢复；不直接替换 | Android 依赖体积、凭据、取消、对象损坏、pack 解压资源上限与跨端竞争 |

具体兼容和故障契约沿用 [设计阶段 B](../../2026-09-22-sync-performance-optimization-design.md#extensions)。这些候选没有自动进入当前必做范围；不选择某项不等于遗漏实现。

## 决策边界

不能因为某项局部改善很大，就宣称接近全局最优。假设某个可消除阶段占总耗时 p，即使该阶段变为零，整体理论加速上限也只有 1/(1-p)；这个公式仅帮助判断投入方向，p 必须来自相同场景的测量。

下一轮优先处理最终测量中仍占主导的本地处理或固定网络等待，再选择一个候选做配对验证。没有占比、明确安全边界和完整流程收益目标的候选，保持待评估，不以完成优化列表为目标。


## 本轮结果后的优先级

已测的 501 项批量裁决通过最多 50 项页事务，将中位耗时从 16.972 秒降至 0.910 秒，正常外层提交从 502 降至 11；继续减少同类提交的边际收益已降低，异常密集回退仍可能较慢。缓存 N=1000/9000 暖读、追加无全目录扫描，但每对象仍有 metadata 与访问标记写入；是否需要延迟刷新标记应以设备 I/O 占比决定。

首次同步 300 收藏的受控七样本，首批确认、全部上传、首次下载分别改善 58.6%、66.3%、83.3%；首次导入仍比旧版慢 6.5%，在预设 10% 容差内。冷读从五次 tree 请求减为一次已经解决本轮明显回退，但不代表大型历史冷同步成本得到同样改善。

下一轮先补“固定新增量、递增历史量”的本地 SQL 行数、解密/树展开与应用进程内存分解，再决定优先复用解析结果还是减少发布轮次。若历史解密占主导，增加 GraphQL 或原生 Git 不能直接解决；若多批固定往返占主导，优先比较有界多批次发布。下载流水线只有串行网络与本地处理均占显著时间时才值得增加恢复复杂度。

现有证据仍不足以宣称最优。完整 T82 历史本地成本、隔离应用堆峰值、大规模正式多样本配对，以及精确恢复切点覆盖属于本地验证缺项；真实设备与私有仓库测试另由用户执行，不能把这些本地缺项一并转交用户。当前不建议继续自动扩展实现，先取得这些观测与用户最终体验，再为单项候选冻结收益目标和预算。


最终提交H100暖增量中位2.526秒，相对旧版仍减少88.0%，但较前轮2.093秒回退20.7%，请求23→30。冷读验证后的目录证据复用值得优先做定向分解：当前递归结果不进入raw tree L2，安全边界明确，但后续首次分层物化可能重复请求。可比较有界、已验证的直接子项内存复用；不得将平铺JSON冒充Git原始tree对象。先证明额外7请求的具体来源，再决定实现，不把推断写成已证实因果。


交付边界：本轮因额度到约5.06%停止，新Windows/Android包未构建，macOS安全存储测试失败。下一笔投入应先完成上述发布与验证缺项，再考虑增加优化实现。现有本地测试收益不能替代安装包与真实设备结论。


## 追加2%预研更新

新的[预研报告](research-2026-09-25/report.md)已将“额外7个tree请求”从推断提升为路径/OID实证。有界共享已验证direct entries原型，配合manifest损坏时强制远端重读的保守准入门控，同轮H100三样本中位2432→2082ms，改善14.4%，HTTP30→23。原型未落地生产，安全集中集合曾出现1项失败并定向修复，仍缺完整专项验证，不称生产可发布。

建议优先落地这一有实测依据的局部优化；大量首次上传则优先研究有界多批次发布，它可能同时减少固定往返与重复历史验证，但本轮只有源码成本模型。后者和解密/不可变证据复用的收益不能与14.4%相加。此次用户明确授权预研，因此发布欠账仍保留，不将预研视为补完构建验收。

# 下载章节打开：双端性能基准

日期：2026-11-02。用户要求以已安装的官方 Mihon 的实际打开体验约束 Mihon Desktop 桌面版和本项目 Android 版。本页是该场景的共同验收定义，区分实测参考、工程预算与尚未取得的证据；不表示任何候选已达标，也不启动构建、完整测试或发布。

## 1. 官方原版参考及解释

参考为 PCE-W30、Android 12/API31 上已安装的 `app.mihon` 0.19.9/code22，APK SHA256 为 `7a7969564a604bf74608758b540730e53dfe63e11782a718d32380dc9febed58`。未 root、未重签或替换 APK。正常界面打开真实已下载章节，第 1/187 页；两次进程重启后的首次阅读器打开和一次同进程再次打开。

| 指标（毫秒） | 首次① | 再次 | 首次② |
| --- | ---: | ---: | ---: |
| 输入送达应用 → 系统开始启动 Reader Activity | 21.156 | 20.774 | 21.811 |
| 输入送达应用 → 开始执行 performCreate | 38.223 | 34.990 | 37.161 |
| 输入送达应用 → Reader 关联图层首个 TX 帧完成 | 79.670 | 73.461 | 82.282 |
| 系统 StartActivity 区间长度 | 432.640 | 421.139 | 428.455 |
| 视频近黑间隔的采样界限 | 16–51 | 18–54 | 0–33 |

观察：旧详情页会保留并逐渐淡出，然后出现短暂近黑画面和漫画。系统启动区间尚未结束时，Reader 图层已开始出帧。因而“内部过程数百毫秒”“窗口快速响应”“近黑间隔很短”可以同时成立。旧页面的延续与转场使一部分内部等待没有表现为无内容画面，这是本次数据支持的体验解释。

不能从这些观察推出：首漫画一定在点击后100ms内出现、原版完全没有加载成本、四百多毫秒全是黑屏，或 Desktop 的全部延迟都由某一个配对/初始化函数造成。线程睡眠也不能直接归因于文件读取、数据库或锁。最终原始时间戳的精简摘录见[参考数据](reader-startup-reference-2026-11-02.json)。

本轮系统追踪和视频使用不同时间原点，尚未建立精确映射；因此没有“输入→首漫画可见”的绝对测量。帧图层完成不证明漫画像素已出现。三个样本不足以给出可靠P95。全分辨率硬件编码和Perfetto同时运行，尚无采集开销对照，不能宣称得到无扰动性能值。

### 1.1 官方安装版与计时副本的差异裁定

| 记录 | 起点 → 终点 | 平板结果 | 可比性 |
| --- | --- | --- | --- |
| `app.mihon.benchmark` 内部四段合计 | `ReaderViewModel.init` → 目标页SSIV在基底图片ready后的`super.onDraw`完成 | 首次400.401–457.011ms，中位424.728ms | 不包括前面的Activity创建，不证明屏幕已呈现；不是官方版的窗口首帧指标 |
| 同一计时副本的请求总计 | 测试代码调用`startActivitySync`之前 → 上述图片绘制完成 | 首次454.072–505.815ms | 测试请求起点，不是用户触摸送达事件 |
| 未修改官方安装版 | 输入送达 → Reader关联图层首个TX帧完成 | 73.461–82.282ms | 该图层可以先显示背景；不能替代目标图片绘制或实际可见 |
| 未修改官方安装版 | 视频中的无内容/近黑区间 | 0–54ms的采样范围 | 只覆盖过渡中的一段，不是全部打开流程 |

**现有数据没有建立同一指标下两种APK的真实速度差，不能计算“425减80”等差值来声称探针增加了345ms，也不能把相近的系统启动span和内部图片绘制时间认定为同一事件。** 此前计时副本的四段数据只说明该副本及夹具路径的耗时分布，不能充当用户已安装官方版的精确四段基线。

已经确认的条件差异：

- 内容：副本把同一张2400×3500 JPEG复制为180页；官方版使用真实187页下载章节及真实卷首图。相同页数级别不等于相同读取、解码或排版成本。
- 数据/存储/设置：副本在自己的应用私有目录建下载库和数据库，使用测试source与固定单页LTR设置；官方版保留实际用户库、下载路径和阅读设置。没有证明两者存储adapter、元数据和运行缓存完全一致。
- 入口与前置工作：副本由Instrumentation准备及逐页哈希文件，打开首页，等待空闲及2秒后直接`startActivitySync`；官方版经首页、历史和漫画详情的真实点击进入。两者先前经过的UI/图片加载、任务栈和初始化路径不同，作用方向及大小尚未量化。
- 冷态：计时副本每轮由外层停止并重建进程，但计时前已完成Application/DI、数据库和首页准备；它测的是该进程首次进入阅读器，不是进程启动全过程。文件写入及哈希已经预热文件缓存。官方版也只计进入阅读器过程，不能用“冷态”一词忽略前置工作差异。
- 构建：副本来自上游v0.19.9源码提交`7a917968e3bf71c4a665e6655a550877d81ead1d`，诊断提交`4296862fc8c674831c3f9de2c00a21365d43c78d`；benchmark继承release且开启R8/资源压缩，但包名、签名、profileable、专用keep规则和探针不同。官方APK的相同版本号不证明相同构建产物或相同ART编译/profile状态。不同签名本身不是已证实的性能原因。
- 探针：启用时记录`System.nanoTime`并通过同步内存map去重；没有在每个时间点同步写文件，但仍有执行和调度影响。`DECODE_SUBMIT`是SSIV请求提交，非底层解码开始；`FIRST_DRAW`不是FrameCommit或物理屏幕呈现。后续快照等待100ms发生在FIRST_DRAW之后，不计入该四段合计，不能拿它解释400ms。

上述差异的存在可由代码和实验记录确认；每项的净耗时、哪项主导以及探针是否产生显著回归，均未被控制实验确认。不能事后给计时值减去一个猜测的“调试开销”。

## 2. 双端共同要求

覆盖已下载章节的单页和双页模式；其他阅读模式沿用相同体验原则，但必须单独提供证据。进程首次打开必须独立验收，不能由同进程暖态成绩代替。双页正确性、用户进度、错误反馈和既有稳定呈现契约继续成立。

| 指标 | 定义 | 当前要求及来源 |
| --- | --- | --- |
| 阅读器响应 | 应用接收到打开输入，到阅读器关联内容首次形成实际显示更新；不能使用按钮涟漪或无关窗口帧 | 初始工程预算≤100ms，依据官方约73–82ms参考留出有限余量；这不是首漫画预算 |
| 无内容间隔 | 旧页面已不可辨认而目标漫画尚未可见的累计时长，同时报告最长连续间隔；加载图标/纯背景算等待，漫画本身的黑边不算 | 初始工程预算≤60ms，依据官方本轮近黑区间上界54ms取整；是工程选择，不是用户逐字指定的数值或原版P95 |
| 首漫画可见 | 从同一个输入起点，到正确目标页在视口中首次实际可见；双页另记可见首目标页及应显示阅读单元完整可读时间 | 必须测量；绝对原版基线待补齐，在同条件下不应慢于官方参考。未补齐相应预算和证据前，不能宣布整体首开性能达标 |
| 呈现正确性 | 正确页码/方向/恢复位置，迟到配对不使已显示内容消失或跳动 | 功能硬门槛；空白、错页、临时显示无关图不能充当快速首图 |

100ms/60ms适用于登记的参考设备及内容场景，不承诺所有机器、压缩格式和任意尺寸图片的统一上限。新设备先登记条件和测量能力，不能静默放宽预算。不同刷新率使用毫秒判定，不用固定帧数替代；采样间隔不足以分辨预算时判为未确认。

其中73–82ms只是系统图层首帧代理值，尚未与该帧具体像素内容逐一对应。因此100ms是工程目标，不能据本轮代理值宣布“实际阅读器内容在100ms内可见”已通过。候选的响应指标也须补齐图层身份和画面内容对应。

只让前两项通过不足以验收：不得人为延长转场、冻结旧页面、只显示空阅读器或降低目标图像质量来掩盖首漫画等待。旧页面可以自然保留，但输入到首漫画的总时间必须同时公开。首次可见后的消失、闪黑也计入无内容累计，不能挑一段有利区间。

这些约束是优化验收目标，不指定实现。优先检查当前页基本读取/显示是否被额外工作阻塞；任何具体改动仍须沿用现有架构、先做真实行为失败测试，再运行受影响的 focused 验证。本页没有授权整章预热、牺牲配对正确性或改写已暂缓研究的结论。

## 3. 可比测量协议

1. 固定包/EXE版本与哈希、构建优化方式、设备/系统/GPU/刷新率、显示尺寸、存储方式、文件哈希清单、章节及起始页、阅读方向/模式/自动配对、窗口动画设置。使用真实文件字节；重复同一张合成图只能作独立压力夹具，不能代替真实阅读基准。
2. Android fork与官方版在同一平板、同一内容与可比设置下交替测量。Desktop使用同一图片内容和固定本机环境，单独报告平台数据；不能将模拟器结果或另一机器上的CPU时间直接解释为实现差异。官方不支持的双页行为注明功能差异，另测该增强功能的增量成本。
3. 冷态是重新启动应用后第一次打开阅读器，先使首页/详情页就绪；不得提前打开目标页、加载解码器或专门预热阅读器来使成绩通过。暖态是同进程再次打开同一章同一页。文件系统缓存条件另记，不能把进程冷态称为冷磁盘。首开流程之前由真实产品自然产生的缓存保留并记录。
4. 每个受影响平台/模式/存储场景，初次定向验收采用3次独立冷进程和3次同进程暖态，逐次保存结果、范围及中位数，不声称得到可靠P95。预算按各有效样本检查；超限不能用平均值抹平。外部干扰/采集失败保留原件与排除理由，不能事后删除慢样本。追加统计样本须有具体不确定性和成本说明，不自动触发完整矩阵。
5. 时间起点使用设备/进程内的实际输入送达；不能使用主机发ADB命令的时间。内部加载intent、Activity创建、数据ready、解码提交/开始/结束、绘制提交、合成呈现分别命名。原有Desktop `FIRST_PAGE_PRESENTED` 若只是绘制回调，须标明它不是物理屏幕呈现，并与实际可见帧校验。
6. 连续画面按原帧PTS分析；不要通过重采样制造帧。系统事件与视频需建立同一时钟映射或给出映射误差界限；未对齐时仅报告各自成立的时间差。近黑按视口内容定义并保留边界帧，排除页码/系统栏，注明残余图像、阈值、编码噪声与漏帧的不确定性。区间上界≤预算才判通过；下界超过预算判失败；跨越预算判未确认并提高测量精度。
7. 正式首开性能结论前，至少对疑似受采集影响的代表场景比较系统追踪单独运行与联合采集，记录线程/帧指标漂移；必要时采用外部拍摄校验显示。采集开销未校准必须标注；不能声称测到未插桩原版的任意函数或私有内存变化。
8. 分别给出响应、无内容、首漫画和正确性状态。原版整体首漫画基线缺失、Desktop显示映射缺失、双页完整可读边界缺失等都保留为未确认，不写PASS。失败时先用已有阶段事件缩小原因，再决定最小补测，不自动重跑全量或放宽门槛。

### 3.1 后续计时构建的有效性校验

在以内部探针评价产品前，先完成以下最小对照；它是下一次专项测量的前置设计，不是现在执行构建或扩大测试的授权。

| 组别 | 应用与入口 | 目的 |
| --- | --- | --- |
| A | 已安装官方APK保持不变，经正常UI打开；外部采集 | 保留真实体验基准 |
| B | 隔离release优化副本，探针存在但运行时关闭，经相同UI打开 | 判断副本整体是否能复现A；A/B差异仍包含包身份、数据、构建和ART状态，不能只归因编译器 |
| C | 与B同一个APK、同一配置和入口，仅运行时开启探针 | 量化探针对同一终点的影响；不能另编译一份导致R8等同时变化 |
| D（有必要时） | 与C相同APK/数据，改走旧Instrumentation入口 | 仅用于定位测试入口影响；D不能替代真实UI验收 |

B/C必须使用相同真实图片字节、页码、模式、存储访问方式和元数据条件，分别保存各自初始状态；探针开关不得暗中重建数据、预读页或初始化解码器。A的官方私有数据不通过未授权手段读取或修改；不能等价复制的状态应列为未控制变量。下载目录、数据库、ART编译配置、系统缓存和温度/后台负载分别记录，包名不同不等于可直接复制私有缓存。

先用A/B/C相同外部方法和相同端点比较，再解释C内部事件。B若不能复现A的行为和耗时分布，先缩小副本差异，不能继续把C的内部比例外推到A。B/C交错运行并分别统计冷/暖态；探针效应若超出采样误差与该场景自然波动，则降低探针开销后重验。单次相减不能作为固定开销校正。新插桩本身必须校验，不假设探针越多测量越准。

正式测量固定输入DOWN送达为公共起点，并另记UP/点击处理，避免不同组混用。候选同时记录内部加载开始、页列表ready、当前页open/read完成、decode submit/start/end、目标图绘制、帧提交/实际呈现；使用章节、目标页、请求代次关联异步任务，不能误取邻页预加载、旧请求或空背景首帧。页面索引不应硬编码为0。记录器采用有界内存缓冲，测量区间外导出，不在热点同步写文件、打印完整堆栈或跨设备请求。异步等待包含在wall time中，CPU time单列，不能将多线程重叠工作相加成端到端耗时。

视频侧下一步应保留编码器原始PTS及容器归零偏移，核验其时钟来源，并与Perfetto clock snapshots或其他可验证的同设备时钟映射对齐；再用可识别的共同事件验证偏差。只记录scrcpy主机启动时间或默认归零后的容器PTS不能完成对齐。映射尚不可用时，保留分别成立的时间差，不生成输入到首漫画的伪精确数字。FrameCommit/PixelCopy只能提供各自提交/采样边界，也不能自动证明屏幕已物理呈现。

最后交付必须包含：每组APK/源/内容身份、采集配置、原始事件与失败样本、同口径外部结果、B/C探针开销、时钟及图像判定误差、未控制变量。只有外部真实体验与内部探针相互核验后，才据内部四段定位瓶颈或决定优化；无证据的阶段保留“未测得”。

## 4. 与既有门禁和证据的关系

旧[Desktop adapter路线图](../roadmap/2026-08-27-desktop-reader-upstream-semantics-adapter-refactor-roadmap.md)的目录首图P95≤1s/单次≤2s、CBZ P95≤1.5s/单次≤3s，以及首帧I/O/decode结构门禁，仍是其既定场景的底线。本页新增用户体验目标；旧底线通过不代表达到原版秒开体验。新门槛与旧首图预算的终点不同，不能拿100ms窗口响应替换真实首图计时，也不改写旧报告的历史通过状态。

此前180张重复JPEG的诊断构建/模拟器以及Windows内部四阶段数据，继续作为各自环境的定位证据，不是本页官方真实章节的等价样本。连续翻页配对研究中的100ms是另一种增量分析预算，也不能当作本页已证明的首漫画值。

当前状态：已确定共同指标和初始工程预算；已有官方原版参考三份。尚未完成时钟对齐的原版首漫画基线、采集开销校准、同条件Android fork对照，以及Desktop原生显示端点对照。没有宣布两端达标或修复完成，不更新公共功能说明。

本机原件位于仓库忽略目录 `.test-tmp/upstream-original-trace-20261102/`（REPORT、原视频、trace、SQL、帧PTS、工具来源及哈希）；目录可能不随克隆分发，使用前验证存在。仓库仅保存精简系统事件/帧边界和来源文件SHA256，不提交含个人阅读内容的视频、截图或系统完整trace。原件不可得时，本页数值保留为历史参考，必须重新取得可复核原件才能做新的达标裁决。

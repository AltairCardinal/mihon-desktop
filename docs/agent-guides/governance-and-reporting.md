# 进度、代理交接与完成报告

本页是[根规则](../../AGENTS.md)按动作加载的项目约束。仅阅读本次动作适用章节；代码命令与普通路径以仓库根为基准，Markdown 链接按本页位置解析。

## 工程治理与进度状态

- 按能够独立交付和审查的功能批次执行，不按文件、测试类或机械行数切成微任务。
- `Estimated scope` 只是审查提示。超过 8 个文件或 400 行时记录内聚性与风险说明即可；不得为满足估算值压缩格式、复制实现或拆开不可独立编译/验收的上下文。
- 父 roadmap 只保存宏观阶段与唯一 `active-child-plan`；当前执行计划保存唯一 `active-task`；产品 child plan 从第一个未勾选项推导进度，不再声明 `active-task`。
- `parity-manifest.json` 是 capability 状态与证据的机器权威；tracker/report 只保存说明或生成视图，不得反向覆盖 manifest。
- checkbox 表示本批承诺的实现、按风险需要的审查、验证和提交均已完成；低风险可由实施者自查。它不表示整个 roadmap 已具备发布条件。发布就绪与剩余平台缺口另在当前 roadmap 或 evidence 中用说明记录，不建立新的状态服务。
- 一个功能批次原则上只产生一个包含测试、production 与必要 checkoff 的提交；审查修复最多增加一个提交。不得为 close、advance、record evidence 等纯状态推进单独提交。
- 审查按风险决定：低风险变更可由实施者自查；数据迁移、安全边界、发布身份、共享协议或公共运行机制等实质高风险部分，由未实施该部分的人独立审查。独立用户能力本身不触发独立审查。仅在架构假设失效、数据/格式迁移、安全边界或独立用户能力出现时重规划；不得仅因行数增长或格式化结果重规划。

## Git 交付细则

目的：保证用户验收并要求推送的功能确实进入日常使用的主干，避免“已推送分支/已创建 PR”被误报为“已交付”。默认路径及本机账号豁免以[根规则](../../AGENTS.md#主干开发与推送完成条件)为准，不从历史任务推导必须创建分支。

1. **先核对工作区与同步关系。** 读取当前分支、`git status`、实际 fetch/push URL 和本地/远端主干差异。用 `git rev-parse --show-toplevel --absolute-git-dir --git-common-dir` 核对实例；目录联接和别名（本机 `D:\Github` 指向 `D:\Shell\Github`）不是隔离。保护已有未提交内容，只暂存本任务文件或必要局部。并发写入、暂存区/HEAD 变动、构建目录争用或必须切换历史时使用独立 worktree；同一 worktree 的提交、整合和构建只由一个协调者执行。快进同步不得覆盖用户改动，不自动 stash、回滚或强推。
2. **直接使用已授权路径。** 向 `AltairCardinal/mihon-desktop` 推送时核对实际认证账号。`AltairCardinal` 的管理员豁免有效且用户已授权推送时，默认直接推送 `main`；GitHub 的 “Bypassed rule violations / Changes must be made through a pull request” 提示不应再被解释为必须转建 PR，也不单独构成失败。其他账号或服务器实际拒绝时，按真实权限处理并说明阻塞，不宣称推送成功。
3. **临时隔离必须回到主干。** 用户指定分支或确有具体冲突需要临时隔离时，记录当前任务提交与主干关系。获得“推送”授权后，应选择适合现有历史的整合方式把本次改动纳入 `main`，按真实影响运行必要的定向验证，再推送主干。若实际必须经 PR，创建后仍须跟进至合并及主干同步；只有用户明确要求停在 PR，或真实门禁无法满足并已说明阻塞时，才在该状态结束。
4. **核验整个推送范围。** 检查远端主干到目标提交之间的完整提交集合，每一项都须有授权；“只暂存我的文件”不能排除之前已经提交的其他任务。使用下述工具固定完整 SHA、核对实际远端和精确授权集合后推送，不能直接推送会随其他会话移动的 `main`/`HEAD` 引用。额外提交须先确认其授权或在隔离 worktree 有界整合；禁止自动把所有待推送提交视为已授权。
5. **核验远端与包的实际终点。** 工具推送后重新读取实际远端，确认目标是它的祖先；本地 `origin/main` 缓存或成功的分支推送输出不足以证明交付。若用户指定 squash 等改变提交身份的方式，核对合并提交与内容。主干体验包使用 [main-preview](desktop-build.md#主干候选包的源码边界)，并分别报告实现提交、实际远端主干、包的源码提交/清单和验证状态；不能把“本地实现完成”“远端已交付”“包已验收”合并成一个完成状态。提交/整合不增加全量测试或正式发布授权。

### 固定推送对象

在完成必要验证并获得推送授权后，读取实际远端提交、固定本次目标完整 SHA，列出 `remote..target` 中所有提交并逐项匹配授权，再用同一组参数执行：

```powershell
python scripts/git-delivery.py plan --repo . --expected-head <目标完整SHA> --expected-remote <实际远端完整SHA> --allow-commit <已授权完整SHA>
python scripts/git-delivery.py push --repo . --expected-head <同一目标SHA> --expected-remote <同一远端SHA> --allow-commit <同一已授权SHA>
```

多个提交重复传入 `--allow-commit`；集合必须精确一致，包括整合提交及尚未进入远端的祖先提交。工具核对当前分支、实际 URL 与远端引用，不接受不同 fetch/push URL 或多个推送目标，推送固定 SHA 的普通非强推 refspec，并在推送后检查实际远端包含关系。账号/授权核对仍由调用者负责，参数本身不创造授权。

目标或远端在检查前变化时重新检查，不自动扩大许可集合；检查后本地 main 即使被钩子推进，也不会夹带新提交。远端竞争由再次读取及普通 fast-forward 规则处理，不提供强推/CAS 保证；分叉将被拒绝，若目标已被别人正常纳入则按实际包含关系确认。远端抓取使用本次唯一临时引用且不改写共享 `FETCH_HEAD`，完成后只删除自己的引用。真实门禁阻塞时报告待交付状态。此工具是 Agent 必经入口，不安装全局 Git hooks，也不更改服务器保护。

定向回归：`python scripts/tests/git-delivery-test.py`（临时仓库和本地 bare 远端，不访问 GitHub）。

### 子代理完成回执与等待

- 子代理完成实现或审查时，先发送结构化回执，再结束任务。回执包含 `status`、`diff`、`tests`、`commit`、`process` 和 `next`；可用 `python scripts/agent-handoff.py` 验证。
- 长时间工具调用前报告命令、预计时间和可用的 PID/日志位置。
- 等待超时后先检查代理状态和已报告进程。进程仍运行时继续等待，不重复执行命令。
- 代理空闲但没有回执时，只发送一次“返回完成摘要”的 follow-up；连续两次确认空闲且仍无回执后才允许中断。
- 恢复代理时传递现有 diff、测试结果和进程状态，不重新探索或重新实现已经完成的工作。

## 完成报告格式

每个面向用户的 change 或迭代最终完成后必须按以下结构汇报，不得省略：

```markdown
## 【功能特性】
- [功能名称]：用户能看到/使用的变化，说明操作路径和边界
  - 示例：下载队列 → 顶部显示 Pause/Resume FAB 按钮 → 点击暂停/继续所有下载

## 【BUG 修复】
- [bug 描述]：修复前现象 → 修复后行为
  - 示例：下载队列管理按钮不可见 → 按钮已改为 FAB，始终可见

## 【验收清单】
面向用户的验收项使用以下格式：
- [ ] 操作路径 → 预期结果
```

规则：

- 每项都必须描述用户实际可见或可操作的变化，不写纯代码细节作为主要内容。
- 验收清单必须可执行；可在几分钟内手动完成的行为给出操作路径，其余行为给出自动化验证命令或运行时证据。若验收生成了构建产物，必须在对应验收项中以 Markdown 超链接给出可点击的绝对本地路径；不得只写纯文本路径。
- Windows Desktop 构建完成后，完成报告必须引用本轮构建日志 `Final unpacked EXE:` 输出的实际绝对路径并先确认文件存在，例如正式构建的 `[Mihon Desktop.exe](D:/Shell/Github/mihon/app-desktop/artifacts/windows/Mihon-Desktop-0.STAGE.FEATURE.BUILD.GIT_HASH-unpacked/Mihon%20Desktop.exe)`；体验包位于 `app-desktop/artifacts/preview/windows/`，链接须指向本轮真实预览产物。不得把 `app-desktop/tmp/`、Gradle `build/` 或其他临时目录中的 EXE 写成交付地址。
- 必须说明功能边界，例如“仅 QUEUED 状态可取消，DOWNLOADING 不可取消”。
- 内部重构无需虚构新增 UI；应报告它保护的既有用户行为、production wiring、自动化验证证据和当前功能边界。
- 拆分的 Task 之间只记录任务状态和验证证据；完整的用户可见完成报告在 change 或迭代最终完成时统一输出。

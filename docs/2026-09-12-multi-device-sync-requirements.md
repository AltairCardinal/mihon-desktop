# 多设备同步用户需求（待确认）

- 日期：2026-09-12
- 状态：需求草案，等待用户确认；尚未开展技术调研或产品实现。
- 本文交付范围：明确用户行为、同步边界、交互、异常处理与验收场景。
- 阅读约定：「已明确」来自用户原始要求；「建议」是本轮细化方案，需要用户确认后生效。文末列出关键决策。

## 1. 目标与使用场景

同一用户在多台设备上使用 Mihon，可以从任意一端同步自己的漫画收藏、阅读记录与作者关注。设备之间地位相同，不要求某一台设备始终在线，也不要求先在指定主设备上操作。

典型场景：用户在手机收藏漫画并读到某一位置，随后在电脑同步，即可看到该收藏并继续阅读；在电脑关注作者后，手机同步后也显示关注。设备可以离线操作，联网后补同步。

「任意端」建议解释为本项目支持并接入该同步功能的 Android 与 Desktop 客户端，首批验收包含 Android、Windows、macOS。是否包含其他平台需要确认；不据此承诺新增 Web/iOS 客户端或未适配客户端的兼容性。

同步完成的含义：在相关设备有联网和执行同步的机会后，无冲突且无需确认的操作自动生效；需要确认或存在冲突的操作明确展示。未处理的确认不能被包装成「所有设备已完全一致」。

## 2. 已明确的需求

| 编号 | 用户要求 | 必须保留的含义 |

| U-05 | 三种触发途径 | 后台定期、启动时异步自动、手动同步都必须提供。 |

## 3. 同步对象与边界

以下表格中的细分范围是建议，尤其「阅读」的具体含义需要按 Q2 确认。

| 对象 | 建议同步内容 | 生效后的用户反馈 | 边界 |
| --- | --- | --- | --- |
| 漫画收藏 | 收藏、明确取消收藏 | 书架新增或移除漫画；取消按确认规则执行 | 阅读漫画不等于收藏；取消收藏不附带删除下载或阅读记录。 |
| 章节阅读状态 | 实际阅读产生的已读状态、手动标为已读/未读 | 章节列表与未读数量更新 | 设备缺少章节记录不等于标为未读；明确标为未读允许撤销既有已读。 |
| 续读位置 | 漫画、章节、章内页码或可恢复的位置 | 漫画详情的继续阅读入口更新 | 位置与显示模式分开；章节无法对应时不猜测页码。 |
| 阅读历史 | 至少保留可在另一端识别最近阅读漫画的历史摘要 | 历史列表可找到未收藏但读过的漫画 | 是否同步完整逐次阅读日志不纳入首期默认范围。 |
| 作者关注 | 关注、明确取消关注 | 作者页的关注状态更新 | 取消关注保留作者归档及已有历史决定，不等于删除作者。 |
| 识别信息 | 足以确定漫画来源、漫画、章节和作者的必要信息 | 接收端能够显示对象并定位其来源 | 不仅凭同名自动合并不同漫画、章节或作者。 |

明确不同步：漫画阅读模式设置。建议同时将阅读方向、单双页、条漫、缩放、裁边及其他阅读器显示偏好统一视为设备本地设置，包括全局默认和单本覆盖。

建议首期不扩展到：漫画文件与封面缓存、下载队列、书架分类与排序、章节书签、完整应用设置、扩展安装包、源登录凭据、第三方追踪账号状态、作者发现结果及审核决定、作者扫描周期与过滤设置。必要的作者身份关联属于同步关注的支撑信息，不等于同步整套作者归档。

本地漫画文件不随同步传输；设备无法确认它与另一端文件对应时，保留待匹配信息，不自动关联同名文件。跨源版本与迁移后的章节对应方式留待调研，禁止以标题或章节号相似直接覆盖阅读记录。

## 4. 操作传播准则

### 4.1 缺失不代表取消

必须满足以下行为：

1. A 收藏漫画 M，B 从未有过 M。
2. 无论 A、B 谁先同步，B 的缺失都不会生成「取消收藏 M」。
3. A 的收藏操作被接收后，B 显示 M 已收藏。
4. 只有用户明确执行取消收藏，才能产生对应的取消操作。

作者关注遵循同一原则。未收藏、未关注、未加载到、尚未安装源、数据读取失败，都不能被解释为取消。

### 4.2 操作与同步本身的区别

- 本地用户操作应先可靠保存在设备上，网络失败不阻止正常收藏、阅读与关注。
- 接收并应用另一端的操作，不应被当成新的本地用户操作再次传播，造成来回反转。
- 同一操作重复到达、重试或重启恢复，只产生一次有效结果，不重复添加条目或反复要求确认。
- 同步期间发生的新操作不能丢失；若未进入本轮，应保持「待发送」，供下一轮发送。
- 清缓存、卸载扩展、同步请求失败、接入空设备和本地数据不完整，不得产生取消收藏、取消关注或清空已读操作。

### 4.3 首次启用与新设备加入（建议）

已有设备首次启用同步时，旧数据可能没有完整的操作历史。建议展示一次初始同步说明，将当前已有的收藏、关注和阅读记录作为「初始导入」加入同步；缺少的条目不导入为取消操作。

- 两台已有设备首次接入同一同步空间时，收藏与关注按保留双方已有项目的方式合并；不以其中一端覆盖另一端。
- 同步启用前已经取消的对象，不能从当前缺失状态推断其历史取消意图。
- 空设备加入时获取已有同步数据，不能上传「空书架」清空其他端。
- 初始导入与旧数据恢复必须可识别，不能通过反复初始化将早已被明确取消的旧收藏无限恢复。
- 若初始导入与已有明确取消操作冲突，应展示双方信息交用户决定；不静默恢复，也不静默删除。
- 恢复旧备份不等同于用户刚刚再次收藏、关注或取消。发现冲突时应说明恢复来源，让用户决定是否作为新操作传播。

### 4.4 先后顺序与多端冲突（建议）

有明确先后关系时遵循用户后续操作。例如用户已看到取消结果，随后重新收藏，后续收藏应生效；旧取消迟到不能再次把它移除。

如果 A、B 离线分别对同一对象作出相反操作，无法证明谁是在回应谁时，不能仅按哪台设备最后上传或设备时钟更晚决定结果。

- 相同方向的重复操作可合并展示。
- 不同漫画、不同作者以及可独立保留的不同章节阅读记录正常合并，不因无关冲突全部暂停。
- 同一对象的相反操作展示为冲突，列出设备、操作及相关时间；时间用于解释，不作为唯一裁决依据。
- 用户明确选择保留收藏/关注或采用取消；选择作为新的用户决定传播，目标端的破坏性变更仍遵守 Q1。
- 对象出现新操作后，旧确认条目须更新或失效；不能让用户确认的旧取消覆盖刚作出的重新收藏。

## 5. 取消收藏与取消关注的确认

### 5.1 推荐规则：接收端分别确认（待 Q1 确认）

操作发生端按现有交互完成本地取消。其他设备收到取消操作时，在「更新 → 同步 → 待确认」中展示，确认前保留该设备当前的收藏或关注状态。

每个受影响的接收端独立处理：

| 用户动作 | 本设备结果 | 对其他设备的影响 |
| --- | --- | --- |
| 确认取消 | 应用这条取消收藏/关注 | 不代替其他设备确认。 |
| 忽略本次取消 | 保留本设备当前状态，记住对这条操作的处理结果 | 不生成新的收藏/关注，不反向撤销其他端的取消。 |
| 暂不处理 | 保持原状态，条目继续待确认 | 其他对象的同步照常执行。 |

该规则允许用户明确保留设备间差异：只有各接收端都接受相关取消且冲突已解决时，相应状态才一致。「忽略本次取消」不是永久屏蔽该漫画或作者；后续新的取消仍需按规则处理。若用户希望重新让各端收藏/关注，应明确发起新的收藏/关注决定，不能从保留状态自动推断。

接收端本来就未收藏或未关注时，取消不造成实际状态变化，可记录为「无需变更」；也不能影响下载、阅读或作者归档。确认对象的粒度是一次用户操作，批量操作须列出受影响对象。

### 5.2 可替代规则：一次确认后跨端生效

若用户希望所有设备统一执行取消，可改为「取消操作等待一次全局确认；用户在任意端确认后，其他端自动应用」。此时需在需求确认中进一步选定：确认前发生端是否立即本地取消、拒绝时是否恢复，以及多个设备作出相反确认时如何处理。

两种规则不能混用或用含糊的「确认同步」按钮掩盖作用范围。本文其余场景暂按 5.1 的推荐规则描述，不表示用户已选定。

### 5.3 待确认条目内容（建议）

至少显示对象名称、漫画来源或作者识别信息、操作类型、来源设备、操作时间、本设备当前状态、接受后的影响，以及可用处理按钮。批量确认必须先展示数量和对象列表，再明确确认；不能将破坏性操作藏在普通「立即同步」按钮里。

待确认项和已处理结果应在退出、重启、断网与重复同步后保留。同一操作不得重复弹出；已有后续决定时，旧条目不得继续执行。确认时发现对象状态已变化，应刷新影响说明。

取消收藏不删除章节下载、阅读历史或阅读模式；取消关注不删除作者归档、匹配决定或历史发现信息。已有作者契约依据：[ADR-0003 第 2 节](architecture/adr/0003-author-archive-v2-contract.md)。

## 6. 阅读同步的具体体验（建议，待 Q2 确认）

- A 将某章读完，B 同步后该章显示已读；A、B 分别读完不同章节，双方记录都保留。
- A 停在某章某页，B 下次从详情进入继续阅读时可使用该位置。未收藏漫画同样可以同步阅读记录，不因此自动加入书架。
- B 正在阅读时收到 A 的新位置，不自动跳章、翻页或切换阅读模式；用非阻塞提示提供采用远端位置的入口，或在下一次进入阅读器时采用已确定的位置。
- 「读到过的进度」「当前续读位置」「显式标为未读」需要分别表达。重读前面的章节是有效行为，不能把永久取最大章节号或最大页码作为完整阅读同步规则。
- 两端离线阅读同一漫画产生无法排序的不同续读位置时，保留双方位置，在同步页让用户选择续读位置；已读章节记录仍可独立合并。
- 显式标为未读与另一端的已读操作冲突时，展示冲突，不能静默丢弃用户的回退意图。
- 接收端缺少源、章节列表或对应内容时，显示「源不可用」或「阅读位置待匹配」，保留同步记录；修复条件后可重试。
- 源的章节编排或页数变化时，不将无法验证的位置套到其他章节。能安全定位到章节但无法定位页码时，应向用户说明并提供从章首打开的选择。

## 7. 同步入口与页面

### 7.1 导航（已明确，细节为建议）

```text
底部导航：书架 / 更新 / ……
                  │
                  ├─ 更新页签：原有更新内容和操作
                  └─ 同步页签：同步状态、立即同步、待确认、冲突
```

「同步」与原「更新」页是同一级页签，不是新增底部导航项，也不是更新列表中的一条记录。保留原更新页内容和原有子分类；各端布局可以适配屏幕，但入口含义一致。

### 7.2 同步页最小内容（建议）

| 区域 | 展示及操作 |
| --- | --- |
| 配置入口 | 未配置时显示「配置同步」；已配置时可查看同步空间、当前设备名称并进入同步设置。 |
| 状态摘要 | 未配置、空闲、同步中、存在待确认、部分完成或失败；显示最近成功交换数据的时间。 |
| 手动按钮 | 「立即同步」执行发送与接收；运行中显示进度状态，重复点击不会启动互相冲突的任务。 |
| 待办计数 | 待发送、待确认、冲突、失败或待匹配数量；区分「已接收」与「已应用」。 |
| 待确认列表 | 展示取消收藏、取消关注及其确认/忽略入口。 |
| 冲突列表 | 展示相反操作或阅读位置分歧，允许查看对象并选择处理结果。 |
| 本轮结果 | 本轮发送、接收、应用与失败摘要；失败项提供重试入口。 |

待确认数量在同步页签上提示；后台同步不强制切换当前页面或弹出阻塞确认框。尚有待发送、待确认、失败或未上线设备时，不笼统声称「全部设备已同步」。

设置入口至少包含：同步服务连接、当前设备名称、启动自动同步开关、后台定期开关及周期。建议这些触发设置按设备独立保存，便于手机与电脑使用不同频率。

关闭本机自动同步或断开连接，不产生取消收藏/关注，不清空本地数据或远端数据。重新连接后应明确显示待处理操作；切换到另一个同步空间时，须提示本地数据是否会导入新的空间，不能无提示混合两份数据。

## 8. 三种触发方式

| 方式 | 用户体验要求 | 建议边界 |
| --- | --- | --- |
| 手动同步 | 任意端进入「更新 → 同步 → 立即同步」，得到明确结果 | 关闭自动同步后仍可手动同步；断网时保留待发送并提示原因。 |
| 启动自动同步 | 启动后异步进行，首页、收藏和阅读操作不等待网络 | 参考现有更新机制的非阻塞体验；自动同步失败不阻断应用使用。 |
| 后台定期同步 | 用户可设置周期，在平台允许的执行机会同步 | 应用进入后台后尽力运行；系统限制、休眠或进程退出可能延迟，见 Q4。 |

建议首次配置成功时，默认开启启动自动同步及每 1 小时后台同步，并允许修改或关闭。该默认值仅是待确认的产品建议，不代表技术调研已经证明调度精度或服务承载能力。

三种方式使用相同的数据范围、冲突和确认准则。自动任务不自动批准取消；手动触发也不隐含批准全部待确认。

多种触发同时发生时，应合并或排队，并给出当前状态；网络错误应有节制地重试，不持续打扰用户。应用恢复可运行后补处理未发送操作，不按错过的每个周期重复执行一批任务。

本轮不要求操作发生后立即推送到所有设备；正常传播时机是上述三种同步触发。若要求秒级同步，应在确认阶段补充。

## 9. Git 服务候选与失败处理

Git 服务是用户指定的调研候选，不在本需求文档中选择 GitHub、GitLab、自建服务或其他提供商，也不确定如何组织仓库和操作记录。

若采用 Git 服务，用户体验建议满足：

- 用户能在应用内配置和验证自己有权访问的同步空间；建议默认使用私有空间，明确告知收藏、阅读和关注数据将存储在哪里。
- 日常同步不要求用户安装 Git 命令行、理解提交/分支或手动解决 Git 文本冲突。
- 同步空间可由所有已授权设备访问；设备间同步不依赖另一台设备在线。
- 凭据不得作为阅读数据同步；不得出现在普通日志、同步内容或界面错误详情中。
- 无法连接、授权失效、权限不足、空间不存在或服务限制时，显示对应原因及可执行的重试/重新配置入口。
- 数据损坏或客户端无法理解的数据版本不能覆盖本地有效数据；暂停受影响部分，提示升级或恢复，不静默跳过后宣称成功。
- 中途退出或网络中断后重试，不重复应用操作、不丢失未发送操作；部分完成应明确哪些已完成、哪些仍待处理。

历史记录的保留、清理与旧设备重新加入，必须保证曾经明确取消的旧数据不会因清理或过期设备而意外复活。保存多久、如何提示设备过旧，以及 Git 历史中的隐私数据如何处理，由后续调研给出方案和限制。本轮不把同步当作完整备份或远端永久删除能力。

## 10. 验收场景草案

以下是未来实现的验收要求，当前均未执行，不表示功能已经完成。A、B、C 表示同一用户已配置同一同步空间的设备；取消相关场景暂按接收端分别确认。

| 编号 | 操作路径或测试场景 | 预期结果 |
| --- | --- | --- |
| AC-01 | A 收藏 M；没有 M 的 B 先同步；再让 A、B 完成交换 | A 不被取消收藏；B 最终出现 M，且仅一条。 |
| AC-02 | A、B 各自首次接入，分别已有不同收藏和关注 | 双方项目保留并合并；缺失不产生取消。 |
| AC-03 | A 阅读未收藏的 M 后同步；B 打开历史和继续阅读 | B 可找到 M 与可用位置，M 不因此自动收藏。 |
| AC-04 | A 收藏、阅读、关注后离线退出；重启联网同步 | 操作仍在，B 能接收；本地使用不因离线受阻。 |
| AC-05 | A 明确取消 M；B 同步 | B 显示待确认，确认前仍收藏；确认后取消，下载与阅读记录保留。 |
| AC-06 | A 取消作者关注；B 同步并确认 | B 停止关注，作者归档和已有决定保留。 |
| AC-07 | B 忽略 A 的一条取消，再重复同步并重启 | B 保留本地状态；该操作不反复要求确认，也不反向恢复 A。 |
| AC-08 | A、B 离线作出相反收藏/关注操作后同步 | 同步页显示可解释冲突；不以最后上传或机器时钟独断覆盖。 |
| AC-09 | 旧取消待确认时出现明确后续重新收藏，再尝试确认旧项 | 旧项更新或失效，不能覆盖新的决定。 |
| AC-10 | A、B 分别读完不同章节后同步 | 两端保留双方已读记录；无数据不会变成未读。 |
| AC-11 | 两端离线产生不同续读位置，或显式已读/未读冲突 | 保留用户意图并提供选择；不单纯取最大页码或章节号。 |
| AC-12 | B 正在阅读，收到 A 的阅读位置 | B 不自动跳章、翻页或改变阅读模式，有采用位置的入口。 |
| AC-13 | A、B 为同一本书设置不同阅读模式，多次双向同步 | 两端全局与单本阅读显示偏好均保持本地设置。 |
| AC-14 | 打开底部「更新」，切换「更新/同步」页签 | 原有更新功能可用；同步页提供按钮、状态与待确认列表。 |
| AC-15 | 关闭自动同步后手动触发；重新启用并启动应用 | 手动同步可用；启动自动同步异步执行，不阻塞首页操作。 |
| AC-16 | 平台运行条件满足时等待所设后台周期 | 实际后台任务执行，结果可在同步页查看；限制导致延迟时不虚报成功。 |
| AC-17 | 同时触发三种同步，期间继续收藏或阅读 | 无互相覆盖的并行任务，新操作被本轮接纳或保留到下一轮。 |
| AC-18 | 同步中断网/退出，随后恢复并重复同步 | 无重复条目、重复确认或操作丢失；界面准确显示部分完成与重试结果。 |
| AC-19 | B 未安装源、作者同名有歧义、章节无法对应 | 数据保留，展示不可用或待匹配；不误关联，也不生成取消。 |
| AC-20 | C 为新空设备加入，或旧设备恢复过时备份后重连 | 不清空其他设备，不将已取消旧数据静默复活；冲突可处理。 |
| AC-21 | 任意设备已发送操作后关闭，其他设备再同步 | 接收不依赖操作来源设备继续在线。 |
| AC-22 | 授权失效、同步数据损坏或版本不兼容 | 有明确恢复入口；本地有效数据与未发送操作受保护。 |

后续技术方案应为这些场景指定真实产品链路的验证方式：跨端共享行为使用契约测试，平台后台调度、导航及设置使用集成与运行验收。本文不先行规定测试框架或实现架构。

## 12. 确认后的技术调研边界

获得用户确认后才进入技术调研，目标是验证这些体验如何可靠实现，并说明无法满足的条件及可选降级，不直接开始产品实现。

届时调研：现有收藏、阅读、作者关注和更新调度链路的复用方式；跨端身份与初始导入；操作顺序、去重、确认和冲突；Git 服务适用性与替代方案；后台限制；失败恢复、历史保留及验证策略。

同步操作应接入已有用户动作与持久化链路，共享行为规则，复用原有更新页的导航与非阻塞反馈模式。具体哪些能力可直接复用、哪些需抽取共享能力、哪些受平台限制必须独立实现，须以调研证据回答；本文不将未经检查的实现假设写成结论。

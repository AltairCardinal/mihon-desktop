## 原问题与试点范围

HTML 交互 DEMO 能快速讨论信息架构、状态和操作路径，但不能准确代表 Android 与 Windows 的 Compose 尺寸、输入、弹层及平台行为。试点尝试让审阅者在独立窗口直接操作生产 Compose 同步面板，从而减少“在 HTML 中修改—再到两端实现—再次核对”的往返。

试点只覆盖**同步面板**，提供 `disconnected`、`setup`、`connected`、`settings`、`progress` 五个本地样本场景。共享 `SyncReviewPanel` 驱动场景状态；Android Debug Activity 和 Desktop 独立窗口调用各自正式使用的同步面板容器和共享内容。场景切换、设置及进度暂停/继续可操作，样本状态不持久化，不执行真实授权、同步、文件或外链动作。具体历史启动与测试方法见[试点指南](../NATIVE_UI_REVIEW.md)。

- 审阅窗口使用真实 Compose 面板内容及平台弹层，但 Android 独立 Activity 不能代表正式 `MainActivity` 的全部系统栏和外围配置；样本状态也不能证明生产数据、授权或后台链路。正式产品入口仍是最终验收依据。

## 探索结论与停止原因

该方法对**少数需要反复调样式的共享组件**有价值：审阅改动可以直接落在生产 Compose 组件，降低 HTML 与原生界面的视觉转译误差。它不是“把所有 UI 交互一次性还原到审阅窗口”的经济方案：每个页面仍要准备可重复的状态、连接平台容器、处理依赖与导航，并做双端测试及正式入口复核；平台独有页面也不能通过共享面板自动获得一致性。

此前给出的“全量接入约需 30%–60% 周额度”只是由单个试点与粗略页面文件数量推得的量级判断，**不是实测成本或与 HTML 的定量对比**。HTML 制作审阅场景的直接成本通常较低；两种方法的完整迭代总成本没有得到可比较的实测数据。用户认为全量推广缺乏实际意义，因此在一个试点后封存，不再据此开展全应用接入。

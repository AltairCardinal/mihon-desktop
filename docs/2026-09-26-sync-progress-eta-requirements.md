# 同步三阶段进度与实时剩余时间需求

日期：2026-09-26。状态：三阶段进度与 ETA 已实施；自动化及本机双平台运行验收已完成，真实账户与读屏人工验收待执行。证据见[验收记录](evidence/sync-progress-eta-2026-09-26.md)。

用户已确定：采用三个阶段；数量单位为数据条目，不按书本计数。本文保留需求定义，并在第 9 节标记已经完成的验收范围。

## 1. 范围与既有规则

沿用“书架 → 同步”面板、首次配置的合并页面和历史记录。Android 与 Desktop 共用组件、计数语义和估算器；不增加独立页面或同步引擎。

三阶段为 **准备数据 → 传输数据 → 确认结果**。首次上传的第二阶段显示“正在上传”；有下载时显示“正在下载”。下载后的解密、校验、数据库合并包含在确认阶段，不能收到网络正文就宣告同步完成。

保留[原进度与恢复设计](2026-09-19-sync-progress-resume-design.md)及[恢复修复设计](2026-09-21-sync-repair-design.md)的暂停、持久化、授权、运行所有权和安全边界。本文补充并细化三阶段显示、条目/字节单位及 ETA；不修改批次上限、加密协议、发布或后台执行策略。不以实现本文为由默认启用分组发布研究补丁。

当前基础可复用：`SyncProgressReporter`、`SyncRunStore`、`SyncPanelController`、共享 `SyncProgressCard`、真实传输和数据库事务。现有导入/上传常上报 `total=0`；界面有确定与不定进度条，但没有 ETA。实施时须补真实观测，不只改 UI 文案或给模拟状态填数字。

## 2. 信息层级与界面

面板从上到下：

1. 三阶段指示：准备数据／传输数据／确认结果；标出当前阶段，区分完成、执行中、等待、失败。
2. 当前动作，例如“正在整理数据”“正在上传”“正在核对结果”。
3. 当前阶段的条目计数与进度条；明确当前阶段，不能冒充全流程百分比。
4. “已用 00:18 · 预计还需约 25 秒”；无法估算全部剩余时使用第 5 节降级文案。
5. 必要的辅助信息：传输百分比、已确认数量、等待原因；技术性吞吐和字节量可放展开详情，不占用主信息区。
6. 最近条目日志及现有暂停、继续、重试等适用操作。

示例仅表示布局，不是速度承诺：

```text
准备数据 ✓    传输数据 ●    确认结果 ○
正在上传
已传输 6,144 / 10,300 条
[██████████░░░░░░░░]  传输进度 62%
已用 00:38 · 当前阶段预计还需约 12 秒
全部剩余时间正在估算
已确认 0 / 10,300 条
[暂停同步]
```

条目大小不等，因此上例的条目比例可以不同于字节百分比。必须写明“传输进度”，不能把字节百分比标成条目完成比例。禁止显示按墙钟匀速前进的假进度。

不得用准备占 20%、传输占 70% 等固定权重制造全流程百分比。默认只提供当前阶段进度；三阶段指示负责表达整体位置。

## 3. 计数定义与任务范围

### 3.1 一条数据是什么

- 一条独立同步变更事件算一条；一个事件内多个字段或 effect 不重复计数。收藏、关注、阅读状态统一用“条”，不混为书本数。
- 本次样本是 1,600 条书架事件加 8,700 条阅读状态事件，共 10,300 条。41 个协议批次、HTTP 请求、tree/index 文件均不算数据条目。
- 同一个事件在重试、对账、重新打开面板和进程恢复时只算一次；按现有事件身份及 space/generation 隔离，不按请求次数累加。
- 上传和下载方向分开计数。总摘要按逻辑事件去重；同一事件的下载去重处理不能又被算作新增成功条目。
- 成功、跳过、失败、待处理必须可核对；“已处理”可含跳过/终止失败，“同步成功”只能指完成必要确认的条目。待重试不算终止失败。

### 3.2 总量与增量

- 分母来自本次工作清单，不能写死 1,600 或读取当前书架数量代替；本次范围不包含已成功结束的历史事件。
- 能从冻结导入任务、待上传队列或已验证远端索引确定事件数时，提前提供确定总量。不能为统计重跑一遍完整事件构造、历史解密或全表扫描。
- 扫描尚未完成、工作项与事件并非一一对应时，总量为未知，显示“正在统计数据”“已准备 X 条”及不定进度条。不得把未知写成“0/0”，也不能把尚未产生的事件猜作精确总量。
- 已知总量后，同一工作范围内分母固定。新增用户操作进入后续工作范围；如果现有引擎必须在同次运行捕获远端追加，则明确显示“发现新增数据，继续同步”，开新轮次并重新估算，不静默改分母或让同一进度条倒退。
- 零条待处理显示“没有需要同步的数据”，正常收口；没有网络数据时跳过传输，不为了动画延长任务。

## 4. 各阶段的完成边界

| 阶段 | 主计数 | 进度条依据 | 进入下一阶段/完成的条件 |
| --- | --- | --- | --- |
| 准备数据 | 已准备 X / N 条 | 已完成本地准备的唯一条目 / 已知准备总量 | 本阶段所需导入、投影、分批及制品准备完成；不得导入结束但投影仍在运行就显示准备完成 |
| 传输数据 | 已传输 X / N 条 | 当前范围实际传输的有效正文工作量 / 已知总正文工作量 | 当前范围全部必要正文传输完成；尚未远端发布/持久确认 |
| 确认结果 | 已确认 X / N 条 | 有真实可拆分确认单元时按已确认条目；否则不定进度 | 上传完成真实远端验证及本地确认事务；下载完成验证、持久接收和必要合并，待人工决策单独说明 |

准备阶段的子动作可显示“整理变更”“生成上传数据”。如果无法逐条观测昂贵的子步骤，必须显示实际子动作及活动指示，不能提前把整个准备阶段报成 100%。已完成的导入条目可作为辅助计数，不能冒充所有本地准备已完成。

传输阶段要求：

- 主进度来源是生产 HTTP 正文读写回调；大请求进行中也能更新，不能只在请求结束时跳一次。
- 上传正文写出仅代表已发送，不代表服务器持久保存。一个条目的必要 batch 正文已完整发送/接收后，条目计数才增加；同一 batch 承载多个事件时可阶梯式增长。不得按发送字节比例虚构半批已完整传输条目。
- 索引、头等必要传输计入字节工作量，但不新增条目。允许已传输 N/N 条时继续显示“正在传输校验信息”，条目 N/N 不等于全流程完成。
- 正文长度未知时可显示已传输条目/字节与速率，不显示猜测百分比。请求头、TLS 流量不混入正文分母。
- 重试字节计入实际网络负载和耗时，但不重复增加有效完成量。展示保留的有效进度与“正在重试”；每次尝试的字节计数单独隔离，不能重发后超过 100%。

确认阶段要求：

- 对本次单组原子发布，允许“已确认 0/N”在成功时直接到“N/N”。期间以“正在确认”与不定进度条表达真实工作，不伪造逐条确认。
- 分组或逐批确认时，只增加已完成确认事务的成员；远端已写但结果未知时保持“正在核对”，不得显示成功或重新计数。
- 上传正文刚发送完可以显示传输阶段 100%，但不得显示“同步完成”。最终成功图标和完成文案必须跟随真实运行结果。

既有双向交换可能下载、合并、再上传，也可能多轮追赶。三个名称是展示分类，不强行重排引擎。界面明确“下载数据／上传变更”及“继续同步新增数据”；同一范围的已确认累计保留，局部阶段切换允许进度条重置，但必须同步更换阶段/方向标题。首轮完成不代表整次运行完成。

## 5. 实时预计剩余时间（ETA）

### 5.1 显示规则

- 默认显示“预计还需约 …”，指当前已知工作范围直至必要确认完成；不是单纯文件发送结束。
- 所有剩余阶段都有可信估算时，才能显示整体 ETA。尚无后续阶段数据时显示“全部剩余时间正在估算”，可同时提供明确标为“当前阶段预计还需约 …”的局部 ETA。
- 首次运行、总量未知、速度样本不足时显示“正在估算”，不显示 0 秒、无穷大或凭空固定的剩余时间。无需收集用户数据或依赖联网服务。
- 有效估算每秒更新一次；速度变化允许剩余时间增加，不承诺一直倒数。不能只是初始 ETA 减去墙钟时间。
- 值小于 1 分钟按秒显示，1 分钟以上按合理粒度约数显示；避免毫秒或小数精度。未完成时不得显示“还需 0 秒”，改为“正在收尾”或“不到 1 秒”。

### 5.2 数据与算法约束

- 使用单调时钟计算本次有效工作耗时，分别采集准备条目、上传/下载字节、确认单元的耗时，不能用“每本书耗时”统一外推。
- 阶段内用近期实际进展估速，初始默认窗口为最近 10 秒有效样本，至少累计 3 秒且有 3 个有效增量样本后给出本轮速率；采用时间加权或等价平滑，避免单个小请求造成大幅跳动。参数集中定义并由确定性测试覆盖。
- 局部 ETA 的基本依据为剩余工作量 / 平滑速率；整体 ETA 为未完成阶段估算之和。用已经耗掉的有效工作时间校准速率，但不得把过去耗时再次加进剩余时间；计入尚需重试及正在执行步骤的剩余成本，不能遗漏本地合并/确认成本。
- 确认阶段若是单次原子操作，尚无可分解进展，也无足够可比历史样本，则只显示“正在确认，剩余时间暂无法估算”。禁止把 HTTP 字节速度继续套用到确认。
- 可复用同设备、同方向、同阶段且规模可比的本地成功记录作为冷启动参考，但必须标为估算、被当前实测及时修正。若现有历史只有总耗时而无分段证据，不得直接冒充可用预测模型；历史估算不是首版必需条件。
- 持续 10 秒没有实际进展时，停止展示旧的乐观 ETA，显示“暂无法估算”；状态原因已知则显示具体等待原因。无进展不等于故障，不自行改成失败。
- 网络切换、传输方向切换、任务范围变化或恢复后重建短期速率窗口。重复请求的字节不得当作新增有效条目来提高估算速度。

### 5.3 耗时口径

“已用时间”展示本次运行自开始以来的实际历时，包含暂停和等待；详情可区分工作与等待耗时。ETA 的工作速率排除用户暂停、系统未调度及离线等待，不把待机时间当作本地处理变慢。重试执行和实际网络等待属于真实工作成本。

暂停、离线或系统等待时，保留已用与完成量，ETA 区域改为对应状态，不继续倒数；“预计多久恢复网络/系统调度”不作预测。重试倒计时与同步 ETA 必须独立标注。

## 6. 暂停、恢复与终态

| 情况 | 进度和剩余时间 | 交互 |
| --- | --- | --- |
| 用户暂停 | 已处理/确认量保留；显示“同步已暂停”，ETA 停止 | 现有“继续同步”，不自动撤销暂停 |
| 正在响应暂停请求 | 显示“正在暂停，正在保存进度”；不得提前声称已停 | 沿用现有安全停止边界 |
| 网络/系统等待 | 保留进度、显示具体原因，ETA 暂不可用 | 沿用既有恢复策略，不额外承诺后台持续运行 |
| 自动重试 | 展示重试倒计时和已保留进度；重新建立速率样本 | 不重置运行完成计数或重试预算 |
| 进程重启 | 先显示“正在恢复并核对进度”；读取安全记录再恢复 | 已确认数量不得回退；进程内未确认字节可丢失，须明确进入恢复状态后再重建，不冒充已持久完成 |
| 取消、授权或数据错误 | 展示真实结果和剩余待处理量，无 ETA | 沿用取消/重新连接/处理问题入口 |
| 部分成功/待人工决策 | 区分已确认、跳过、失败、待处理；不显示全部同步成功 | 保留现有待处理入口 |
| 成功 | 显示已确认条目数与总历时，隐藏 ETA | 可见会话展示结果；收起后不补播旧通知 |

关闭面板不停止同步；重新打开订阅当前任务，不重新开始计时。切换账户、仓库、空间或 generation 后，旧任务计数、速率和 ETA 不得污染新任务。历史记录显示实际结果和耗时，不显示仍在变化的预测。

## 7. 实现约束与性能

- 准备、传输、确认的统计在真实操作发生处产生。UI 只订阅，不轮询全库、不从日志文案解析进度、不靠计时器累加完成数。
- 复用已有共享 reporter/store/controller 和 HTTP 客户端；只增补区分条目、字节、阶段/方向、工作范围、估算有效性所需的信息。不得给 Desktop 或 Android 各写独立估算器。
- 高频字节与速度样本保存在内存，最多每 250ms 推送一次 UI 进度，ETA 每秒刷新。成功、失败、暂停、阶段切换不受节流延迟；后台面板不可见时无需每秒重绘。
- 安全记录仍按原有事务及时持久化。新增展示状态最多每秒合并一次写入，优先复用已有事务；字节回调、定时刷新不得各自启动数据库事务。仅由计时器造成的 ETA 变化不落库。
- 不能为了显示计数提前确认、放松持久化、扩大事务或重新生成已冻结密文。统计错误不得改变同步结果。
- 聚合计数应为 O(本轮增量)，去重状态有界，不能为每次 UI 刷新遍历全历史。新增数据表/迁移如确有必要，实施计划须说明来源、版本兼容及恢复，本文不预先指定新 schema。
- 计时与计数实现必须接入 production wiring。若删除 HTTP 进度回调或真实事务通知后测试仍通过，该测试不能作为本需求完成证据。

## 8. 双端与可访问性

Android/桌面沿用当前面板宽度及导航。小屏和放大字体下不能截掉数量或状态；布局允许换行。时间、数字、单复数与错误文案使用现有国际化机制。

阶段不可仅靠颜色区分；进度条提供明确的阶段和单位语义。读屏仅在阶段/状态切换及有意义的进度节点播报，不每 250ms 或每秒打断用户。纯进度变化不抢焦点、不滚动日志、不抢占阅读页面。

- [x] 性能 → 验证高频回调不会逐事件/字节落库、不会重复扫描历史。用同样本做显示遥测启用/关闭对照，累计准备与传输主路径不应因进度功能增加超过 5%；超过时先分段归因，不能删减安全确认来达标。单次波动不能证明通过或失败，必要时按预先声明的验证预算复测。

## 10. 实施交付边界

实施已按共享进度事实与计时模型、真实操作通知、共享 UI 和双端集成验证完成，并按项目 TDD 要求执行。以一个可独立验收的用户能力收口，不按单文件拆成可见但无真实数据的半成品。

交付包含真实链路的确定性功能测试、UI 集成证据、性能开销报告和双平台本机构建运行证据。真实 GitHub 账户同步与读屏人工验收仍由用户在适当环境执行；本轮没有写入真实仓库。

## 11. 实现维护边界

本功能沿用共享 `SyncRuntime`、`SyncDatabaseExchange`、`SyncPanelController` 和 `SyncPanelContent`。准备阶段的首次导入已提交条目只是辅助信息；上传轮次由 outbox 在同一事务内封存并取得批次身份和分母，封存后新增的本地操作进入下一轮。制品生成开始即进入准备阶段，只有安全保存制品后才累计已准备条目。传输回调来自生产 HTTP 正文；请求有可信 `Content-Length` 时可估算“当前正文”剩余时间，不能把它当成整轮 ETA。

数据库迁移 37 保存每次运行的 `confirmed_items` 和按方向、批次去重的确认回执。下载回执在接收前记为 `PENDING`，只有收件、索引及必要字段投影均通过检查才改为 `CONFIRMED`；上传仅在真实远端 ACK 后确认。已接收数量仍可用于传输阶段，但不得用于确认阶段、最终成功判定或持久确认补计。未满足依赖或来源的投影即使没有人工待决项，也以 `projection_pending` 保留部分完成结果，提示稍后重试。重启先读持久确认数，丢弃未确认的进程内字节速率。

若同一运行已有 `PENDING` 下载回执，手动或周期重试要沿用该运行身份核对未完成投影；启动恢复不自动重试该部分结果。只有待处理人工决定、但没有下载回执的旧运行仍走原有运行边界。再次重试时不能新开运行将未投影条目计作成功，也不能把相同回执重复确认为新条目。

`progressTelemetryEnabled` 仅用于同样本性能对照时关闭内存时间线与 HTTP 展示观测；安全回执、投影检查和运行结果在两种配置下保持一致。界面最多每 250 毫秒接收一次进度推送，仅在可见时每秒刷新耗时与 ETA；这些计时变化不写数据库。此实现不改变加密格式、批次上限、发布策略或真实 GitHub 仓库数据。

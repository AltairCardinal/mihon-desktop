### 1.1 已观察、已证实与尚未证实

| 问题 | 观察与证据 | 当前结论 |
|---|---|---|
| 不能重新同步 | UI层级中“立即同步”的父按钮 `enabled=false`；共享 `SyncMainOperation` 的终态分支只在 `connection.enabled==true` 时启用 | 已证实入口缺陷：历史终态存在时，原连接入口被隐藏，卡片又没有提供连接恢复操作 |
| 时间过长 | 多次读取、详情/设置返回及关闭重开后，历时始终291:54；终态公式为 `updatedAt-createdAt` | 未证实继续计时；该数是历史总历时，按现有口径包含暂停/等待。为什么历史跨度接近5小时仍未知 |
| 可能仍在后台尝试 | 系统采样显示该应用无运行服务、0个运行中的后台作业 | 当前采样不支持持续运行猜测；这不能证明此前从未重试，也不能排除未观测的进程内活动 |

| 连接为何停用 | `SyncRuntime.connection()` 的启用值为 `exchange_enabled && !unsupported` | 尚未读到私有原始字段；可能是持久停用或格式不兼容。凭据读取异常本身不等于这两个条件，不能归因为令牌过期 |

## 2. 已证实问题的修复规格

### 2.1 运行状态与连接状态共同决定主操作

目前判断偏重运行终态；修复后必须同时判断当前连接和可执行动作。复用现有 `BeginSetup/Authorize/Synchronize` 及不兼容错误页面；不直接把 `exchange_enabled` 改为1，也不把按钮无条件启用。

| 当前状态 | 主操作与说明 | 点击结果 |
|---|---|---|
| 连接启用、无活动运行、历史CANCELLED/SUCCEEDED | 立即同步；明确这是上次同步结果 | `Synchronize` 创建/取得合法新运行，旧记录保留；不得要求清除终态才能执行 |
| 无连接，或连接保留但已停用；不存在活动执行 | 连接同步空间；说明本设备尚未连接或已断开 | `BeginSetup` 进入现有连接流程，保留已有空间/本地数据；不能伪装成已开始同步 |
| 已明确格式不兼容 | 查看连接问题；可阅读不兼容原因 | 使用现有错误/详情路径；不跳过兼容检查，不循环重新授权，不提供无效的立即同步 |
| 连接启用但运行BLOCKED，已有授权问题 | 重新连接GitHub | `Authorize`；保留现有浏览器认领、失败与取消反馈 |
| 连接启用，FAILED/PARTIAL | 重试同步 | `RetrySync`；原有失败日志、待决定与核对入口保留 |
| 活动/暂停/等待/恢复中的运行 | 沿用当前合法暂停、继续、等待操作 | 不因历史记录或新连接文案覆盖运行所有权；发现连接状态与活动运行矛盾时先刷新并展示原因，不盲目再起一个运行 |

状态无法判定时显示“正在检查连接”，暂时禁用但有说明；检查失败应提供明确重试检查/查看原因路径，不能无限停在无原因的禁用按钮。连接检查仅读取本地状态；网络授权验证仍由用户进入原授权流程触发。

修复位置以 `SyncPanelContent.kt` 的 `MainPage/SyncMainOperation` 为主，展示投影继续复用 `SyncProgressDisplaySession`。controller的 `Synchronize` 已在连接未启用时进入setup，UI应和该契约一致；具体入口统一在一处决定，不在Android/Desktop各写一份判断。

### 2.2 清楚区分当前任务与上次结果

- 无正在执行的运行、仅展示最近终态时，用“上次同步已取消/完成/未完成”等明确语境；不要让用户误以为取消状态仍控制当前后台任务。
- 七槽摘要继续保留，终态的动作槽不再重复同一句取消标题，可说明“已确认结果会保留”；主操作根据当前连接决定。终态时间标签为“上次历时”，整体剩余为“—”；暂停/等待的实际当前运行仍按原“已用”口径显示。
- 原终态、确认量与日志不删除；通过新运行替换主卡的观察对象，而不是清零数据库。历史记录仍可查看。断开连接不会借本修复恢复上传，也不抹掉已确认记录。
- 当前没有可用的持久实际工作时长，不能把291:54改成估计的网络时间，不能扣除没有记录的等待区间。详情可显示持久开始/最后更新时间及“历时包含等待”，不得把updatedAt冒充新增的精确结束字段。
- 焦点、窄屏/大字、唯一主操作与单轨道继续遵守已审核契约；终态无加载语义，主题与新进度不推动按钮反复增减。

### 2.3 冻结回归矩阵

测试先红→最小实现→绿→重构。先扩展现有 `SyncPanelContentTest` 的断开连接用例：该用例原本只覆盖没有run的情况，必须加入真实反馈组合。新测试不能只检查文案存在，应点击真实Compose按钮并接入controller验证路由/运行变化。

| ID | 行为场景 | 必须断言 |
|---|---|---|
| R01 | `connection.enabled=false` + CANCELLED + confirmed=1536 | 出现可执行连接入口；点击进入现有setup；不调Synchronize、不修改启用值；历史仍可读 |
| R02 | enabled=true + 同样CANCELLED | 点击立即同步能进入合法新运行；旧终态不会阻塞，新runId与旧记录分离；确认数不跨run串用 |
| R03 | disabled + SUCCEEDED/FAILED/PARTIAL，以及connection=null | 每种组合有正确连接路径；不会留下仅灰色“立即同步”的死路 |
| R04 | unsupportedFormat=true + 历史终态 | 原不兼容原因全文可达，不能绕过guard或被历史摘要遮住 |
| R05 | PAUSED_USER/WAITING_RETRY/RECOVERING，含连接变化竞态 | 保持原暂停/恢复和nextRetryAt规则；不启动并行运行或绕过所有权 |
| R06 | 终态显示，连续推进时钟/刷新/关闭重开 | 历时冻结、整体剩余为—、无活动轨道；显示上次结果语境，重开不补播临时成功消息 |
| R07 | 新运行、空间/generation变化、旧异步结果晚到 | 旧终态/连接检查结果不能覆盖新身份；主操作与真实最新连接保持一致 |
| R08 | 真机Release、320dp/200%字体、Desktop窄窗、中英双主题 | 主操作/错误原因可达；详情/关闭/返回焦点正确，摘要稳定且终态不会表现为仍在处理 |

共享Compose与真实 `SyncPanelController` 集成至少覆盖R01/R02/R04/R07；共享文件数据库存储契约覆盖取消后新运行及记录保留；Android/Desktop wrapper验证正确使用共享操作和setup入口。断开操作、首次合并与批处理的已有危险确认和独立暂停语义不能被修改。

## 3. 进一步 DEBUG：先补事实，再决定是否修运行链路

### 3.1 问题与判别条件

| DEBUG问题 | 必须取得的事实 | 可作结论的边界 |
|---|---|---|
| 当前未启用来自哪里 | 原始exchange_enabled、unsupportedFormat、连接解码结果、panel投影值 | flag为0可确认持久停用；unsupported为true可确认格式问题。没有历史来源记录时，仍不能断言是谁/哪次操作停用 |
| cancelled是历史还是仍被当作活动 | activeRun与latestRun查询结果、coordinator.running、owner/attempt、选择来源 | CANCELLED不在活动查询集合；若仅latest命中就是历史。出现矛盾时查事务/缓存/竞态，不从标题推断任务线程 |
| 291:54如何产生 | createdAt、updatedAt、lastProgressAt、state/phase/stopReason及已有日志时间范围 | 对照公式确认持久跨度；没有分段/重试轨迹只能记“历史原因不足”，不能把全部历时算网络工作 |
| 终态时间是否继续被改写 | 同run连续快照，持久updatedAt、confirmedItems、后台写入事件来源 | updatedAt改变需找到实际写入调用；UI nowMillis变化而updatedAt不变只是刷新，不是续跑 |
| 前后台是否刷新正确 | 生命周期事件、Open/Close、刷新开始/结束、选择run来源及连接revision | 观察刷新实际执行及新值消费；只有证实遗漏/旧结果覆盖才追加生命周期修复 |
| 是否真的继续重试 | coordinator/worker状态、持久nextRetryAt/owner、attempt变化及生产调度事件 | 系统jobs只有旁证；需匹配应用同一run的生产执行记录，不能仅凭RUNNABLE或定时任务存在判断正在交换 |

### 3.2 Release可用的最小诊断入口

优先复用现有可用日志/导出设施。若不能获取上述事实，在共享“同步设置 → 诊断”增加一次性本地快照和“导出诊断”，复用平台文件分享/打开adapter。该入口是待实施能力，不是当前包已存在的功能；必须有真实production wiring、可见生成/失败反馈和集成测试。

快照从同一 `SyncRuntime/SyncPanelController` 与现有SQLDelight查询读取，不能另建独立客户端或靠日志文案重建状态。采样前后记录状态revision；若身份发生变化，标为不一致并允许再次采集，不拼出新连接+旧运行的伪快照。读取不拿长期运行锁，不触发refresh token、发现空间、同步、重试或修改偏好。

| 分类 | 必需字段 |
|---|---|
| 环境 | schemaVersion、应用版本/build/sourceRevision、Release身份、采集时间与单调时钟、进程会话标记 |
| 连接 | hasActiveSpace、exchangeEnabled、unsupportedFormat、storedBindingDecode状态枚举、panelConnectionEnabled；读不到明确记unknown/read_failed |
| 运行 | 查询选择来源active/latest/none；脱敏run关联标记、generation、state/phase/stopReason、attemptId、ownerPresent；active与latest是否同一运行 |
| 计数与时间 | confirmedItems、uploaded/downloaded、pending摘要、createdAt/updatedAt/lastProgressAt/nextRetryAt、计算历时 |
| 当前观察 | coordinator.running/trigger、panel.visible/busy、progress是否匹配run、hold、scope关联标记、最近刷新来源/开始/结束及错误类别 |
| 调度 | 当前生产worker/job的关联/执行状态（可得才填）；不可直接取得时用对应ADB只读采样补充 |

不导出令牌、密码、密钥、授权码/链接、账号、仓库路径、作品/作者名、事件正文或完整数据库。run/space/scope等关联标记使用诊断会话内别名，原值不写报告。跨进程比较需要用户明确开启一次诊断会话：私有缓存只保留随机盐与上一快照的关联摘要，用随机盐HMAC生成诊断别名；最长24小时或用户结束诊断时清理，盐不导出。不开启时不保证跨进程别名可比较，报告明确这一限制；该缓存不保存凭据、事件或完整状态轨迹。

仅内存保留最近128条元数据转换事件：panel open/close、refresh开始/结束、连接判定变化、运行状态/attempt/owner变化、调度开始/退出。字节回调与逐秒数字不逐条记录。导出JSON上限256KiB，截断写明；生成失败不影响业务，正常同步也不为诊断增加DB事务。若需要跨进程持久追踪，先说明额外存储/保留/清理和预算，不默认扩大为长期日志系统。

内存轨迹只解释安装诊断包之后的观察，不能还原9月历史经过。历史记录证据不足时，保留未确定结论；受控复现只能证明相同机制可发生，不能证明真机历史必然由该机制造成。

诊断测试执行实际查询/投影/平台导出：验证disabled与unsupported可区分、active/latest正确、并发采样不会混身份、输出无敏感字段、超限截断/写入失败有反馈；导出前后安全确认/连接/任务/偏好保持不变。不要用只扫描源码关键字的“脱敏测试”代替实际输出检查。

### 3.3 真机取证顺序与停止条件

1. **保留基线**：核对设备、目标包、版本、APK哈希与源码输入；采集当前只读UI/系统jobs、诊断快照A，再执行任何恢复动作。正式包禁止run-as时使用应用自身诊断，不改debuggable、不卸载、不清数据。
2. **持续观察**：同一run采集A/B/C（例如0/30/60秒），比较updatedAt、确认量、attempt、coordinator及调度。持续观察不足时只报告采样时段结论。
3. **面板生命周期**：关闭→重开、设置返回→同步，采集刷新事件和快照；验证七槽展示来自当前持久事实。此步骤只导航，不点击连接/授权/同步。
4. **应用前后台/冷启动**：先确认并报告当前任务与自动同步设置。进后台/回前台、自然进程重建可能触发现有自动同步；真正执行前需具备该设备业务操作授权。优先在隔离夹具测试生命周期；不为取证随手force-stop正在运行的用户任务。
5. **连接恢复**：按诊断区分停用/不兼容/其他错误，再进入相应现有修复流程；原授权/密码由用户完成。不兼容原因未解决不能强启用连接；恢复前后保留快照，禁止清空历史伪造成功。
6. **新任务与正常取消对照**：在有真实同步授权后执行一次手动同步、记录run/attempt/安全确认及终态，再正常取消/重新同步验证R02。先用隔离数据库+MockWebServer验证，不能用真实用户仓库制造故障或强行断网。保留已确认1536条的安全事实，不重算为新任务成功量。

观察到owner/活动运行矛盾、格式错误、凭据读取失败、并行任务或任何安全确认异常，停止恢复/重试，保留快照并定位对应生产边界。仅历时大或存在未来定时job不构成反复重试理由。

### 3.4 条件修复，而非预先改生命周期

- 若刷新遗漏/晚到结果覆盖被证实，局部修复现有controller串行队列/订阅或Android可见生命周期接线；测试同身份最新值与跨身份旧结果丢弃。不得给每次ON_RESUME再创建同步任务。
- 若终态仍被非业务刷新改写updatedAt被证实，沿真实写入入口修复并用文件数据库回归；不为UI随意引入endedAt迁移。确需数据格式变更先独立规划。
- 若正常退出/取消留下所有权或coordinator.running被证实，沿既有取消/NonCancellable释放路径修复，验证同一运行、事务及多调用者；不得全局清owner、重置重试预算或无限启动新run。
- 若仅持久连接停用，修复入口与解释并验证合法重新连接即可；若仅历史跨度大且终态冻结，保留正确时间语义，不改时间算法。

- [ ] **SR02：补齐一次性Release诊断快照与真实导出入口。** 前置为字段可用性核对，优先复用已有设施；只增加本地只读取证。TDD覆盖真实状态查询、敏感数据排除、采样一致性及平台导出失败，满足第3.2节的数量/大小上限。交付可在正式包读取的事实，不能只在Debug独立客户端显示假状态。
- [ ] **SR03：完成真机DEBUG判别并关闭已证实的剩余缺陷。** 前置为SR01/SR02的focused测试、兼容签名候选和设备操作范围。执行第3.3节，生成逐项结论：已证实/排除于当前观察窗口/历史证据不足。只实施第3.4节证实且在边界内的必要修复，先补红测；没有证据时不改生命周期。涉及安全/迁移/显著扩张则暂停相应部分重新定范围。
- [ ] **SR04：集中平台验证、正式产物与证据收口。** 前置为稳定修复diff、独立审查通过。完成相关模块/共享存储与双端wiring、一次完整Android/Desktop测试、格式和规定构建运行验收；真机重点R01/R02/R06/R08。保存唯一聚合证据，包含安装包身份、诊断前后、未解边界、正式产物路径和提交；不把浏览器/测试替代真实Release路径。

依赖：SR01与SR02共享面板/数据上下文，默认串行；SR03依赖可采集的正式候选；SR04复用同一diff有效证据。若需要先交付诊断候选再取证，候选构建一次、取证后最终修复候选构建一次，分别使用递增versionCode和原证书；无后续产品变更则复用已验候选，不为文档hash重建。

下一轮实施建议最多2个子代理：首个SR01任务簇交实施者主要实现与focused TDD；SR02及后续修复优先复用该实施者；另1位未实施目标代码的审查者，主代理规划/接口/整合/真机证据。独立审查1轮，修复复审最多1轮；稳定SR01/SR02与SR03中无高风险的必要修复可合并审查，未审查项不勾选。出现必须先审查的安全/迁移边界则停止依赖工作并重新声明预算。

同worktree重型Gradle由一个协调者串行。红绿只跑当前focused测试；集中全量Android/Desktop各一次，不每个任务重复。正式Desktop必须走 `scripts/build-desktop.sh`，用build-only需同diff已具备等价全量证据；按实际脚本是否内置协调器选择唯一包装层。Android走 `build-android.py check --signing/candidate/verify`，不交付临时outputs APK；安装和设备业务操作另按现有授权执行。Mac不可用时记录待验，正式EXE只引用构建日志Final unpacked EXE的实际地址。

预估：SR01 1–2小时，SR02 1–2小时，SR03 0.5–1.5小时（不含新增复杂根因修复），SR04 1–2小时，总计约3.5–7.5小时；主要成本为原生Compose/集成测试、正式打包和真机采样。过程产物沿用协调器日志/少量截图，聚合报告仅1份，不建全新遥测服务或逐任务快照。本轮规划0子代理、一次文档核验，不运行Gradle/构建/ADB。

## 5. 收口验收与交付结论

- [ ] 真机历史已取消、连接未启用 → 有正确的连接恢复入口与原因，历史记录保留。
- [ ] 连接恢复完成后立即同步 → 新任务合法启动，旧取消结果不会锁住主操作。
- [ ] 终态等待60秒并关闭重开 → 上次历时冻结、无活动语义，剩余时间为—。
- [ ] 连接停用/不兼容/其他读取错误 → 诊断明确区分；未取得历史来源不猜测用户操作。
- [ ] 前后台及授权范围内冷启动 → 消费当前状态，不因refresh重复启动同步；旧结果不覆盖新运行。
- [ ] 完整测试、真实Release运行、签名产物和独立审查 → 实际证据可追溯，未验平台/行为明确保留。

最终报告分别说明“入口BUG已修复”“历史历时解释”“当前是否有执行”“生命周期是否存在缺陷”四个结论。后面三项允许真实结论为尚无历史证据，不以猜测写成已修复；已证实且属于本次范围的阻塞问题未关闭时，不宣布迭代完成。

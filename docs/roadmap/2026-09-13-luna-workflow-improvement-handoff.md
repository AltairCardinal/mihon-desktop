## 1. 已知事实与归因边界

1. AEX-02 在 2026-09-13 20:04–21:10（UTC+08）约 66 分钟内有 36 次 Gradle 调用，记录的命令运行时间合计约 22 分钟。20 次失败退出包含正常 RED，不能当作 20 次浪费；其余时间也包含有效编码/分析，不能全部归因等待或协调。
2. 真实装配失败包括协程测试调用方式、MockWebServer 依赖、SQLDelight Adapter、String/ByteArray 参数错误。它们不能证明目标产品行为已被正确测试。
3. B2 先改后测曾通过撤回自有草稿重新执行纠正；B3 随后再次出现相同偏差。重复发送顺序要求没有阻止重犯。事后回退重放不改变原始顺序事实。
4. 一次重复 Gradle 调用中的目标测试和编译任务均为 UP-TO-DATE，不是新增测试执行。测试结果可合理复用，但必须绑定对应输入，不能引用被后来运行覆盖的 XML 证明早先失败已通过。
5. 主模型在持续写入时多次插入局部审查和临时指令，也产生了协调成本；不能把原因全部归为 Luna。目标原文/哈希核验曾反复往返，属于交接问题，不是产品验证失败。
6. roadmap 的 B1–B4 太宽，却按每组各一次红/绿/重构计命令，预算与行为粒度不匹配。该问题已在关联 roadmap 修订，但没有据此声称产品实现完成。

这是一个项目中的执行案例，不足以证明某模型或 effort 的普遍优劣。当前技能已经要求范围隔离、证据、原代理修复和有界预算；需要改善的是可执行性及重复偏差处置，而非把已有要求再复制一遍。

既有 `REPORT.md` 明确其题集没有实际 Kotlin/Compose、长周期多模块工程等覆盖；`benchmark/verify_all.py` 主要重放既有解答和反馈夹具。原评测可作回归，但不能单独证明本次真实调度、TDD 顺序和等待问题得到改善。

## 4. 如何测试：不能只测“规则写进去了”

### 4.1 先冻结判定，再运行候选技能

- 为 L01–L12 各建立正例与反例；合并共享上下文为少量场景包，不为 24 个变体启动 24 个长期 agent。
- 提前固定任务输入、允许文件、产品断言、事件不变量、停止预算和效果指标。实现 agent 可看公开需求，不看保留的验收用例或其他候选答案；不能事后为通过而放宽判断。
- 测试结果至少区分 `PASS`、`FAIL`、`NOT_RUN`、`INVALID_RUN`；工具故障、截断和缺失轨迹不能记 PASS。预期正确 RED 不计失误，runner 错误不得算产品缺陷覆盖。
- 技能语法/链接/模板检查只算静态检查。对模拟 trace 的规则判定器测试只证明判定器自身；必须再让真实主模型和真实 Luna 使用候选技能执行受控场景，观察实际行为。

### 4.2 事件证据与负例

最小观察记录：任务/场景 ID、执行角色、事件序号、目标行为、受影响文件、命令及起止/退出、报告指向、必要环境/输入版本、暂停/授权事件。优先复用现有工具事件和构建记录；只保存脱敏摘要及必要证据，不复制整个私有会话，不记录凭据、真实 memo、个人线程 ID 或用户数据库。

TDD 判定示例（行为名称由预先固定任务确定，不能由候选实现自行划分以规避顺序检查）：

1. 验收器观察候选新增测试，实际 runner 返回该行为正确 RED。
2. 验收器随后观察首次相关 production 行为修改及 GREEN。
3. 若测试装配自身错误，RED 未成立；若只有预期缺失 API 的编译差异，按项目规则判定，不一概要求运行期失败。
4. 若先修改 production、后来撤回重放，记录历史违规和后续恢复质量；不能把最终文件正确改判为全程 TDD 合规。
5. 测试加入后已经通过：检查是否是既有覆盖/新增回归，不能伪造一次失败。是否已发生未测实现按工具时间线判断。

故意投放的判定器负例：打乱 RED/production 顺序；将旧 XML 配给新 diff；把 NO-SOURCE/必要 skipped 改成 exit0；让父模型接受子代理自报作为独立验收；超时后重复启动；在审批未到时提交/发布。每个负例必须被拒绝，正常缓存命中、合法等待、正确 API RED 则不能被误拒。

真实行为测试不能只让代理写“下一步应该怎样”：L04 要实际改隔离工程并运行测试；L09 要真实启动/查询受控进程；L06 要在实际工作消息边界注入反馈；L10 的模拟工具返回只能证明该分支决策，还需一次真实可用工具的隔离/原文核验。工具能力缺失时保持该项 NOT_RUN，不偷换验收层级。

### 4.3 保留现有产品质量基线

- 复跑既有 `benchmark/evaluate.py` / `verify_all.py` 的有效行为断言，保留原结果与小样本限制；执行前读取实际脚本和所属环境要求，不把文档示例路径当已验证命令。
- 新场景的最终代码必须通过维护 agent 独立控制的产品/回归测试，至少有一个跨模块调用和一个真实存储或 HTTP 集成点。破坏 production wiring 时测试必须失败。
- 固定模型/effort、主模型版本、授权、工具和工程版本；若同时改 roadmap 与 skill，实验结论是组合改进，不得称为 skill 单独效果。测试 skill 单独效果时，两组使用同一冻结任务计划。
- 不通过删验收项、mock 被验收的实现、跳过必要运行层、使用宽权限或去掉主审来换取速度。

## 5. 如何判断改善确实有效

### 5.1 有界的前后对照设计

以下是建议实验预算，维护 agent 须开始前明确实际成本；本轮没有运行这些实验：

1. 保存技能旧版与候选版的可追溯版本/哈希，在各自隔离的测试环境加载，不覆盖用户正在使用的技能做 A/B，也不创建新的长期调度服务。
2. 先通过第 4 节受控场景与判定器测试。随后选两类有代表性的真实小任务：A 为有现成测试骨架的多模块行为修改；B 为带既有草稿/明确故障的恢复任务，含 HTTP 或真实 DB 集成。A 正常路径测试 TDD；B 的历史违规不计为候选新违规，但必须如实处理。两组使用同样预设的授权与模拟用户反馈；故意不给必要授权的分支用于第 4 节停止边界测试，不混入可完成任务的提效比较。
3. 每类任务对旧/新版各运行两次新会话，共 **8 次完整流程**，包含主模型规划/监督/主审，不仅运行 Luna 子代理。它们不是 8 个同时活跃代理；并发仍遵用户预算，争用同一构建缓存/设备的任务串行。
4. 配对运行使用相同工程基线、fixture、环境、计划和公开要求；不同组不共享答案。交换旧/新版的先后顺序，统一冷/热缓存条件；记录不可控制的模型或服务版本变化。固定每次时间上限和修复预算，未完成同样计入结果，不只挑完成运行比较速度。
5. 用同一独立量表检查匿名产物；若评审人知道版本映射，明确这是非盲评。模型随机性与只有四对运行的限制必须报告，不宣称统计显著或普遍节省比例。

### 5.2 指标定义

| 指标 | 计算与边界 |
| --- | --- |
| 产品通过与新增违规 | 独立产品/集成测试通过率；新增 TDD 顺序违规、越权、误报完成、用户改动损坏分别计数，不用总分抵消 |
| 装配失败 | 测试未进入目标行为的编译/依赖/runner 失败次数，以及同原因重复失败次数；正常 RED 不计入 |
| 无依据重复验证 | 输入未变、有有效通过证据、又无独立验收或回归目的的重复调用；合法主审验证、实际改动后的复验不计入 |
| 调度往返 | 非必要审批、反复空闲唤醒、重复目标格式纠正、碎片化非阻塞干预分别计数；必要安全制止单列，不作为浪费 |
| 返工 | 因流程顺序错误撤回重做或重复实现的行为组数量及可证实时间；正常最小实现后的重构不算返工 |
| 端到端时间 | 从主模型开始执行到独立验收/交付的墙钟，包含规划、Luna、主审与修复；有证据的外部用户/服务等待另列，未归因间隔保留未知 |
| 用量 | 仅引用统一统计已提供、同口径且包含主模型的汇总；没有就写未取得，不另抓私有日志/建计费脚本，不用理论 API 单价冒充账单 |

### 5.3 预先约定的接受门槛

- **正确性硬门槛**：全部必需受控场景及既有有效回归通过；候选真实运行不新增越权、数据破坏、假完成或 TDD 顺序违规，预置历史偏差不得掩盖。受影响 wiring 验证不能减少，必要项目没有 NOT_RUN/skipped。任一硬门槛失败则不能判改进成功。
- **行为改善门槛**：本轮投放的重复装配盲试、旧证据误用、超时重复启动和无意义空闲唤醒均被正确处理；同时正常缓存、普通修复和正确 RED 不被新审批阻塞。验证“该停时停”和“该继续时继续”，不能只靠更保守地全部暂停得高分。
- **效率门槛（建议预注册值，不是已测收益）**：四对真实运行中至少三对的可避免事件总数下降；候选端到端时间中位数不增加。若旧版至少一对已有 0 个可避免事件，则该对允许持平，但必须保持 0；不得通过弱化定义把事件移出统计。欲对外称“明显提效”，建议要求端到端中位时间再下降至少 20%，开始实验前固定阈值，不根据结果改口径。
- 四对样本只支持“在这些任务上观察到改善”。质量通过但效率无改善：可报告正确性加强，不能报告提效成功；效率变快但质量失败：拒绝；样本/工具不足：标未验证。扩大样本或增加其他语言/平台应另报预算，不自动不断重跑到出现好结果。

## 6. 维护 agent 应交付的结果

1. 技能及契约的最小修改 diff，逐项映射 L01–L12；说明哪些是既有规则落实，哪些是新增约束，以及冲突时的优先级。不把此清单全文塞入每次子代理 prompt。
2. 受控场景、实际执行证据和判定器负例结果；静态验证、模拟分支、真实工具/agent 运行分层报告，不互相替代。
3. 一份简洁的旧/新版配对结果及边界说明，含失败/未运行，不只精选最快结果。旧 benchmark 原始数据保留，不改历史报告结论来制造提升。
4. 技能所属仓库的 scoped commit 与安装/发现验证；本项目 roadmap、AEX 差异和产品提交不由技能维护 agent 修改。

当前交接完成只表示需求与测试方案已给出。技能是否改好、是否更省时，必须由上述后续证据回答。

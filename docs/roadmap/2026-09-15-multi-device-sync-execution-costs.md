# 多设备同步执行经验与成本

本文件记录 2026-09-15 起由当前主模型接续完整同步 roadmap 的执行方法、可观察成本和失败。产品范围与完成状态以[实施计划](2026-09-13-multi-device-sync-implementation.md)为准。本文件不新增产品任务，也不把过程活动算成功能完成。

## 计量与归属

- 用户以累计 token 消耗作为成本近似；记录工具可读取的 goal/token 快照及其口径，缺失的数据写“不可得”，不由墙钟时间或模型单价反推实际扣减。
- 新 goal 创建时工具报告 tokensUsed=0。旧 Luna 阶段成本不混入本轮；历史测试与已完成 S1 直接复用，除接口变化不重复验收。
- 每个交付任务记录开始/结束累计值、差值、并行上下文与无法分摊部分。若计数无法区分代理则不虚构分项精确值；最终用任务用量工具输出补充总量。
- 初始固定流程：每完整任务一轮独立审查和至多一轮定向修复复审，focused TDD 随实现执行，阶段/发布才全量。使用既有协调器日志与测试 XML，不制作快照或巨型 diff。

## 逐项交付记录

S1 为历史完成项（`ed5501cb1`），不重新计为本轮交付。

### S2b：共享加密与恢复资料

- 交付：严格批次校验、固定 AES-256-GCM wire 向量、恢复资料错误脱敏及不可变字节；本记录与代码/测试同次提交。生产安全存储和真实设备运行保留 S4/S5。
- 成本快照：goal 从 0 到 366,791 tokens，墙钟 1,188 秒（提交前）。该区间包含 roadmap 核对、S2a 并行实现与两项独立审查，工具没有可靠分项归属，不将全部 token 记为加密独占成本，也不重复计入后续累计总额。
- 失败：首次 RED 10/4；修复绿后独立审查发现事件 batchId 接收侧漏检，新增 RED 13/1，随后闭合。最终两目标各 15 项通过，独立复审通过。
- 工具开销：首次后台/代理环境启动命令被自动审批拒绝，改用现有协调器 run + 本地缓存成功；Spotless 第一次相对路径 hook 实际跳过，核对日志后改为绝对路径；两次不可自动修复长行在同一格式处理流程内修正。最终所有本项 Kotlin 文件逐个 IS CLEAN，未把进程 exit 0 单独当格式证据。
- 反思：首次测试补齐了明显字节/序号边界，却遗漏 encrypt/decrypt 对内部事件 batchId 的对称性；后续协议任务先列发送与接收校验的同一反例集合。派生数据格式与接收路径应由同一上下文连续实现。
- 方法调整：保留 root 的 Git 状态机连续实现，授权代理在自己上下文修分页边界；复用一个独立审查代理，不为每个漏洞再加载新代理。新测试先 RED，不重复旧阶段全量。

## 可复用经验

1. 能力拆分应减少同时未决的设计约束，同时保留强耦合格式与状态机的上下文；文件数量和行数不是独立交付的判据。
2. 已有可复现失败测试及其 production 未变化时可复用红色证据；新增边界必须通过真实失败验证，不能把 fixture 或编译错误当业务红色。
3. 并行任务必须约定文件所有权与验证执行者。共享构建产物不因源码文件不同就自动具备并行运行条件。
4. 已有缺陷是观察事实，分工是否更省成本是待验证判断；没有可比样本不宣称某模型或固定重试次数最优。
5. 格式器或其他工具 exit 0 可能代表没有匹配目标，必须核对实际目标与执行证据；限定格式应使用绝对路径，避免同树并行作者文件被自动修改。

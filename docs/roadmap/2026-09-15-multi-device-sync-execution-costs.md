# 多设备同步执行经验与成本

本文件记录 2026-09-15 起由当前主模型接续完整同步 roadmap 的执行方法、可观察成本和失败。产品范围与完成状态以[实施计划](2026-09-13-multi-device-sync-implementation.md)为准。本文件不新增产品任务，也不把过程活动算成功能完成。

## 计量与归属

- 用户以累计 token 消耗作为成本近似；记录工具可读取的 goal/token 快照及其口径，缺失的数据写“不可得”，不由墙钟时间或模型单价反推实际扣减。
- 新 goal 创建时工具报告 tokensUsed=0。旧 Luna 阶段成本不混入本轮；历史测试与已完成 S1 直接复用，除接口变化不重复验收。
- 每个交付任务记录开始/结束累计值、差值、并行上下文与无法分摊部分。若计数无法区分代理则不虚构分项精确值；最终用任务用量工具输出补充总量。
- 初始固定流程：每完整任务一轮独立审查和至多一轮定向修复复审，focused TDD 随实现执行，阶段/发布才全量。使用既有协调器日志与测试 XML，不制作快照或巨型 diff。

## 逐项交付记录

S1 为历史完成项（`ed5501cb1`），不重新计为本轮交付。

### S2b：共享加密与恢复资料

- 交付：严格批次校验、固定 AES-256-GCM wire 向量、恢复资料错误脱敏及不可变字节；本记录与代码/测试同次提交。生产安全存储和真实设备运行保留 S4/S5。
- 成本快照：goal 从 0 到 366,791 tokens，墙钟 1,188 秒（提交前）。该区间包含 roadmap 核对、S2a 并行实现与两项独立审查，工具没有可靠分项归属，不将全部 token 记为加密独占成本，也不重复计入后续累计总额。
- 失败：首次 RED 10/4；修复绿后独立审查发现事件 batchId 接收侧漏检，新增 RED 13/1，随后闭合。最终两目标各 15 项通过，独立复审通过。
- 工具开销：首次后台/代理环境启动命令被自动审批拒绝，改用现有协调器 run + 本地缓存成功；Spotless 第一次相对路径 hook 实际跳过，核对日志后改为绝对路径；两次不可自动修复长行在同一格式处理流程内修正。最终所有本项 Kotlin 文件逐个 IS CLEAN，未把进程 exit 0 单独当格式证据。
- 反思：首次测试补齐了明显字节/序号边界，却遗漏 encrypt/decrypt 对内部事件 batchId 的对称性；后续协议任务先列发送与接收校验的同一反例集合。派生数据格式与接收路径应由同一上下文连续实现。
- 方法调整：保留 root 的 Git 状态机连续实现，授权代理在自己上下文修分页边界；复用一个独立审查代理，不为每个漏洞再加载新代理。新测试先 RED，不重复旧阶段全量。

### S2a：设备授权与安全 HTTP

- 交付：设备授权/续期、私库筛选、分页和安全 HTTP adapter；8 个 Kotlin 文件由同一个当前模型子代理实施、另一个代理独立审查，root 串行运行验证并提交。
- 成本快照：goal 累计 440,581 tokens、1,819 秒（提交前）。相对 S2b 快照增加 73,790 tokens / 631 秒；这是共享执行时间窗口的新增消耗，S2a 初始实现已经包含在前一窗口，不把此差值冒充 S2a 全部成本。S2b 提交为 `46827b207`。
- 失败：首次 RED 28/14；自测两目标各 33 项全绿。独立审查后 RED 17/1，修复分页恰好达到上限时的误拒绝。最终两目标各 35 项绿，原审查代理一次限定复审通过。
- 过程开销：受限格式器先后被不同文件的不可自动修复长行挡住，增加了数次短 Gradle 格式运行（没有重复全量）；其中 raw JSON 常量和格式展开后增加的缩进使仅按原始源码长度搜索不足。root 与实现者来回处理这些机械格式的收益低于同一作者直接用检查器完成整簇收口。
- 反思与调整：后续委派时，完整能力交付应同时包含范围内格式核验；root 掌握 Gradle 单一执行权，但交由原作者一次收齐当前格式器全部诊断后修正。Git 索引与发布保持 root 连续实现，不再把共享状态机拆给不同作者；候选稳定后复用原审查代理。
- 范围边界：没有做真实用户授权、系统凭据保存或 UI，不将 HTTP fixture 的结果升级为产品端到端完成。

### S2c：Git 数据交换闭环

- 累计快照 627,947 tokens / 3,281 秒；相对 S2a 快照增加 187,366 tokens / 1,462 秒。包含 root 的 Git 实现、测试及 S3a 只读勘察，独立审查刚开始，不能视为本任务最终成本。
- root 连续处理同一 Git 状态机，避免把固定索引、持久制品和竞争发布拆成重复加载的代理任务。原授权代理仅做下一阶段稳定事务入口的只读映射，限制为 10 分钟，不穷举 UI。
- 当前失败包括业务 RED、初始化竞争与响应丢失，以及两次长行格式阻塞。格式成本仍偏高：第一次批量修正遗漏了 123 字符的路径字符串；以后在交检查器前检查整簇长行，字符串也纳入，而非仅检查表达式。
- 主工作树新增未提交 migration 19 与模型变更，记录为整合约束；不为了赶进度占用编号或复制未提交文件。
- 完成前快照：累计 725,213 tokens / 3,943 秒；相对 S2a 窗口新增 284,632 tokens / 2,124 秒。该差值还包含 S3a 有界勘察；S2c 更早的部分工作已在前窗口，不虚构任务独占精确值。累计值只累加一次。
- 独立审查失败：残缺索引被误判为可初始化、历史 snapshot 被当作当前发布确认；另有发送侧提前拒绝掩盖接收链测试。新增 RED 26/2，集中修复；对接收缺序测试做一次定向失效注入，移除真实序号校验后 1/1 失败，再恢复。两目标各 32 项绿，限定复审通过。
- 阶段验证：domain/data 两目标完整测试共 1,092 项全绿，单次协调器运行约 23 秒。保留 UI、真实服务和发布验收边界。
- 反思：正确的公共读取/写入方法不能自动保证每个捷径都满足相同不变量。后续事务任务先列“正常、重试、恢复、已有状态”四类入口，逐条核对业务写与事件写是否同事务；所有能清队列的路径必须有当前有效凭据。发送与接收独立给反例，避免某一侧提前失败掩盖另一侧漏检。
- 后续方法：S3a 共享 schema、来源上下文和事务强耦合，先由 root 连续实现，保留原审查代理；不因两代理已存在就分散同一数据库改动。独立能力边界稳定后再评估并行，不预设每项固定双代理。

## 可复用经验

1. 能力拆分应减少同时未决的设计约束，同时保留强耦合格式与状态机的上下文；文件数量和行数不是独立交付的判据。
2. 已有可复现失败测试及其 production 未变化时可复用红色证据；新增边界必须通过真实失败验证，不能把 fixture 或编译错误当业务红色。
3. 并行任务必须约定文件所有权与验证执行者。共享构建产物不因源码文件不同就自动具备并行运行条件。
4. 已有缺陷是观察事实，分工是否更省成本是待验证判断；没有可比样本不宣称某模型或固定重试次数最优。
5. 格式器或其他工具 exit 0 可能代表没有匹配目标，必须核对实际目标与执行证据；限定格式应使用绝对路径，避免同树并行作者文件被自动修改。
6. 一个单元待最终验证时，其他单元暂不破坏共享编译接口；先收口可提交候选，再切换下一能力的签名，减少并行开发引入的验证等待。


### S3a1：事务日志与收藏入口

- 依据实际事务入口将 S3a 拆为收藏/共享日志、作者关注、阅读三个能力；先由 root 建立稳定事务 API，再允许后两者独立接入，避免让依赖未就绪的代理相互等待。仅整合主工作区已提交的 `bc8256569`，保留其未提交迁移 19。
- 当前累计快照：goal 续轮提供 870,371 tokens，包含本阶段早期实现和构建诊断；未收口，不计算独占任务成本。
- 已有行为 RED：日志首轮 6/5；迁移追加 10/2；Desktop 收藏入口 1/1；独立审查并发 heads 1/1。遗漏 SQL Boolean import、跨模块 smart cast 和 Gradle 命令转义导致的编译/启动失败不算行为 RED。
- 额外成本集中在 Android 测试前置许可证任务：离线 POM 缺失、代理配置 argv 中竖线被 cmd 解释、JitPack 404、排除 task 导致 provider 未完成、停用 task 后缺少资源 ID。修正为 JAVA_TOOL_OPTIONS 传代理；临时测试 init script 停用许可证生成并声明资源 ID，仅用于本批测试，不伪造许可证、不用于发布。原诊断代理用量受限退出，root 接续已有证据，不再新建同类诊断代理。
- 首轮审查发现原协议允许 generation=0 而新增数据库拒绝；另有旧观察操作误删并发 heads。反思：存储层要用既有协议边界作为约束来源，并让接入测试覆盖多个真实 UI 调用路径，不能根据同名用例推断全部入口已统一。修复仍在本批范围内。

- 完成快照：累计 1,108,928 tokens / 6,982 秒（提交前）；相对 S2c 完成快照 725,213 / 3,943 增加 383,715 tokens / 3,039 秒。该区间包含旧接口勘察复用、AEX 已提交基线整合、构建诊断、两轮限定审查与格式适配，不能虚构各代理独占成本。最终相关 108 项通过；没有重复执行全量产品测试或发布构建。
- 格式适配失败过多：先猜测 Desktop 具有 Spotless 任务，再尝试跨模块绝对字符串 target（被当 glob，0 个输入）、FileCollection（跨项目相对路径错误）、root 插件（buildSrc 同名根与已有 clean 冲突）。最终只在 Desktop 模块临时加载现有 lint 插件，显式校验 2 个输入，成功格式化并复验。后续先读目标模块的插件配置；需要临时检查时绑定目标模块，不从别的模块改写其文件；检查输入数量后再宣称通过。测试工具适配不能默默演变为生产构建重构。
- 交付边界：本地日志和既有收藏入口已接通，完整同步 UI/网络调度与发布尚待后续。主工作区未提交 migration19 保留不碰；本任务 migration20 在最终整合前不能发布。下一步仅复用 1 个可用代理做作者能力，root 连续做阅读能力，稳定 API 与文件边界先交付再分派，不再启动失败的环境诊断代理。


### S3a2：作者关注事务接入

- 交付：15 个作者能力文件；portable_key FOLLOW 操作与关注同一事务，保留本机扫描偏好、默认非用户来源不上传，双端真实页面与 Test Mode 复用 SetCreatorFollow。独立审查由 root 完成，无阻塞及额外复审；最终相关 84 项全绿，格式 15 文件有实际覆盖，提交仅包含作者能力和必要记录。
- 最后采样累计 1,279,296 tokens / 8,288 秒；相对 S3a1 完成窗口增加 170,368 tokens / 1,306 秒。此窗口还包含 root 并行实现阅读数据库及会话快照（两目标各 9 项绿），不能将全部差值归为作者独占成本。
- 失败：作者存储 RED 各5/4，追加来源与入口 RED 存储7/5及双端/测试模式 User 断言失败；在新增来源约束接入前，两端 UI 的共享用例尚未传递 User 标记。完成后相关能力全绿，没有审查返工。重关注清空来源/语言是确认的旧行为缺陷，null 保留和显式空清空通过真实 SQL 数据验证。
- 并行成本：同文件写入隔离仍不足以保证测试独立。作者接口修改了漫画详情测试中的 fake，root 同时改变章节同值操作语义，使整类回归有一项预期外失败；这是阅读任务未更新旧断言，不是作者缺陷。以已提交阅读用例进行一次有界作者验证后原样恢复开发代码，进程最终通过。下次按行为依赖安排验证窗口；同一 UI 模型包含不同能力时，先收口依赖接口批次，再改变其另外一类行为。
- 格式处理复用了 S3a1 已验证的模块内临时 lint 方式，一次格式化、一次检查成功；未重新探索插件或扩大生产构建配置。相较前一窗口的流程开销减少，但能力复杂度不同，不能据此断言固定并行策略或模型更省成本。

### S3a3：阅读会话与明确已读/未读

- 交付：root 连续实现共享阅读事务与 Desktop，复用同一个代理实现 Android，按文件所有权隔离后交叉审查。真实激活捕获因果基线、进度接受时固定无痕许可，旧队列不串到新会话；明确同值操作仍记录，保留下载清理原范围。最终相关 238 项与 26 个 Kotlin 文件格式通过，一轮交叉审查及一次限定复核通过，随功能代码与 roadmap 一起提交。
- 提交前采样累计 1,927,284 tokens / 10,440 秒；相对 S3a2 最后采样增加 647,988 tokens / 2,152 秒（约 36 分钟）。部分阅读共享层成本已计入上一并行窗口，本窗口也包含 roadmap 答复和收口准备，不能宣称这是完整能力独占成本，亦不能从原始 token 计数反推实际收费。
- 行为失败：存储早期 6/5、会话追加 9/3（均为每目标）；Android 实际入口缺少 User/session、同值过滤和一次无痕时序问题；Desktop runtime 4/4 初始失败，以及已读下载清理范围扩大。独立审查再发现 1 个基线读取失败后无错误反馈的问题，5 项中唯一 RED 后修复。手动多章第二条 outbox 回滚属于审查补测，现有事务本身未被证实有缺陷。
- 准备失败与额外开销：Desktop fixture 先缺少真实源，再遇到 MockK get 重载/返回类型问题；改用现有 SourceManager 轻量 adapter 形状后才得到正确业务 RED。Android 的宽松 DownloadPreferences Mock 返回 Object 污染后续用例，显式 Boolean stub 后消除。格式首次遇到 7 条不可自动修复的超长行，机械换行后通过。上述准备错误没有混入产品失败统计。
- 反思：复用共享命令前要盘点所有调用方是否拿“需要更新的集合”同时决定下载删除等副作用；操作日志需要同值意图，副作用可能仍只针对状态变化。异步链要分别固定会话身份与隐私许可，且给新增持久化前置读取补失败反馈；只测成功路径会漏掉永久加载。
- 后续成本控制：先复用已通过的真实 repository/runtime fixture 和明确类型 adapter，避免宽松 Mock 造成反复编译与运行准备。读取文档只取当前权威段，不重复加载长历史；一次汇总相关结果，避免无意义轮询。S3b 的事务/投影上下文重合度高，由 root 连续实现；稳定且独立的接口出现后才委派，不机械沿用本批双端并行。当前没有足够可比样本证明某一固定分工总是更省 token。

### S3b1：对象描述与持久上传

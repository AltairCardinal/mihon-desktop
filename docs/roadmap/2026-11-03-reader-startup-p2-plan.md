## 3. 编译条件：如何查，如何继续

### 3.1 保存真正的失败证据

仅针对隔离包`app.mihon.desktop.fork.benchmark`。确认包路径、APK SHA、签名及进程；停止这个隔离包，保留数据。读取当前设备支持的命令/帮助与目标包的dexopt信息，保存未经过滤丢失语义的目标输出和退出码；不依赖其他Android版本的命令形状。

围绕**一次**编译请求保存设备时间范围、原始stdout/stderr/退出码，以及该窗口内与目标包编译、PackageManager/ART/dex2oat相关的系统错误。先保留必要的限定时间窗口，再按实际tag/PID/package归属筛选；不能只过滤包名把dex2oat不带包名的错误丢掉。不得清空整个设备logcat或导出无限历史。

请求后重新读取目标包状态。报告必须区分：请求是否成功、实际优化状态是否能读到、是否有具体失败原因。旧P1“could not be compiled”是失败结果，不是根因；空输出也不是状态核验通过。只有日志指向空间、温控、电量、权限或并发任务时才做对应的最小检查，不扫描整机做泛化健康检查。

若有不影响用户数据的明确修复条件，在已授权隔离范围内处理并验证一次；不得清应用数据、卸载重建、重启整台平板、修改官方安装的编译状态，或切换编译模式只为让命令返回Success。

### 3.2 不把环境未知变成无限阻塞

- 实际状态可核对：后续控制版和候选使用相同请求策略并读回状态，保存设备负载/采集条件。
- 命令Success但filter仍不可读：标明“请求一致、实际状态未知”；不宣称与历史P0或官方编译状态完全一致。
- Failure原因仍未暴露：报告查过的命令、时间窗口和具体缺失证据。仍可完成**同一APK内部**分段定位，不能以此证明跨APK净性能收益。若控制/候选编译条件明显不一致，候选结果只能作为受限观察，不宣布稳定达标。

不先重装P0或重新测官方；P0/P1历史数据只作参考。本轮修复编译条件本身也不是产品优化，必须与产品改动收益分开记录。

## 4. 一级分段：一次看清整条P区间

现行源码已核对：

- [ReaderViewModel.loadChapter](../../app/src/main/java/eu/kanade/tachiyomi/ui/reader/ReaderViewModel.kt)加载页表后进入UI上下文，先`dualPagePairings.ensure`，再评估无痕状态与`recordReadingProgress.openSession`，之后激活章节窗口、取消已排队下载并发布状态。
- [GetIncognitoState.await](../../app/src/main/java/eu/kanade/domain/source/interactor/GetIncognitoState.kt)是**同步函数**，读取偏好和扩展映射，不应因名字含await就写成协程挂起。首次访问`incognitoMode`还有lazy求值，是否显著须实测。
- [RecordReadingProgress.openSession](../../domain/src/commonMain/kotlin/tachiyomi/domain/reader/interactor/RecordReadingProgress.kt)是suspend；未提供resume snapshot时调用仓库`beginSyncSession`。不能直接等同SQL耗时，也不能把会话建立移到首绘后而改变进度基线。
- [ReaderActivity](../../app/src/main/java/eu/kanade/tachiyomi/ui/reader/ReaderActivity.kt)收集`viewerChapters`并调用`setChapters`；[PagerViewer](../../app/src/main/java/eu/kanade/tachiyomi/ui/reader/viewer/pager/PagerViewer.kt)可能立即应用或等待idle，随后绑定事实、更新adapter及首次布局；[PagerPageHolder](../../app/src/main/java/eu/kanade/tachiyomi/ui/reader/viewer/pager/PagerPageHolder.kt)启动图片链并派发header IO。

保留P1全部事件，仅在现有固定数组末尾追加以下**七个首次时间点**；不是逐函数日志，不新建trace框架。只针对本次目标章节/page0/request，仍区间外导出。

| 名称 | 精确记录位置 | 到下一个边界的解释 |
| --- | --- | --- |
| 已有`PAGE_LIST_READY` | 页表成功发布 | 到UI激活入口：返回、章节列表处理、UI派发等 |
| `ACTIVATION_UI_ENTER` | `loadChapter`的`withUIContext` body入口，确认对应本次目标 | 到owner就绪：原有效性检查和pairing.ensure等 |
| `PAIRING_OWNER_READY` | 本次`dualPagePairings.ensure`正常返回后 | 到进度门完成：激活条件、resume取得、无痕读取及可能的openSession |
| `READING_GATE_READY` | 上述无痕/session分支正常完成，保持原有分支选择 | 到状态发布前：窗口归约、恢复位置、下载取消等，不预判哪项慢 |
| `CHAPTER_STATE_PUBLISH_BEGIN` | 实际发布本次viewerChapters的`mutableState.update`调用之前 | 到Activity接收：state计算/发布、Flow和主线程调度 |
| `ACTIVITY_CHAPTERS_RECEIVED` | Activity收到并将应用本次章节/pages的`setChapters`入口 | 到本页setImage：viewer/idle、adapter/布局、holder创建/状态处理 |
| `TARGET_IMAGE_ENTER` | 目标holder的`setImage`入口、首次呈现准备之前 | 到IO派发前：beginPresentation、代次与身份快照等 |
| `TARGET_HEADER_DISPATCH` | 原`withIOContext`调用前、身份快照之后 | 到已有header BEGIN：IO派发排队 |
| 已有`TARGET_HEADER_BEGIN` | IO body内真实header调用前 | P区间终点，后续H/Q继续保留 |

**关联与时序规则：**

1. VM/Activity/holder使用同一捕获的诊断request，结合当前章节与pages对象确认归属；迟到回调不能现场取全局active请求冒充新样本。不向共享业务状态/持久数据增加诊断字段；必要的关联仅在当前诊断生命周期内有界保存。
2. 各事件只记录第一次合法命中。合法短路分支按真实“分支已完成”记录，例如无痕时READING_GATE_READY不表示创建了session；相关分支身份可由现有状态或区间外观察记录，不为探针额外查询仓库。
3. STATE标记放在update**之前**，避免消费者可能同步/重入执行时，把发布后标记和接收标记错误要求为串行。`update`的可重试lambda内部不放“完成”时间点。
4. 源码调用顺序不代表实际事件必然有全链。只有目标匹配且上述边界非递减时才相减；重复/重入/切换导致归属不明时保留原件，不按名字重新排序、不跨尝试拼接。
5. 八个相邻差值的和必须精确等于`TARGET_HEADER_BEGIN−PAGE_LIST_READY`。它们是wall区间，不是独占CPU；再结合对应trace线程Running/Runnable/等待判断，不能只看函数名归因。

## 5. 二级定位：只进入最大的未解区间一次

一级一首一暖后，按实际占比和跨样本机制选一个主要区间，不默认所有区间都加点。若已确定具体生产操作/等待和安全改动，可直接进入候选；否则本计划**已经包含一次必要的二级细分**，不必另起会话或另写计划。

| 一级集中位置 | 二级最小动作 | 禁止的推断/改法 |
| --- | --- | --- |
| owner建立 | 对ensure内部已找到的主要子调用加最多3个边界，结合现有cache/identity逻辑 | 不能删原图/内容校验或默认伪造几何 |
| owner之后、进度门之前 | 分开无痕评估与openSession；若session慢，沿真实beginSyncSession仓库/锁/查询边界取证，最多3个新点 | 不能把整个suspend wall当SQL CPU，或先记录进度再补隐私判断 |
| 进度门之后、状态发布之前 | 只夹住实际可疑的窗口处理或cancelQueuedDownloads等子调用 | 不能因函数“看起来不影响图片”就删业务动作 |
| 状态发布到接收 | 区分update计算/提交和调度；提交后边界可能与消费者重叠，单独报告，不重复相加 | 不能把StateFlow全局改成另一种流或强行同步调用UI |
| Activity接收到holder | 记录真实viewer内部应用入口、adapter更新结束或目标holder创建等最多3点；确认是否真的走awaitingIdle | 不能把正常手势idle保护无条件删掉 |
| holder内准备 | 在beginPresentation/现有capture路径最慢调用两侧取证 | 不能跳过像素锁或把非空容器当漫画绘制 |
| UI/IO派发间隔 | 用已对齐的Perfetto线程调度和相应边界确认排队；必要时补一个可归属的入口 | 不能看到Runnable就全归某调度器，不能全局扩大线程池 |

二级保持相同产品逻辑与采集协议，再一首一暖；记录为新的仪器版本，不能把一级和二级混成同一基线。二级后输出具体操作/依赖和耗时、是否可安全削减；仍无法归因时明确列出最小剩余未知及证据缺口。不能连续无限细分，但也不能完成一级后仅写“准备与等待较长”就结束。

若首次和暖态集中位置不同，分别保留差异，选择证据更明确且影响实际首次体验的一项；不以混合均值制造统一根因。编译条件仍未知时同APK内部定位继续有效，跨版本因果判断仍受限。

## 6. 条件化优化方案与必要保护

只有证据显示**重复工作、无功能依赖的前置等待或可安全复用的同身份结果**时才实施一个最小候选。可以是复用现有同一激活内已取得的值、解除明确无依赖的串行等待、避免同一绑定的重复准备；必须先指明真实消费者与失效条件。用户看到的变化仍是正常点击下载章节更快显示，无新设置/弹窗。

不预先指定“延迟进度会话”“合并所有IO”或“跳过配对初始化”。若最终瓶颈恰是必要业务且无安全替代，就交付确定的原因和成本，不伪造优化。需要改共享协议、持久化、EXIF或身份权威的方案超出本轮，应另说明设计与风险。

最小验证按实际变更选择：

- 插桩：扩展一个现有记录器方法，验证新增事件、首次命中、错误request/page拒收；真实端到端接线以同次设备事件/像素/恒等式验证。复用未变的P0/P1已通过证据，不跑整个记录器或大型viewer类。
- 产品：一个真实生产链红测证明拟去除的重复工作/等待，最小实现后同方法GREEN；加直接受影响的必要保护。涉及进度/隐私时，无痕不写入、session/revision及恢复位置必须定向覆盖；涉及生命周期/编码内容时，旧回调拒收和取消/关闭必须覆盖。这些是必要风险检查，不能全部拖到B。
- 只运行上述方法和受影响格式检查；不做全EXIF、所有格式、所有模式或全模块排列。测试已绿且无新变化就继续构建，不为提交或报告再跑一遍。
- 主代理一次独立差异审查确认授权/身份/进度/资源不变；涉及共享机制的真实扩大先限定范围，不靠“只改几行”忽略风险。

## 7. 执行roadmap

### [ ] P2-0：承接P1与编译诊断（10–20分钟）

核对HEAD/用户改动、正在运行的Gradle及设备状态；读取本文件、P1报告和目标指南。执行第3节的有界编译诊断。成果必须是具体失败原因/修复证据，或经过明确检查后的不可获取边界；不能再次只留一句Failure。Luna独立准备P1原始数字，Sol单独操作平板。

### [ ] P2-1：一级七点接线、一首一暖（20–35分钟）

不改变产品顺序，追加第4节事件和一个必要记录器测试，格式通过后构建控制版。保留R8/资源压缩、诊断签名、隔离包及SAF；记录实际源码、APK、编译策略和状态。按P1已校正的脚本和page0条件采集两个有效样本。

交付一张按真实顺序的区间表和恒等式验证，并标出CPU执行/派发等待能确认到什么程度。必要前置文件/状态可在已有授权内修正，不再次执行P0整个准备流程。

### [ ] P2-2：最大区间二级闭合（按需15–30分钟）

若一级还不能把主要等待落实到具体操作/依赖，按第5节只选一个区间、最多三个点、一首一暖；已有足够证据则注明跳过原因。完成后给出“原因已确认”“仅相关、未确认”或“必要工作、暂无安全替代”，列证据。此阶段是定位闭环，不把函数名当答案。

### [ ] P2-3：一个候选的红绿与构建（有证据时25–45分钟）

在本轮单一报告草稿中固定：事实、改动、必须保留的行为、受影响文件、最小tests。满足第6节即可继续，无须对范围内每个小改动重复求许可。候选保留**最终控制版的同一套探针**，仅改变被测产品机制，不能同时更换编译策略/动画/采集设置。

找不到安全候选时，不执行此步及候选测量；保留P0成果与有价值诊断，直接P2-5。不得为了达成计划勾选而制造无收益代码改动。

### [ ] P2-4：三次真机候选对照（有候选时20–30分钟）

首次①→同进程再次→新进程首次②，原表MKV+Perfetto与probe同次；最终控制版仅一首一暖，分别与候选首①/暖作描述性比较，候选首②作复现，不拼别的版本补齐控制组。历史P0/P1、一级/二级控制和候选分别列出来源，不混池、不扣固定探针成本。

同时报告原四阶段、P/H/Q、P2子段、输入→应用FIRST_DRAW、原表近黑与可用的系统端点。正确漫画像素必须出现，之后顺手1→2→1；有效慢样本保留，设置/身份/导出失败样本单列，不取“最好三次”。

若机制工作减少但总时长/近黑没有稳定改善，写清未确认收益，不当默认产品采用。≤60ms按每个近黑区间判断：上界≤60才通过，下界>60明确失败，跨60未确认；改善与达标分开。MKV归零PTS不能生成输入→视频首漫画，绝对视觉端点仍留待B的已存在源PTS工具。

## 3. 本轮唯一首要问题：54.8ms具体花在哪里

[PagerPageHolder.setImage](../../app/src/main/java/eu/kanade/tachiyomi/ui/reader/viewer/pager/PagerPageHolder.kt)现有顺序为：UI呈现准备与身份快照→`withIOContext { page.publishHeaderFact() }`→回到调用上下文核对代次/附件/编码身份→再次呈现绑定→进入第二段IO→记录`OPEN_PAGE`→打开正常编码流。

因此第二阶段可能包含owner/holder准备、UI与IO调度、实际本页header、恢复执行及验证。不能把54.8ms直接命名为“读图片头耗时”，也不能只因为有两次IO切换就宣布合并它们必然更快。

### 3.1 先用已有证据

先按同PID、同请求时钟，检查P0三份trace的`PAGE_LIST_READY→OPEN_PAGE`区间。可观察明确的线程执行、调度等待及已有命名slice；没有匹配slice时不能把某个线程的全部睡眠、Running或I/O统一归给header。没有明确细分就进入3.2，不耗时反复猜测旧trace。

### 3.2 必要时只增加两个本页header事件

在现有[ReaderOpenLatencyProbe](../../app/src/main/java/eu/kanade/tachiyomi/ui/reader/ReaderOpenLatencyProbe.kt)的固定事件数组**追加** `TARGET_HEADER_BEGIN`、`TARGET_HEADER_END`。不复用已撤除的章级`HEADER_FACTS_*`名字，也不在数组开头插入破坏现有按索引记录的事件。

- BEGIN和END都放在现有`withIOContext`的body里，紧贴真实`page.publishHeaderFact()`调用前后。这样测到的是本次调用的wall time，而不是把整段派发/恢复等待也命名为header。
- 传入holder已捕获的`latencyPage/chapter/request`，不在回调时重新取“当前活动请求”。默认关闭、page0限定、固定容量、区间外导出保持原样，不打印热路径日志。
- 用BEGIN首次写入成功的返回值认领这对事件；只有认领成功的同一次调用可以写END。END仅在调用正常返回后写入，不在取消/异常的finally中写成成功完成；后续调用不得替缺失的END补时间。
- 不增加新的重试、缓存、调度或产品开关。若出现重复holder、内容替换或取消而无法证明这对事件属于有效目标调用，则该对事件不用于首绘归因；不能拼接首次BEGIN与另一次END。无需为一个异常样本建立全局attempt追踪框架。
- 仅在同章/页/请求且 `PAGE_LIST_READY ≤ BEGIN ≤ END ≤ OPEN_PAGE ≤ FIRST_DRAW`、正常目标内容可见时用于下面拆分。缺事件/重试歧义保留原件和原因；原五段端点仍可独立有效，不补造缺项。

得到三个互不重叠的子段：

| 子段 | 算式 | 能说明什么 |
| --- | --- | --- |
| 前段P | BEGIN − PAGE_LIST_READY | header真正执行前的准备与等待，包含进入IO的排队；不能全算UI CPU |
| header段H | END − BEGIN | 实际调用wall time，可能含流读取/解析/锁/缓存命中；不是独占CPU |
| 后段Q | OPEN_PAGE − END | 返回、验证、呈现准备、第二次IO准入等；不能全部叫文件读取 |

逐样本验证`P+H+Q=原第二段`。若H很短，停止优先猜测header重复读取；若H长，也必须确认具体重复工作再选优化。归档打开次数或读取字节只有在实际计数后才报告，不能由事件数量推断。

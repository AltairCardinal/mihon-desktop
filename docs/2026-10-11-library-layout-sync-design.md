# 作品分类与手动双页布局同步

日期：2026-10-11。源码核查基线：`dff19a7cf1`。用户授权：设计完整方案、编写 roadmap 并实施。实现进度和验证证据见 [roadmap](roadmap/2026-10-11-library-layout-sync-roadmap.md)。本方案以当前 production 为入口，不以 HTML DEMO 或历史需求中的首期排除项限制本次授权。

## 1. 用户行为与边界

### 1.1 作品分类

用户继续在 Android/Desktop 既有作品详情或书架批量分类入口选择分类。保存成功后，通过既有手动、启动或定期同步传至同一空间的其他设备。接收端复用同名分类，不存在时创建，再更新该作品的分类集合；无需先手工建立分类。

- 一部作品可属于多个分类；传递完整集合，取消全部分类是明确的空集合操作。
- 分类身份使用名称精确匹配，区别大小写，不按本机自增 ID 匹配，不模糊合并近似名称。复用已有同名分类，保留它的本机排序和显示 flags；本机遗留同名重复分类选稳定的最小 ID，不擅自合并或删除其他分类。
- 内置未分类是空集合的显示结果，不能把系统分类 ID 0 的本地化名称创建为普通分类。
- 分类被重命名或删除时，对原来关联的作品记录新集合；远端不再使用的旧分类允许保留为空分类。创建一个尚未关联作品的空分类不独立同步。
- 不同步分类显示顺序、分类内排序、过滤条件、默认分类、应用主题或窗口设置。接收新分类采用本机默认 flags，追加到本机现有分类之后。
- 同步分类本身不收藏作品，也不取消收藏；接收端可先建立缺少的作品记录，后续收藏字段仍遵循原取消确认语义。

### 1.2 手动双页布局

用户继续使用阅读器已有“调整页面配对”入口。同步的单位是作品下的具体章节，覆盖当前持久化格式中的开篇方式、强制单页边界和明确相邻配对；不新增已被撤销的“章节开篇”专用菜单。

- 同步 `formatVersion`、`pageCount`、`openingMode`、`forcedSinglePages` 和 `manualPairStarts`。页序使用来源的零基页序，不使用屏幕左右位置。
- 持久化操作将布局全部恢复自动时，也必须同步明确清空；不能仅删除本机记录后失去同步意图。现有“本次使用默认”仅影响当前会话，不清除持久记录、不产生同步清空；本次不新增永久清空按钮。
- `currentPage` 属于当前导航，`revision` 属于本机 CAS 并发控制，均不跨设备复制。
- 章节以来源 ID、漫画原始 URL、章节 canonical URL 定位。不同来源或不同作品不按标题、章节号猜测对应。
- 沿用共享 `ChapterPairingRecord` 校验和恢复规则。对端实际页数与记录不一致时，保留数据并沿既有无效记录反馈处理，不按比例缩放页码，不强行应用。
- 接收后下次加载/重开章节使用新布局。正在显示的画面不因后台同步强制跳页；若本地旧会话随后保存，必须由 revision 冲突阻止静默覆盖，并沿现有重新载入/失败反馈处理。
- 不同步阅读方向、单双页模式、缩放、裁边、自动匹配结果、图片尺寸缓存或图片文件。手动布局只是共享引擎的输入，两个平台继续消费同一规则。

## 2. 复用与实施边界

| 现有能力 | 本次接入 |
|---|---|
| `MangaRepositoryImpl`、`SetMangaCategories`、收藏 membership 事务 | 在真实分类变更事务内记录同步操作，覆盖详情、书架批量和收藏时分类 |
| `CategoryRepositoryImpl` | 重命名/删除后记录受影响作品的新集合，保留本地 category 数据模型 |
| `ChapterPairingRepositoryImpl` 与双端应用级保存协调器 | 本地保存和 outbox 同事务，远端写入复用相同校验与持久化语义 |
| `SyncTransactionJournal`、outbox、Git transport、空间加密 | 追加字段，不建立第二套传输、账号或队列 |
| `SyncReducer`、因果头、`SyncInboxProjector` | 复用依赖等待、去重、确定性归并和原子应用标记 |
| baseline/import 与真实 SQLite 共享契约 | 冻结首次已有值、补传升级前的数据、验证重启和回滚 |
| 既有同步面板及运行日志 | 分类/手动布局操作能计入待同步量并显示可理解的类型；失败保留可重试信息 |

Android 和 Desktop 采用相同 payload、归并和 SQL 实现。平台仅保留原 UI、调度与运行环境 adapter。不得复制分类仓库或布局引擎，不扩展备份文件格式、阅读进度格式或作者同步语义。

## 3. 协议与归并契约

新增两个独立字段：`MANGA_CATEGORIES`（`SET_CATEGORIES`）、`CHAPTER_PAIRING`（`SET_PAIRING`）。两者均为完整值替换，不把设置操作伪装为收藏或已读。顶层操作分组仍复用 `FAVORITE` 和 `READING`，面板文案覆盖分类/双页调整，运行记录明确显示实际字段类型。

1. 有因果先后的操作由有效后继决定。
2. 并发有效头中，明确 USER 操作优先于 INITIAL_IMPORT/BACKUP_RESTORE 基线，避免旧设备加入复活已清空的设置。
3. 同优先级完整值按 `occurredAt` 再按稳定 effect 引用排序选一个值，所有设备得到相同结果。设备时钟不能证明现实世界的绝对先后；用户再次明确保存会建立后继并覆盖已有冲突。
4. 不把两份并发分类集合直接求并集，不把两份手动配对边界拼接为可能矛盾的布局。
5. 清空必须作为有效值存在。没有字段、没有记录或没有收到数据，不等于用户清空。
6. 校验 payload 字段集合、JSON 类型、整数范围、重复项、布局格式和配对互斥关系。每作品最多 256 个非空分类名，每名最多 512 个 Kotlin 字符，单 effect 的 UTF-8 payload 沿用 64 KiB 上限。超限不能产生部分业务写入或推进已应用标记；本地用户保存沿既有失败反馈处理。

采用双层版本：批次/传输封套、descriptor 的历史字段 `eventProtocolVersion` 和 AEAD binding 保持 1；新字段所在事件的 schema 版本为 2，旧字段事件仍为 1。新版 batch validator 明确接受同一个传输 v1 批次中的已支持 event v1/v2，新字段不得出现在 event v1。两层常量和校验须明确区分，不能全局把 `CURRENT_VERSION` 改为 2。

这保留旧事件、旧待发送批次、空间 descriptor、AAD 和恢复密钥。固定基线旧客户端要求 event 版本等于 batch 版本，且其严格 enum 解码不认识新字段，因此会拒绝新事件所在批次，不会丢掉新字段后报告成功；旧端可能显示“不兼容/数据异常”，本次无法回写已安装旧版的提示。既有修复只重取/重新投影，不删除远端新事件；应先升级旧端再重试。使用本能力的设备需要升级到支持版本；不自动改写远端历史、不重建空间、不换密钥。

## 4. 捕获、接收与本机并发

分类集合变更覆盖直接 setter、批量修改和收藏附带分类。分类重命名/删除应先获取受影响作品，在同一数据库事务修改并记录结果。未连接同步时照常保存本机，后续首次/升级基线负责补传。

手动布局成功保存才生成事件；CAS 失败、校验失败或业务事务回滚不得留下 outbox。远端应用不同布局时递增本机 revision，清空仍保留 revision，确保旧 reader 快照不能覆盖新接收数据。语义相同的布局不递增 revision，旧 format 1 与等值 format 2 也按相同布局处理，避免自身基线投影使活动阅读会话失效。

接收分类时，创建分类、更新关联、记录应用头必须原子提交。布局写入同样参与 projector 的事务。任何异常均回滚；网络重试或重启重放不重复创建分类、不重复改变 revision，不生成反向 USER 事件。

备份恢复、来源迁移和远端接收必须带明确 origin，不能因复用分类 setter 默认当成用户操作。已有同步修复应重试原数据而不是合成新的 USER 值。

## 5. 初次接入与升级补传

必须同时支持空设备、新连接设备以及已连接且已有 initial import 的升级设备：

- 新连接冻结当前真实分类和已保存布局，避免稍后读取改变造成初始快照漂移。
- 已连接空间为新增字段执行持久化、幂等、可恢复的补传，不能因历史 initial import 已存在永久跳过。
- 无分类和没有手动布局的普通初始数据不生成清空意图；明确清空的 USER 事件继续保留并胜过旧基线。
- 每个空间/代次隔离补传标记；重连、切换空间、重启和失败重试不丢失未完成数据，也不无休止重复导入。
- 不迁移全应用偏好；schema 仅在持久化补传状态确有需要时扩展，并用真实旧 schema 到新 schema 验证数据保留。
- 旧手动布局 format 1 按既有兼容规则读入，上传前转换为可验证的完整值；不因升级丢失原 revision/边界。

数据库由 schema 45 升至 46：`45.sqm` 给既有 `sync_import_entries` 增加冻结字段与 payload，并建立按空间/代次隔离的 `sync_metadata_imports` 标记。不修改旧 migration。连接和切换空间沿原 import 事务冻结元数据；已连接空间在真实 exchange 的导入阶段补扫一次，冻结和标记同事务。恢复已有冻结运行时不扩大原计划，补扫留给下一次新运行。已有布局记录损坏时不将其传播到其他设备，仍由本机阅读器既有校验处理。测试用 SQLite 文件重建 schema 45 的相关旧结构、执行真实 migration 并重开核验，不等于已安装旧 APK 的原生升级验收。

## 6. UI 固定验收

SOURCE：既有分类对话框、书架批量分类、Android/Desktop 调整页面配对、共享同步面板以及持久化失败反馈。规范入口为 [Desktop UI 规范](design/mihon-desktop-ui/README.md)，本次没有 HTML_ADAPTER。

PROJECT_POLICY：保存结果进入既有同步；新类型的计数与反馈不得被漏掉或误标成已读。

| ID | 用户路径 | 固定结果 |
|---|---|---|
| UI-C1 | A 作品详情 → 修改分类 → 同步；B → 同步 → 打开作品分类 | 完整集合一致，缺分类创建，同名分类复用 |
| UI-C2 | A 书架批量选择 → 修改/清空分类 → 双向同步 | 仅选中作品变更，B 无多余关联，不取消收藏 |
| UI-C3 | A 修改关联分类名称/删除分类 → 同步 | B 对应作品的新集合生效；不删除 B 其他作品或分类 |
| UI-P1 | A 双页阅读 → 调整页面配对 → 同步；B 同步后重开同章 | 手动开篇、边界和配对恢复；其他作品/章节不变 |
| UI-P2 | 自动化调用真实布局 repository 保存 AUTO+空边界/配对 → 同步 → B 重开同章 | 手动记录清空，沿用本机自动规则；另验证现有“本次使用默认”不产生持久化清空 |
| UI-P3 | B 已打开旧布局，期间接收 A 修改，随后 B 保存 | 不后台跳页；旧 revision 不静默覆盖，出现既有恢复/失败反馈 |
| UI-S1 | 只修改分类或布局 → 打开同步面板 → 立即同步 | 待同步计数包含新操作，记录可识别，失败可重试 |

重用原入口不增加导航层级；不需要新页面、独立开关或额外账号授权。原分类保存确认和本机错误反馈继续生效。

## 7. 验证与交付标准

只执行受影响 focused 范围。行为测试执行真实 codec/reducer、SQLite repository/journal/projector，以及双端真实入口到存储/队列的接线。测试中不能复制实现或扫描源码替代行为。

- 协议：正确 round-trip，非法 payload/大小/身份拒绝，旧数据兼容，多种收件顺序确定性，因果覆盖，并发清空与初始值优先级。
- 数据：两个不同本地 ID 的数据库，缺分类创建/同名复用/不重复创建，空集合，重命名删除，事务回滚，无回流，重复收件，首次/升级/重启补传。
- 布局：三种手动数据、format 1、明确清空、不同页数不套用、错误作品/章节隔离、远端接收使旧 CAS 失败、下一次加载恢复。
- 平台：Android 与 Desktop 共用存储契约；各至少一条实际分类入口与手动配对入口验证；同步面板真实反馈检查。
- 独立审查：由未实施 production 的主代理核查协议、持久化、初始迁移、无回流及并发路径。稳定协议先审，再进入下游；收口合并检查整体同一功能批次。必要修复最多一轮聚焦复审。
- 格式和文档：仅受影响模块/文件；`git diff --check`；核对方案描述与实现。相关文件多于 8 个属于同一跨双端共享同步能力的必要接线，不据此拆出不可验收的微提交。

本轮默认日常体验验证，不自动运行完整模块、全量、正式构建或真实用户云空间操作。若环境阻塞，记录实际命令、失败原因和未覆盖项，不能以静态阅读冒充运行通过。最终报告列出已实现、实际证据及剩余平台边界。

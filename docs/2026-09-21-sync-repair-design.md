## 2. 第一个问题：先独立验收，再延后合并

### 2.1 采用固定结构基线与显式兼容迁移

在当前 worktree 引入固定提交 `0e68f9c5e9` 中必要的数据库结构与 27–29 迁移语义，保留当前同步功能；仅移植表、列、索引、触发器及编译必需的最小适配，不整批合并作者功能、UI 或未完成需求。不直接替换整份 author_archive.sq，以免混入无关查询改动。以已有 SQLDelight schema、DatabaseMigration 和 Android/Desktop driver callback 为接入点，不另建数据库或同步协议。

目标结构包含固定作者基线和本轮同步表。按当前已知编号，候选目标为 schema 31：保留作者 27–29 历史，在后续 30 号迁移补齐同步运行表；实际分配前核对两侧已交付结构。31 是本轮候选编号，不能当成对另一分支的编号预留。禁止为避冲突跳到极大版本号。

已交付的同步版 schema 28 与作者版 schema 28 含义不同，不能仅根据 user_version 分派迁移，也不能删除历史记录后假定所有数据库来自同一谱系。保存两条历史结构的 fixture、来源提交和结构指纹，建立显式兼容入口：

| 输入数据库 | 当前 worktree 修复包应执行 |
| --- | --- |
| 新安装 | 创建完整目标结构，包括同步表 |
| 共同基线 schema 27 及更早受支持版本 | 执行原有迁移，再执行作者结构和同步结构迁移 |
| 同步分支 schema 28 | 识别已有同步表，补作者 27 号迁移缺失的缓存结构，再执行作者 28、29 迁移；保留同步记录，后续同步表迁移验证结构后跳过重复创建 |
| 作者分支 schema 28 | 执行作者 28、29 迁移和同步表迁移 |
| 真机已证实的 schema 29 | 执行作者 29 迁移和同步表迁移；不能重新执行已完成的 ALTER TABLE |
| 固定作者基线 schema 30 | 仅补同步表及必要兼容元数据 |
| 当前修复包目标结构 | 验证后正常打开，不重复迁移 |
| 未知同号结构、未来更高版本或不完整结构 | 明确阻止业务启动，显示可理解的版本不兼容原因，保留数据；不尝试降级或猜测修补 |

上述路径由同一共享兼容决策实现。指纹覆盖相关表、列类型/默认值/约束、索引和触发器，允许明确登记的两条历史谱系；不能只用“某表存在”或 application version 判断。同步 28 的预处理必须在执行普通版本区间迁移前完成。所有修补和正常迁移在同一升级事务内执行，最后验证目标结构与必要数据不变量后更新版本/兼容标记；异常整体回滚。Android 必须在 onUpgrade/创建路径进入共享决策，不能等 onOpen 才补救；Desktop 也经同一决策，不复制另一套逻辑。

不以无条件 IF NOT EXISTS 掩盖错误结构，不直接改用户数据库的 user_version，不删除重建用户库。保留同步事件身份、冻结上传制品、作者新字段、书架和阅读数据。作者新功能的 UI 不属于当前同步修复验收；仅保留结构还不够，须测试当前旧查询/更新不会清空作者字段、触发器产物或关联数据。

### 2.2 正式产物与真机验收

使用既有包名和签名，分配新的、可追溯的 APK versionCode/versionName，不继续覆写 aex.11 产物目录。分配时核对本地发布记录及目标设备版本；另一分支期间继续发版时需重新核对，不猜测固定 code 30 足够。

先用历史结构 fixture 和隔离设备证明覆盖升级，再在用户设备验收；真机数据恢复副本的取得必须采用可用、已授权方式，release 包无法 run-as 时不能声称已经备份。真实私有数据库和凭据不进仓库，结构 fixture 使用合成数据。当前仅授权设计，不自动安装 APK 或改真机数据库。

验收期间同包名修复包可能将数据库提升至当前作者包不支持的版本，因此不把未整合的作者包作为可直接覆盖回退路径。可在隔离设备继续作者侧验收。需要返回另一包时，先验证该包接受的数据库谱系或使用已验证恢复方案。

### 2.3 另一分支继续开发与最终合并

当前修复只依赖冻结结构基线，不要求另一分支停止开发。另一分支新增迁移不会使本轮已经完成的固定输入测试失效，但不属于本轮兼容承诺。

待用户确认另一分支完成并要求合并时，重新读取双方 HEAD、发布包版本、schema 与结构指纹。若双方出现“版本号相同、内容不同”，保留两条已交付路径的证据，在合并目标中增加显式结构分派和收敛迁移；不能仅在 Git 冲突中选择一方或重命名旧迁移。最终 schema 高于双方实际发布版本，具体编号届时分配。

最终合并必须分别验证“本 worktree 验收包 → 合并包”和“另一分支最终包 → 合并包”的真实覆盖升级及核心功能。不删除已发布兼容入口。当前 worktree 验收通过是阶段 A；双方完成后的合并验证是阶段 B，后者不阻塞前者，也不能被前者替代。

## 3. 共享运行与真实进度修复

- 将新请求、恢复、观察分开。STARTUP/PERIODIC/RECOVERY 共用暂停、阻塞、耗尽与 nextRetryAt 检查；普通新队列遵守偏好。用户明确继续/重试才解除对应状态；显式取消禁止恢复旧 run，但不关闭未来周期设置。active run 保持唯一，替换旧 run 必须终结其活动状态。
- 分开 attemptId、执行接管次数与连续网络失败次数。系统取消/进程重建不计网络失败。统一为首次网络失败后最多 3 次自动重试，退避 10 秒、30 秒、120 秒；第 4 次网络失败耗尽。此规则取代旧文档中“第三次失败耗尽”的矛盾表述。Retry-After 是额外下限，联网事件/前台切换不能绕过。
- 运行意图提交后立即触发调度对账；每个中断、等待与重试状态变更都产生可观察持久状态。claim/取消/完成条件写保护保留，跟随者取消不杀 owner，旧执行者释放前不能开始替代发布。
- 进度按 run、phase、segment 及稳定业务身份保存。阶段切换允许当前阶段计数从零开始；同一段的已确认计数重试不回退、不双计。已知冻结范围才有 total；新快照/新增操作进入下一段或下一轮，不跨阶段取最大值，也不将 uploaded+downloaded 当当前阶段计数。
- 导入单元提交、inbox 接收和实际投影、上传确认分别报告真实事实。接收不等于合并，上传响应未知先确认制品。计数尽量与业务事务同提交；无法同事务时从稳定业务检查点重建，覆盖“业务已提交、计数未写”窗口，不能以 UI 计数驱动业务恢复。
- 日志从可解析的漫画/作者操作产生，带本地化操作类型与结果；未知标题回退到类别。以运行、阶段、业务身份去重，不能以批次日志替代全部条目。不持久化密钥或原始异常。保留最多 20 次终态运行和每次最近 500 条，活动恢复数据不清理；日志截断有提示。
- pendingSetup 收口移至共享恢复链：真实交换成功、导入为空且连接修订仍匹配时幂等 complete。覆盖绑定后尚未建立 run 的中断窗口；完成记录与 setup 标记之间崩溃时可对账。面板观察结果并在适用时返回主页，后台不打开面板、不要求重新输密码。

## 4. 平台与页面修复

- Android 启动、ON_START、网络变化、运行状态变化统一触发调度对账；对账创建/保留与 runId 和下次到期时间匹配的后台补偿。KEEP 不能代替时间更新与尾部竞争处理。过早执行的 Worker 必须确保未来唤醒仍存在，不能直接 success 丢掉唯一任务。
- 前台到期计时与一次性 WorkManager 都只请求共享执行权；周期关闭不删除手动恢复。旧 HTTP/阶段有界等待，先取消并释放失效执行者再接管。后台交接、通知提升限制和系统停止须保留恢复意图。Desktop 同样要在周期关闭时驱动已接受运行的到期重试，仍不新增系统电源监听。
- 用户发起且需要后台持续执行的任务使用独立同步通知 channel/id，显示真实阶段/数量和绑定 runId 的暂停/取消操作；锁屏不展示标题。周期工作使用有界片段，不无条件长期前台化。提升异常区分取消与受限，记录状态并走可验证的普通任务/前台恢复路径，不吞异常后宣称提升成功。UIDT 仍不是必选。
- 抽取同一进度组件供 MAIN 与 SETUP/MERGING 使用。等待、暂停、耗尽不显示正在处理的动画假象；主动暂停与暂停导入继续分离。真实 controller 状态驱动组件，不让 UI fixture 代替 production wiring。
- 完成结果在当前面板会话保留；关闭后不补播成功提示。历史以 runId 查看概要和分页条目，最多 500 条时提示截断；新运行开始不混入旧日志。等待网络/退避时仍提供暂停。
- error_handler 使用最小启动路径，不启动数据库/同步/WorkManager 业务初始化，也不再次安装会递归启动自身的异常处理器。其页面实际使用的资源/依赖需验证，不能简单提前 return 后留下未初始化依赖。
